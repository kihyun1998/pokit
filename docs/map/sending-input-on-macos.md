# Sending input on macOS

## What it is

How `type`, `key` and `click` reach a WKWebView page on macOS without taking the user's keyboard, cursor or frontmost app, and which route each takes (#6). On the plugin route, the default on macOS, pokit's plugin inside the app gives key events to the app's own window, text the US layout has no key for to the webview as an input method commits it, and mouse events to the view under the point; pokit checks focus and delivery by evaluating in the page. `--route os` on macOS is refused today; the OS route measured for keys (`CGEventPostToPid`) is recorded here with its traps. Unless marked #33 or #34, every value here was measured in #10 with a throwaway probe against the fixture app: macOS 26.6.2 (25G83), WebKit 21624.5.1.11.3, Tauri 2.12.1, wry 0.57.0, tao 0.37.1, objc2-app-kit 0.3.2; runs on 2026-10-02 are marked, the rest are 2026-10-06.

## Governing decisions

**None.** [ADR-0001](../adr/0001-commands-talk-to-a-session.md) sits adjacent: input is a request to the session like any command, but the record decides where commands go, not how input is delivered. [ADR-0002](../adr/0002-hand-written-cdp-client.md) covers CDP, which the plugin route does not use.

## Design model

The rules come from maintainer's calls on #33 and #34, the measurements of #10, #33 and #34, and otherwise the source.

**Input bounds.** Nothing bounds the length of `type`'s text: each character is one or more plugin requests (`send_press` sends one request per event of `KeyPress::mac_events`; an inserted character is one request). Each request is one line under the channel's `MAX_REQUEST` ([Reaching the page through the plugin](reaching-the-page-through-the-plugin.md)); pokit waits `INPUT_TIMEOUT` (10 s) for each, the plugin's main thread `DELIVER_TIMEOUT` (10 s). A click point is any number; one not over the webview is refused.

### Routes

- **Keys go through the plugin, by `NSWindow sendEvent:` with the text in the event's `characters`** (`crates/tauri-plugin-pokit/src/input.rs — deliver`, the `Event::Key` arm). The page sees trusted `keydown`/`input`/`keyup` with the window behind, covered, minimized or on another Space, and not key; the text arrives as given whatever the user's input source is (see Reference behaviour). Pinned by `type_and_key_reach_the_page_behind_another_app_and_leave_the_front_and_the_cursor_alone` and `typed_text_arrives_as_given_under_a_korean_input_source` (tests/macos.rs).
- **Clicks go through the plugin, by calling `mouseDown:`/`mouseUp:` (and the right-button and dragged forms) on the view under the point** (`input::give`), found with `hitTest:` on the window's content view and kept only when it lies inside the webview (`deliver`, the `Event::Mouse` arm). A click given to the window's `sendEvent:` is dropped unless the window is key, which pokit cannot make it while the app is inactive (see Reference behaviour); hence the click goes to the view, past the window. Pinned by `clicks_reach_the_page_behind_another_app_and_leave_the_front_and_the_cursor_alone`.
- **Text the US layout has no key for goes to the webview's `insertText:replacementRange:`** (`Event::Insert`; `chord::key_for_char` gives no key). The page sees one trusted `input` with `inputType` `insertText` and no `keydown`, as `Input.insertText` raises on Windows (#33). Hangul goes the same way until #37 composes it, so `composed_chars` is 0 (`State::plugin_type_cmd`) and `capabilities` says `ime_composition: false`. A line break is sent as `Enter` (`\r\n` and `\r` become `\n` first).
- **Composing text through `NSTextInputClient` is measured, not built.** `setMarkedText:selectedRange:replacementRange:` per step, then `insertText:replacementRange:`, raised the page's composition events behind another app and on another Space (see Reference behaviour); the plugin has no marked-text event today (`input::parse` takes `keydown`, `keyup`, `flags`, `insert` and the three mouse types). Tracked: #37. Compare [Typing Korean through the IME](typing-korean-through-ime.md), where each composed key is a `Process` key-down.
- **`--route os` is refused on macOS.** For `key` and `type`: "OS input is not built on macOS yet"; for `click`: there is no OS click on macOS that leaves the cursor alone (`crates/pokit/src/support.rs — route_refused`). The route measured for keys is `CGEventPostToPid` with the text set by `CGEventKeyboardSetUnicodeString`; it needs no frontmost app but does need a focused window, and drops silently without one (see Reference behaviour). Tracked: #113. No OS route for clicks leaves the cursor alone: `CGEventPostToPid` mouse events never arrive, and the HID tap moves the cursor.
- **Route naming. Maintainer's call (2026-10-23, #33):** `--route` gains `plugin`, the default on macOS (`crates/pokit/src/request.rs — Route`, its `cfg_attr` defaults); Windows keeps `cdp`. `--route cdp` on macOS, and `--route plugin` on a CDP session, are refused as unsupported before any input (`route_refused`, checked in `State::handle`); `capabilities` names the route `plugin` with `takes_focus: false` (`support::routes`). Shown were this, and keeping `cdp|os` with `cdp` meaning the plugin on macOS (a smaller change with a name that says the wrong thing). Pinned by `input_refuses_what_macos_cannot_take_and_masks_a_secret` and `macos_clicks_through_the_plugin_and_names_no_os_route` (unit, support.rs).
- **None of the routes takes the user's keyboard, cursor or modifiers** (#10: across half covered, fully covered, behind and minimized, no route changed the frontmost app or moved the cursor, a TextEdit document in front kept its text, and Shift sent to a process left the system modifier state at 0, `CGEventSource.flagsState`, HID and combined session). Bringing the app forward is not needed by any chosen route (see Reference behaviour).

### Keys on the plugin route (#33)

Measured 2026-10-23 against the fixture app, macOS 26.6.2, with a throwaway probe sending raw `input` requests, then pinned by tests/macos.rs.

- **`chord.rs` carries a macOS key code beside each Windows one, and the delivery check expects the same codes as on Windows** (`chord::KeyPress::mac_down_codes`), since the page takes `code` from the macOS key code and `key` from `characters` (see Reference behaviour). The one difference: key code 114 is `Help` on the page, so `mac_down_codes` expects `Help` for `Insert`. Pinned by `the_page_sees_the_same_codes_on_a_mac_as_on_windows_but_help_for_insert` (unit, chord.rs).
- **A modifier goes as a `flagsChanged` event of its own** (`KeyPress::mac_events`, `MAC_MODS`: Control 59, Alt 58, Shift 56, Meta 55, pressed in that order and released in reverse, each key event carrying every held flag). The page sees each as a trusted `keydown`/`keyup`, so a chord sends the same key-downs as on Windows (`Ctrl+Shift+KeyT`: three) and `keydowns_sent` matches. A letter with Control carries its control character, as a keyboard gives it (`\u{14}` for T; `KeyPress::mac_characters`); the page's `key` was still `T`. A key that types nothing carries AppKit's function-key character (`function_key`, `\u{F700}` for `ArrowUp`). Pinned by `a_mac_chord_changes_each_modifier_around_the_key_with_its_control_character` and `a_key_that_types_nothing_carries_appkits_character`.
- **The page is not there when the port file appears.** The plugin writes its port before the main webview exists; a request then answers `no webview labelled main`. The probe's first run read that as keys being dropped. `launch` waits for readiness ([Reaching the page through the plugin](reaching-the-page-through-the-plugin.md)), so pokit never sends that early.
- **A Command chord reaches the app's menu.** `Meta+KeyQ` through `sendEvent:` quit the fixture app, as the key would from a keyboard. Over CDP on Windows, input reaches only the page and never the app's native menu. **Maintainer's call (2026-10-24, #33):** left as it is, as a keyboard behaves; shown were that and taking it to an open decision on whether the routes should match.
- **Inserted text waits for the keys before it.** Key events reach the page through WebKit's queue while `insertText:` goes straight in (see Reference behaviour), so `type` waits until the page has noted every key-down sent so far before it inserts (`keys_handled`, polling `window.__pokitKeydowns` up to `PLUGIN_KEYS_SETTLE_MS`). Measured before the wait: with the fixture stalling 30 ms per key, `type abcé` left `aébc` in 4 of 5 runs; without a stall, `abcdé` ×10 came out of order once in 9 runs, and ` Kim é한` once in 20. Pinned by `inserted_text_keeps_its_place_behind_keys_a_busy_page_has_not_handled_yet` (the fixture's `#stall` field and `window.__stallMs`).
- **The delivery check waits `PLUGIN_KEYS_SETTLE_MS` (2000 ms) for the keys**, and stops as soon as every sent key-down has arrived (`delivery`, through `delivery_js`). The events reach the page after the request that sent them returned, and on a cold runner well after. It was `KEYS_SETTLE_MS` (500 ms), the OS route's value from Windows (#73), until CI (#112): on `macos-latest` (macOS 26.6.2) `type` failed `not_delivered` in 2 of 5 runs, and the page's log showed every key arriving, the first key's keyup 552 ms after its keydown and the third keydown 701 ms after the first. 2000 ms is that worst case with margin; a check only waits that long when a key is really missing.
- **The front-app and cursor checks tell pokit from a person only so far** (`FrontAndCursor` in tests/macos.rs). It samples the frontmost app every 50 ms and fails only if the fixture came forward, so a person switching apps does not fail it. It reads the cursor around each input command; when it moved, it watches an equally long window with no input, and a cursor that moves then too is a mouse in use: `cannot_judge`, which fails on CI and is a note elsewhere. The tests that use it run only on CI (`quiet_machine`), since #33 found the maintainer's Mac in use failing them with pokit not the cause ([Testing against the fixture app](testing-against-the-fixture.md)).

### Clicks on the plugin route (#34)

Measured 2026-10-25 against the fixture app, macOS 26.6.2 (25G83), WebKit 21624.5.1.11.3, with a throwaway probe sending raw `input` requests, then pinned by tests/macos.rs.

- **A page point becomes a window point by the safe-area inset and the zoom** (`input::window_point`): `inset.left + x × scale`, `inset.top + y × scale` in the `WKWebView`'s own coordinates, `scale` being `pageZoom × magnification`, then converted to the window. Without the inset a point landed 32 pixels too high (`clientY` 252 for 284); with it, `clientX`/`clientY` matched the element's centre on `#target`, `#submit` and `#context-target`, scrolled or not. pokit sends the element's centre from `getBoundingClientRect` after `scrollIntoView` (`State::plugin_click_cmd`); an element with no size is `not_found`. This is a site of [Page pixels on the screen](page-pixels-on-the-screen.md).
- **Every move pokit sends is a left-dragged event** (`input::parse` maps `mousemove` to `LeftMouseDragged`; `give` calls `mouseDragged:`): `mouseMoved:` raises nothing while the window is not key (see Reference behaviour). That covers `--hover` and the move before every click.
- **A double click is two presses with `clickCount` 1 then 2** (`plugin_click_cmd`, `clicks`); the page saw `detail` 1, then 2, then `dblclick`. A right press raised `mousedown` (`button` 2) and `contextmenu`.
- **A right-click closes the menu WebKit opens when the page did not prevent `contextmenu`.** **Maintainer's call (2026-10-25, #34):** close it at once and say so in the result (`menu_closed`). Shown with it: leaving it open as a mouse would and saying so in `capabilities`, and refusing `--right` on macOS until a separate decision. How: the plugin counts each right-click it delivers (`crates/tauri-plugin-pokit/src/menu.rs — arm`) and notes each menu that begins tracking after it (`NSMenuDidBeginTrackingNotification`, `observe`). pokit reads whether the page prevented the trusted `contextmenu` (`NOTE_CONTEXTMENU`, `close_menu` in `crates/pokit/src/session/plugin_input.rs`), and only when it did not does it ask the plugin to close the menu (`menu` request, `menu::close`), so a menu the app opens itself after preventing the page's, as the fixture's `#context-target` does, stays open. Over 4 right-clicks in a row each menu closed within 0.25 s and the next left click landed. Pinned by `a_right_click_closes_the_menu_webkit_opens_and_leaves_the_page_taking_clicks`.
- **The menu is cancelled from a block on the main queue, not from its begin notification** (`menu::close`, `NSOperationQueue::mainQueue`, `cancelTrackingWithoutAnimation`). A menu cancelled inside its own begin notification leaves WebKit taking no more mouse events (see Reference behaviour); the block runs inside the menu's tracking loop and closes it with the page taking clicks after. The pinning test above reddened when the cancel was moved back into the notification (#34).
- **`click` returns once the page has handled the event that ends it** (`mouse_handled`, counting trusted events in `NOTE_MOUSE`, up to `PLUGIN_KEYS_SETTLE_MS`): the move of a hover, the last `mouseup`, the `contextmenu` of a right-click. The page handles a click after the request that sent it returned: with a page stalling 300 ms in each `mousedown`, a `read` straight after `click --double` saw `mouseover`, not yet `dblclick`; in a full test run a left click after a right-click read empty once in four runs. Over CDP on Windows the call returns once the page has the event. It reports nothing when the wait runs out; a click has no delivery check, as on Windows. Pinned by `a_click_returns_once_a_busy_page_has_handled_it`.
- **A point that is not over the webview is refused** (`the point is not over the page`, from `deliver`).
- **A ref is refused as unsupported** for `click`, `--into` and `type` (`refs_unsupported`, through `plugin_focus` and `plugin_click_cmd`), until macOS has a snapshot (#14).
- **The focus guard runs in the page before anything changes** (`State::plugin_focus`, `State::plugin_guard_focus`, sharing `focus_holds_js`, `focus_verdict` and `target_verdict` with the CDP route). A `type --secret` is masked as on Windows ([Masking secrets](masking-secrets.md)); pinned by `input_refuses_what_macos_cannot_take_and_masks_a_secret`.

## Reference behaviour

All in the fixture app on macOS 26.6.2, with the throwaway probes of #10 (2026-10-02 where marked, else 2026-10-06), #33 (2026-10-23) and #34 (2026-10-25).

**AppKit and WebKit, from inside the app**

- Keys given to `NSWindow sendEvent:` reached the page as trusted `keydown`/`input`/`keyup` with the window behind another app, fully covered, minimized, on another Space, and while not key (`isKeyWindow` false). The text arrived as given under 2-Set Korean (`한`, `Z`) (#10).
- The page's `code` comes from the event's macOS key code and `key` from its `characters`: key code 0 arrived as `KeyA`, 17 as `KeyT`, 126 with `\u{F700}` as `ArrowUp`; key code 114 is `code` `Help` with `key` `Insert` (#33).
- A `flagsChanged` event reaches the page as a trusted `keydown`/`keyup`: Control (59) as `ControlLeft`, Shift (56) as `ShiftLeft`, Command (55) as `MetaLeft`, with `ctrlKey`, `shiftKey` and `metaKey` set on the key between (#33).
- `insertText:replacementRange:` raised one trusted `input` (`insertText`) and no `keydown` (#33). Key events reach the page through WebKit's queue, one after the page handled the one before, while `insertText:` goes straight in (#33).
- `setMarkedText:selectedRange:replacementRange:` per step, then `insertText:replacementRange:`, raised `compositionstart`, `compositionupdate`, `input` with `isComposing` true, and `compositionend`; typing 한글 that way left `한글`, behind another app and on another Space. No `keydown` was raised for these steps; a real keyboard raises one per key (#10).
- `mouseDown:`/`mouseUp:` on wry's `WryWebView`, found with `hitTest:` on the content view, raised trusted `mousedown`/`mouseup`/`click` at the right client point (window point (165, 400) became client (165, 168) under a 32-point title bar), behind another app and on another Space (#10).
- The fixture's window has a full-size content view: the `WKWebView` is 600 points tall, flipped, with `safeAreaInsets.top` 32 (the title bar), and `innerHeight` was 568 (#34).
- `mouseMoved:` given to the view raised no `mousemove` or `mouseover` while the window was not key. `mouseDragged:` raised trusted `pointerover`, `mouseover`, `mouseenter`, `pointermove` and `mousemove`, with `buttons` 0 and `:hover` set, and a click after it was an ordinary click. `rightMouseDragged:` did the same; `otherMouseDragged:` raised nothing (#34).
- A right-click on a page that does not prevent `contextmenu` opens WebKit's own menu (Reload, Inspect Element) on screen at the point, over the app in front; the frontmost app did not change and the plugin kept answering, but the menu stayed until the app ended. The page sees no `mouseup` for that press (#34).
- A menu cancelled from inside its own `NSMenuDidBeginTrackingNotification` closed, and then every later `mousedown`, `mouseup` and `click`, left or right, was dropped (#34).
- A click given to the window's `sendEvent:` arrived (trusted) when the app was frontmost, and never with the app behind. Neither the plugin's `makeKeyWindow` nor AX's `AXMain`/`AXFocused` makes the window key while the app is inactive (#10).
- A JS-synthesised event is never trusted: `dispatchEvent(new KeyboardEvent(...))` from `WebviewWindow::eval` arrived with `isTrusted` false in every arrangement. The free WebDriver plugin for Tauri on macOS (`tauri-plugin-wdio-webdriver` 1.4.0) drives input this way (`src/platform/executor.rs` 729, 1283) (#10).

**From another process (the measured `--route os`, #113)**

- A key posted with `CGEventPostToPid` reaches the page only while the app has a focused window. Whether the app is frontmost does not matter: keys arrived trusted with the app behind (5 of 5), on another Space (9 of 9, 2026-10-02) and fully covered. With no focused window they are dropped silently: minimized, 3 of 3; restored by AX while the app was inactive, `AXFocusedWindow` was empty and 4 of 5 runs dropped every key (the fifth had a focused window again by then). Nothing is queued. `postToPid` returns nothing, so the sender cannot tell; #7 is the same gap on Windows ([Sending OS input](sending-os-input.md)). `sendEvent:` from the plugin had no such condition (#10).
- A key code becomes the character of the user's current input source: key code 0 arrived as `a` under ABC and `ㅁ` under 2-Set Korean (2026-10-02). `CGEventKeyboardSetUnicodeString` overrides that: `A`, `한` and `é` arrived as given under 2-Set Korean (#10).
- Keys posted to a process compose through the IME only while the app is frontmost: under 2-Set Korean, ㅎ ㅏ ㄴ became 한 frontmost (3 of 3) and stayed ㅎㅏㄴ behind (2026-10-02). Even frontmost no `composition*` events were raised, only `input` events whose `data` changed, and the open composition carried over to the next keys: a second run started 핞 (#10).
- Mouse events posted with `CGEventPostToPid` never arrived, in four variants (plain; window number fields set; a private event source; another point), not even with the app frontmost (2026-10-02). The same point posted to the HID tap arrived, which rules the coordinates out, but that moves the user's cursor and needs the window on top. cua's driver says the public call is not taken as live input by Chromium and posts through the private `SLEventPostToPid` instead (trycua/cua `skylight.rs` 5–8, read 2026-10-02) (#10).
- `AXPress` clicks an element without the cursor: on a button it raised trusted `focusin`, `mousedown`, `mouseup` and `click` at the element's centre, behind another app and on another Space, in 1 ms. It does nothing while minimized and needs an element that offers the action, so it is not the general click route (#10).
- `NSRunningApplication.activate` from pokit's process returned true and changed nothing on macOS 26 (2026-10-02); setting the app's `AXFrontmost` did bring it forward (#10).
- enigo 0.6.1 and rdev 0.5.3 post only to the HID tap and take no process ID (enigo `src/macos/macos_impl.rs` 140; rdev `src/macos/simulate.rs` 91). `objc2-core-graphics` 0.3.2 has `CGEvent::post_to_pid` and `keyboard_set_unicode_string` (`src/generated/CGEvent.rs` 520, 298) (#10).

## Cross-cutting invariants

- [Page pixels on the screen](page-pixels-on-the-screen.md) — site: `crates/tauri-plugin-pokit/src/input.rs — window_point` (safe-area inset, `pageZoom × magnification`).
- [Capabilities match behaviour](capabilities-match-behaviour.md) — site: `support::routes` declares the `plugin` route for `click`, `key` and `type` with `takes_focus: false` and no `os` route; `support::route_refused` refuses the routes not declared.

## Blast radius

- [Reaching the page through the plugin](reaching-the-page-through-the-plugin.md) — input assumes the channel's `eval` awaits a promise and reports a throw as `js_error`, since the focus guard, the key and mouse notes and every settle wait are plugin evals; it also assumes readiness waited for the main webview.
- [Sending input over CDP](sending-input-over-cdp.md) — both routes share `delivery_js`, `delivery_verdict`, `NOTE_KEYDOWNS` and the focus-guard functions, and assume the page sees the same `code` per key (`mac_down_codes` against `down_codes`); a change to the delivery check's fields or a key's code there changes the macOS result too.
- [Typing Korean through the IME](typing-korean-through-ime.md) — `type`'s output fields (`composed_chars`, `inserted_chars`) are shared; #37 is to compose Hangul on macOS with the same steps, so the composition model there is what the macOS route will follow.
- [Masking secrets](masking-secrets.md) — a `--secret` text travels in the plugin's `input` requests; the masking assumes nothing on the plugin route writes the text to output, logs or record.
- [Platform support](platform-support.md) — the routes and refusals `capabilities` reports are written in `support::routes` and `support::route_refused`; a route added here without them is refused or misreported.
- [Sending OS input](sending-os-input.md) — `Route::Os` is one name for two platforms; on Windows it takes focus and needs the app in front, while the macOS route measured for #113 needs a focused window but no frontmost app, so a shared rule about `os` can be wrong on one of them.
- [Testing against the fixture app](testing-against-the-fixture.md) — the input tests rely on the fixture's `#stall` field, `#context-target` menu and `#last-mouse`, and the front-app and cursor tests on `quiet_machine` running only on CI.

## Known holes / open

- `--route os` for `key` and `type` is not built. Tracked: #113.
- `type` inserts Hangul instead of composing it. Tracked: #37.
- `hold` is not built through the plugin. Tracked: #38.
- When the capture listener on the top `window` never sees the `contextmenu` (the right-click lands in an iframe, or an earlier capture listener stops the event), pokit cannot tell whether the page prevented the menu, closes nothing, reports `menu_closed: false` as for a prevented menu, and waits `PLUGIN_KEYS_SETTLE_MS` longer; WebKit's menu then stays on screen. Found by reading the code in #34's review, not measured. Tracked: #118.
- Nothing bounds the length of `type`'s text, and each character costs at least one request.
- A Command chord reaches the app's native menu on macOS but not over CDP on Windows; the maintainer left it (#33) without deciding whether the routes should match.
- A click has no delivery check; when `mouse_handled`'s wait runs out, nothing is reported.
- The macOS backend as a whole: #6.
