# Sending input on macOS

How keys, text and clicks can reach a WKWebView page on macOS without taking the user's keyboard, cursor or frontmost app, and which route each one takes (#6). Code: none yet. Every value here was measured in #10 with a throwaway probe against the fixture app: macOS 26.6.2 (25G83), WebKit 21624.5.1.11.3, Tauri 2.12.1, wry 0.57.0, tao 0.37.1, objc2-app-kit 0.3.2. Runs on 2026-10-02 are marked; the rest are 2026-10-06.

## Routes chosen

- **Keys go through the plugin, by `NSWindow sendEvent:` with the text in the event's `characters`.** The page sees trusted `keydown`/`input`/`keyup` with the window behind another app, fully covered, minimized, or on another Space, and while the window is not key (`isKeyWindow` false). The text arrives as given, whatever the user's input source is (`한` and `Z` under 2-Set Korean).
- **Composed text (IME) goes through the plugin, by calling the webview's `NSTextInputClient` methods.** `setMarkedText:selectedRange:replacementRange:` per step, then `insertText:replacementRange:`. The page sees `compositionstart`, `compositionupdate`, `input` with `isComposing` true, and `compositionend`. Typing 한글 that way left the value `한글`, with the window behind another app and again on another Space. No `keydown` is raised for these steps; a real keyboard raises one per key. Compare [[sending-input-over-cdp]], where each composed key is a `Process` key-down.
- **Clicks go through the plugin, by calling `mouseDown:`/`mouseUp:` on the view under the point.** That view is wry's `WryWebView`, found with `hitTest:` on the content view. The page sees trusted `mousedown`/`mouseup`/`click` at the right client point (window point (165, 400) became client (165, 168) under a 32-point title bar). This worked with the window behind another app and on another Space.
- **`--route os` is `CGEventPostToPid` for keys.** It is real OS input and needs no frontmost app, but see its traps below. There is no OS route for clicks that leaves the cursor alone.

## Traps

- **A key posted with `CGEventPostToPid` reaches the page only while the app has a focused window.** Whether the app is frontmost does not matter: keys arrived trusted with the app behind (5 of 5), on another Space (9 of 9, 2026-10-02) and fully covered. With no focused window they are dropped silently: minimized, the drop was 3 of 3; restored by AX while the app was inactive, `AXFocusedWindow` was empty and 4 of 5 runs dropped every key (the fifth had a focused window again by then). Nothing is queued for later. `postToPid` returns nothing, so the sender cannot tell; #7 is the same gap on Windows. `sendEvent:` from the plugin had no such condition.
- **A key code becomes the character of the user's current input source.** Key code 0 arrived as `a` under ABC and `ㅁ` under 2-Set Korean (2026-10-02). Setting the text on the event with `CGEventKeyboardSetUnicodeString` overrides that: `A`, `한` and `é` arrived as given under 2-Set Korean.
- **Keys posted to a process compose through the IME only while the app is frontmost.** Under 2-Set Korean, ㅎ ㅏ ㄴ became 한 frontmost (3 of 3) and stayed ㅎㅏㄴ behind (2026-10-02). Even frontmost, no `composition*` events were raised; only `input` events whose `data` changed. The open composition also carries over to the next keys: a second run started 핞.
- **Mouse events posted with `CGEventPostToPid` never arrive.** None arrived in four variants (plain; window number fields set; a private event source; another point), not even with the app frontmost (2026-10-02). The same point posted to the HID tap arrived, which rules the coordinates out, but that moves the user's cursor and needs the window on top. A cross-project claim agrees: cua's driver says the public call is not taken as live input by Chromium and posts through the private `SLEventPostToPid` instead (trycua/cua `skylight.rs` 5–8, read 2026-10-02).
- **A click given to the window's `sendEvent:` is dropped unless the window is key.** It arrived (trusted) when the app was frontmost, and never with the app behind. Neither the plugin's `makeKeyWindow` nor AX's `AXMain`/`AXFocused` makes the window key while the app is inactive. Hence the click route goes to the view, past the window.
- **`AXPress` clicks an element without the cursor.** On a button it raised trusted `focusin`, `mousedown`, `mouseup` and `click` at the element's centre, behind another app and on another Space, in 1 ms. It does nothing while minimized, and it needs an element that offers the action, so it is not the general click route.
- **A JS-synthesised event is never trusted.** `dispatchEvent(new KeyboardEvent(...))` from `WebviewWindow::eval` arrived with `isTrusted` false in every arrangement. The free WebDriver plugin for Tauri on macOS (`tauri-plugin-wdio-webdriver` 1.4.0) drives input this way (`src/platform/executor.rs` 729, 1283).

## Ruled out

- **Taking the user's keyboard, cursor or modifiers.** Across the four arrangements (half covered, fully covered, behind, minimized) no route changed the frontmost app or moved the cursor, and a TextEdit document in front kept its text. Shift sent to a process, as a flag or as a real Shift press, left the system modifier state at 0 (`CGEventSource.flagsState`, HID and combined session).
- **Bringing the app forward from pokit's process.** `NSRunningApplication.activate` returned true and changed nothing on macOS 26 (2026-10-02). Setting the app's `AXFrontmost` did bring it forward. No chosen route needs either.
- **Cross-platform input crates.** enigo 0.6.1 and rdev 0.5.3 post only to the HID tap and take no process ID (enigo `src/macos/macos_impl.rs` 140; rdev `src/macos/simulate.rs` 91). `objc2-core-graphics` 0.3.2 has `CGEvent::post_to_pid` and `keyboard_set_unicode_string` (`src/generated/CGEvent.rs` 520, 298).
