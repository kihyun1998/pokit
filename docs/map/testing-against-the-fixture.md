# Testing against the fixture app

How the integration tests run pokit against the fixture app: most on one instance their test binary shares, the rest on their own, one test of a binary at a time (#58). Code: `shared_fixture`, `Shared`, `Turn`, `Pokit::new`, `Pokit::launch_fixture`, `sweep_homes`, `KEEP_FAILED_HOME`, `build_fixture`, `Built` (crates/pokit/tests/common/mod.rs).

## Design model

- **A test that judges only on a machine nobody is using measures on CI only** (`quiet_machine`, `cannot_judge`, `is_ci`; `.github/workflows/ci.yml`). It returns at once elsewhere, saying CI measures it, and on CI a case where it cannot judge (no app frontmost, the mouse in use, an input source that would not select) fails instead of passing. **Maintainer's call (2026-10-23, #112):** what CI can measure is measured only on CI. It came from #33, where on the maintainer's Mac in use the cursor check failed in 2 of 4 runs and the front-app check once with pokit not the cause: the cursor moved with no input sent, and System Settings was in front. Marked: on macOS the front app at launch, the front app and cursor around `type` and `key`, and the input-source switch, which also changes the user's own input source; on Windows the `--route os`, `window activate` and OS drag tests, and the native UI tests whose menu or dialog holds the foreground. The rule for a new test: it takes the mark when a person at the machine can change its result, or it changes the person's own state.
- **CI runs `cargo fmt --check`, `cargo clippy --workspace --all-targets -D warnings` and `cargo test --workspace` on `macos-latest` and `windows-latest`**, on pushes to `main` and on pull requests. Each of the three runs whatever the one before it did, so a lint does not hide the tests' result. **The toolchain is pinned in `rust-toolchain.toml`, for local runs and CI alike. Maintainer's call (2026-10-24, #112):** the first CI run followed stable (rustc 1.99.1) while the maintainer's Mac had 1.97.0, and clippy 1.99's new `chunks_exact_to_as_chunks` failed it on code no change had touched. Shown were pinning both, following stable and fixing what each new release brings, and pinning only CI to the local version. GitHub Actions sets `CI` to `true` on every run (docs.github.com, Variables reference, read 2026-10-24). On CI the input-source test enables 2-Set Korean when it is not enabled, and disables it again after.
- **Windows runs on `windows-2022`, whose WebView2 runtime still reads `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`.** On `windows-2025` (Windows Server 2025, 10.0.26100, runtime 155.0.4283.62) WebView2 ignores the variable altogether: with `--lang=ko-KR --remote-debugging-port=0` set, the browser's command line held neither and no `DevToolsActivePort` appeared, at high integrity and at medium integrity (a scheduled task in the interactive session), and the `AdditionalBrowserArguments` policy for `pokit-fixture.exe` and a fixed port did no better. Edge 155.0.4283.62 on the same runner opened its debugging port. On `windows-2022` (10.0.20348, runtime 131.0.2903.86) the same launch opened the port and the browser carried both switches. Measured 2026-10-24 (#112). The cause is elevation, not the image: from runtime 150 WebView2 ignores the variable in an elevated app, and every hosted runner runs elevated (`runneradmin`, high integrity). With the runtime raised to 156 on `windows-2022`, every launching test failed the same way (#116, run 40257564629); see [[launching-a-test-instance]]. **Maintainer's call (2026-10-24, #112):** run Windows CI on `windows-2022` and take runtime 155 to an issue of its own (#116). Shown were that, digging into the cause in #112 before any merge, and keeping `windows-2025` red. What CI cannot show while it runs runtime 131 is `launch` on runtime 150 or later, elevated or not: an elevated `launch` there starts the app at medium integrity, which on the runners opened no usable port (#116).
- **The fixture has an empty `capabilities` directory so that it is not rebuilt on every build.** tauri-build 2.7.1 watches `<cwd>/capabilities` (`acl.rs` 437–448), and a watched path that does not exist is dirty on every fingerprint check, so the fixture recompiled on every `cargo build` (15–20 s), and each new binary's first launch on the maintainer's Mac took up to 47 s against `launch`'s 30 s ready timeout. tauri-utils reads only `json`, `toml` and `json5` files there (`parse_capabilities`), so `.gitkeep` changes nothing about the app's permissions. Since: a second build 0.69 s with the binary untouched (2026-10-24).

- **Tests that only read and act inside the page share one instance per test binary; the rest launch their own.** **Maintainer's call (2026-10-07, #58):** they were shown that each test launched its own instance, said to be 27 at once in `tests/fixture.rs` (the harness runs as many tests at once as there are logical processors, 16 here, so 16 at most, not measured), with the flaky failures (#47), the windows on their desktop and the leftovers (#56) that came with it, and the options of sharing one instance per file, capping how many run at once, or mixing the two. They asked why not one app, were shown which tests cannot share (below) and what sharing needs, and chose one shared instance per test file with only those tests on their own.
- **A test keeps its own instance when it is about the instance's life or the session's record**: launch and close, the idle end, a session dying or left stale, profiles, attaching, the run record and logs, secrets, the foreground at launch, native UI, OS input, windows, the clipboard. These read what a shared session has accumulated from other tests, or change what a reload does not undo.
- **One test of a test binary runs at a time** (`Turn`): a shared session has one page, and tests driving it at once would mix their focus and events. Every `Pokit::new` takes the turn, and `shared_fixture` takes it too, so at most the shared instance and one of a test's own are up. A thread that holds the turn takes it again without waiting, for a test that makes a second `Pokit`.
- **Between tests the shared instance is reloaded, scrolled to the top and checked** (`reset`): any measurement, trace or profile is stopped, the page is reloaded and waited for by its `timeOrigin`. When the last test left another window, a dialog or a context menu, or the session ended, the instance is launched again instead.
- **The shared instance is closed, and its home removed, when its test binary exits** (`atexit`, `close_shared`); a static is never dropped, so nothing else would. Its session also ends after 20 s without commands (`SHARED_IDLE`), for a binary that aborts, where `atexit` does not run. Reporting on a failing test never panics again (`eval_quietly`), since a panic while one is unwinding aborts.
- **A fixture build that fails puts cargo's error in the failing test's message** (`build_fixture`, the last 60 lines of its stderr). Before #76 the build's stderr went straight to the console, apart from any test, and the test said only "fixture app failed to build"; that is how #20's failure was seen three times and never diagnosed. A build's outcome, failure included, is kept for the rest of the test binary (`Built`): the first test that needs the fixture fails with cargo's error, and every later one at once with a line pointing back to it. Until #79 a failed build left the `OnceLock` empty, since its initializer panicked, and every test built again: with the fixture broken on purpose, `tests/fixture.rs` built 28 times and took 27.8 s; since, once and 8.7 s (2026-10-08).
- **A failing test keeps its home** (`Drop for Pokit` removes it only when the thread is not panicking), so its run record, logs and WebView2 profile can be read afterwards; the failure report prints its path. Each is 8–9 MB.
- **Each test binary, before its first home, removes the `pokit-test-*` homes in the temp directory that last changed more than a day ago and whose session is not running** (`sweep_homes`, `KEEP_FAILED_HOME`): no `session.json`, or its `pid` is not alive. **Maintainer's call (2026-10-08, #65):** they were shown 553 homes (3.4 GB) left from failing tests and the bystander test, and the options of never sweeping, sweeping homes a day old whose session is gone, sweeping every home whose session is gone (which removes a failing binary's home as soon as the next binary in the same run starts), and keeping failed homes under `target/`. They chose the day-old sweep. The first run removed 373 homes (2.2 GB) and its first binary took 151 s against about 13 s.
- **A test that starts the fixture outside pokit removes the profile it gave it** (the bystander in `a_stale_session_file_never_gets_a_process_pokit_did_not_start_killed`, through `remove_home`); nothing else would, since no `Pokit` owns it.
- **An attached session is closed on drop, as a launched one is** (`Pokit::attach`, #19). The handle keeps what `attach` answered (`attached`), and dropping it runs `close`, which leaves the instance it attached to running; a test that closed it already gets a second `close` that finds no session. Before, only launched handles were closed, so an attached session whose test failed before its own `close` kept running until its 10-minute idle timeout and held `target/debug/pokit.exe`, and the next build failed with access denied (#17). Three tests marked their attached sessions launched by hand to get the close.
- **A second handle on a home leaves it alone** (`Pokit::on_home`): the `wait` test drives its instance from a second thread, and that handle's drop used to remove the home, which on the shared instance is the running session's.
- **Keys someone else types are a `hold Backquote` over CDP from a second thread** (`Pokit::while_someone_types`, #78). CDP commands are not held back behind OS input, so it runs beside an OS `type` too, and it needs no person at the keyboard. The command under test starts once the first of its keys has reached the page. The page then takes 100 ms over the first keydown that is not one of them, so held keys queue up while the command is still waiting for its own (#81): without it, an OS `type abc` could take all its keys inside one 5 ms gap and see none of the others, which failed the #78 test in 2 of 11 runs on 2026-10-12. With the held keys 50 ms apart it failed 3 runs of 3 without the slow keydown and passed 3 of 3 with it. The hold is 1000 keys (about 5 s), and the helper fails with its own message unless held keys are still arriving once the command has returned (#97): at 600 keys an OS `type` once saw none of the others in a full run (1 of about 20 runs, 2026-10-22, not reproduced in 10 more), which read as a pokit failure. Reddened 2026-10-22: a hold of 1 key failed the helper's assertion, not the command's. A CDP hold cannot be stopped early, so each use waits out the rest of it.
- **Traps in the turn:** a `Pokit` dropped on a thread other than the one that made it would leave the turn taken for the rest of the binary, since the turn is counted per thread; a thread spawned by a test that calls `Pokit::new` waits for its own parent forever; and `shared_fixture` twice in one test waits for itself. No test does any of these.

## Measured

- **Before and after, two full runs each (2026-10-07, 16 logical processors):** before, 155 s and 243 s, no failures; after, 218 s and 207 s, no failures, and at most 3 fixture processes up at once (sampled every 0.5 s). Earlier full runs of the old structure that day failed 3–4 fixture tests a run, a different set each time (#47); two clean runs on each side did not show the failure rate had changed (the next entry does).
- **Failures over a fixed number of runs (2026-10-08, `main` 55f227b, #47):** 5 full runs and 10 runs of `tests/os_input.rs` alone, no input from the user during them. `tests/fixture.rs` failed nothing in 5 runs, 8 clean runs in a row counting the 3 after #59 that #47 records; before #59, most recorded runs had failed. 3 failures, all in `tests/os_input.rs`, none a dropped input (#7) or a time limit (#9):
  - twice, the CLI reported `no_session` (os error 10060) for a command the session's run record shows succeeded (`window activate`, `hold --compare`), and the session recorded its next command 10 s and 2.8 s later, well inside the CLI's 30 s and 80 s. The cause was the CLI reading the answer through a socket clone that kept a 3 s time-out (#63, see [[starting-the-session-process]]);
  - once, one OS wheel notch reached the page as two wheel events of 100, and scrolled 150 against the CDP notch's 100. The cause was pokit sending the cursor's move and the wheel in one `SendInput` call (#64, see [[sending-os-input]]).
- **Maintainer's call (2026-10-08, #47):** they were shown that table and that none of the issue's three remedies (fewer tests at once, looser time limits, waiting for #7) matches a failure seen, and chose to change nothing in how the tests run, close #47, and track the two failures as their own issues.
- **A shared instance left running holds the fixture's executable,** and the next test binary, which builds the fixture when it starts (`build_fixture`), failed with "failed to remove file … pokit-fixture.exe … access denied". Closing it at exit is what lets the binaries follow each other.
- `input_carries_its_send_time_on_the_page_clock` now reads a clock aligned at an earlier test's launch; it asserts only that the times are not negative, so it holds either way.

## Testing

- Skipping the reload between tests turned `input_is_refused_when_focus_is_outside_the_required_target` and `refused_input_leaves_focus_where_it_was` red (2026-10-07): the reset is load-bearing.
- Not tested: relaunching after a test left another window or a dialog, and the at-exit close beyond the measurement above.
- `an_attached_session_dropped_without_close_ends_and_leaves_the_app_running` (tests/fixture.rs) drops an attached handle without `close` and expects its session gone within 5 s and the app alive. Reddened 2026-10-12: with `Drop` closing only launched handles the session outlived it.
- `old_homes_whose_session_is_gone_are_swept_and_the_rest_kept` (tests/fixture.rs) sweeps a folder of made-up homes. Reddened 2026-10-08: sweeping without the running-session check, without the age check, or without the `pokit-test-` prefix each turned it red.
