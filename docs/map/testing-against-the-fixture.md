# Testing against the fixture app

## What it is

How the integration tests run the real `pokit` binary against the fixture app, and how CI runs them. The fixture app (`fixtures/app`) is the webview app this repo owns as a test target, with a page whose every behaviour has a known answer; its `pokit` feature makes it a test build with pokit's plugin. The harness (`crates/pokit/tests/common`) builds the fixture once per test binary, gives each test a pokit home of its own, shares one fixture instance per test binary among the tests that only read and act inside the page, runs one test of a binary at a time (#58), and marks the tests that can judge only on a machine nobody is using, which CI measures (#112).

## Governing decisions

**None.** [ADR-0001](../adr/0001-commands-talk-to-a-session.md) sits adjacent: the tests drive pokit through its session like any agent, and the shared instance leans on the session outliving each command, but the record decides pokit's shape, not how its tests run.

## Design model

The rules come from maintainer's calls on #58, #65, #47 and #112, and otherwise from the source.

### The fixture app

- **Two builds of one app, each in its own target directory** (`fixture_exe`: `target/fixture`; `fixture_test_build_exe`: `target/fixture-pokit`, with `--features pokit`; both through `build_fixture`). `Pokit::launch_fixture` and `shared_fixture` launch the test build on macOS and the plain build on Windows. The `pokit` feature adds the plugin and, on macOS, `activate_ignoring_other_apps(false)` (`fixtures/app/src/main.rs — main`; [Reaching the page through the plugin](reaching-the-page-through-the-plugin.md)).
- **The window opts out of focus.** `fixtures/app/tauri.conf.json` opens one window labelled `main` on `index.html` with `focus: false` ([Launching a test instance](launching-a-test-instance.md)), `withGlobalTauri` on (tests call `window.__TAURI__.core.invoke`) and no CSP.
- **What the fixture offers the tests:** `index.html` (form, panes, events log, `#stall`, whose keydowns block for `window.__stallMs`, `#context-target`, which prevents the page's menu and opens the app's own, `#on-demand`), `second.html` (a second window, `open_second`), `drag.html` (HTML5 drag with Tauri's drag-and-drop handling on or off, `open_drag_page`); the commands `backend_log`, `open_dropped`, `show_context_menu`, `pick_file`, `hide_webview_for`; a native menu (`native_menu`), a tray with `--tray` (`tray`), a dialog (`ask_in_a_dialog`, Windows), `--take-focus`, and on Windows a log of accelerator keys (`log_accelerator_keys`). It prints `fixture-backend: started` first.
- **The fixture has an empty `capabilities` directory so that it is not rebuilt on every build** (`fixtures/app/capabilities/.gitkeep`). tauri-build watches `<cwd>/capabilities`, and a watched path that does not exist is dirty on every fingerprint check (see Reference behaviour), so the fixture recompiled on every `cargo build` (15–20 s), and each new binary's first launch on the maintainer's Mac took up to 47 s against `launch`'s 30 s ready timeout. tauri-utils reads only `json`, `toml` and `json5` files there (`parse_capabilities`), so `.gitkeep` changes nothing about the app's permissions. Since: a second build 0.69 s with the binary untouched (2026-10-24).
- **A fixture build that fails puts cargo's error in the failing test's message** (`build_fixture`, the last 60 lines of its stderr). Before #76 the build's stderr went straight to the console, apart from any test, which is how #20's failure was seen three times and never diagnosed. A build's outcome, failure included, is kept for the rest of the test binary (`Built`): the first test that needs the fixture fails with cargo's error, and every later one at once with a line pointing back to it. Until #79 a failed build left the `OnceLock` empty, since its initializer panicked, and every test built again: with the fixture broken on purpose, `tests/fixture.rs` built 28 times and took 27.8 s; since, once and 8.7 s (2026-10-08).

### One instance per test binary, one test at a time

- **Tests that only read and act inside the page share one instance per test binary; the rest launch their own** (`shared_fixture`, `Pokit::launch_fixture`). **Maintainer's call (2026-10-07, #58):** they were shown that each test launched its own instance, said to be 27 at once in `tests/fixture.rs` (the harness runs as many tests at once as there are logical processors, 16 here, so 16 at most, not measured), with the flaky failures (#47), the windows on their desktop and the leftovers (#56) that came with it, and the options of sharing one instance per file, capping how many run at once, or mixing the two. They asked why not one app, were shown which tests cannot share and what sharing needs, and chose one shared instance per test file with only those tests on their own. Measured after the change, two full runs each side (2026-10-07, 16 logical processors): before, 155 s and 243 s, no failures; after, 218 s and 207 s, no failures, and at most 3 fixture processes up at once (sampled every 0.5 s). Earlier full runs of the old structure that day failed 3–4 fixture tests a run, a different set each time (#47); two clean runs on each side did not show the failure rate had changed (the count below does). The shared users are all Windows test files today (`tests/fixture.rs`, `measure.rs`, `profile.rs`, `ime.rs`); every macOS test in `tests/macos.rs` launches its own.
- **A test keeps its own instance when it is about the instance's life or the session's record**: launch and close, the idle end, a session dying or left stale, profiles, attaching, the run record and logs, secrets, the foreground at launch, native UI, OS input, windows, the clipboard. These read what a shared session has accumulated from other tests, or change what a reload does not undo.
- **One test of a test binary runs at a time** (`Turn`): a shared session has one page, and tests driving it at once would mix their focus and events. Every `Pokit::new` takes the turn, and `shared_fixture` takes it too, so at most the shared instance and one of a test's own are up. A thread that holds the turn takes it again without waiting (`HELD`, counted per thread), for a test that makes a second `Pokit`. Traps in the turn: a `Pokit` dropped on a thread other than the one that made it would leave the turn taken for the rest of the binary; a thread spawned by a test that calls `Pokit::new` waits for its own parent forever; and `shared_fixture` twice in one test waits for itself. No test does any of these. A second thread drives the same home through `Pokit::on_home`, which takes no turn.
- **Between tests the shared instance is put back as launched** (`reset`): any measurement, trace or profile is stopped, the page is reloaded and waited for by a new `performance.timeOrigin`, and scrolled to the top. When the last test left more than one target, a dialog or a context menu, or the session ended, the instance is launched again instead. The reload is load-bearing: skipping it turned `input_is_refused_when_focus_is_outside_the_required_target` and `refused_input_leaves_focus_where_it_was` (tests/fixture.rs) red (2026-10-07).
- **A shared instance reads a clock aligned at an earlier test's launch.** `input_carries_its_send_time_on_the_page_clock` (tests/measure.rs) asserts that the first key arrived no earlier than it was sent, within the clock's uncertainty plus 1 ms, and within 1000 ms of it, which holds whichever launch aligned the clock.
- **The shared instance is closed, and its home removed, when its test binary exits** (`atexit`, `close_shared`); a static is never dropped, so nothing else would. A shared instance left running holds the fixture's executable on Windows, and the next test binary, which builds the fixture when it starts, failed with "failed to remove file … pokit-fixture.exe … access denied"; closing at exit is what lets the binaries follow each other. Its session also ends after 20 s without commands (`SHARED_IDLE`), for a binary that aborts, where `atexit` does not run. Reporting on a failing test never panics again (`eval_quietly`), since a panic while one is unwinding aborts.

### Homes

- **A failing test keeps its home** (`Drop for Pokit` removes it only when the thread is not panicking), so its run record, logs and WebView2 profile can be read afterwards; the failure report prints its path and what the page received. Each is 8–9 MB. `remove_home` retries for up to 3 s while WebView2 processes still hold the profile.
- **Each test binary, before its first home, removes the `pokit-test-*` homes in the temp directory that last changed at least a day ago and whose session is not running** (`sweep_homes`, `KEEP_FAILED_HOME`): no `session.json`, or its `pid` is not alive (`process_alive`). **Maintainer's call (2026-10-08, #65):** they were shown 553 homes (3.4 GB) left from failing tests and the bystander test, and the options of never sweeping, sweeping homes a day old whose session is gone, sweeping every home whose session is gone (which removes a failing binary's home as soon as the next binary in the same run starts), and keeping failed homes under `target/`. They chose the day-old sweep. The first run removed 373 homes (2.2 GB) and its first binary took 151 s against about 13 s. Pinned by `old_homes_whose_session_is_gone_are_swept_and_the_rest_kept` (tests/fixture.rs); reddened 2026-10-08 by sweeping without the running-session check, without the age check, or without the `pokit-test-` prefix.
- **A test that starts the fixture outside pokit removes the profile it gave it** (the bystander in `a_stale_session_file_never_gets_a_process_pokit_did_not_start_killed`, through `remove_home`); nothing else would, since no `Pokit` owns it.
- **An attached session is closed on drop, as a launched one is** (`Pokit::attach`, #19). The handle keeps what `attach` answered (`attached`), and dropping it runs `close` (`close_home`), which leaves the instance it attached to running; a test that closed it already gets a second `close` that finds no session. Before, only launched handles were closed, so an attached session whose test failed before its own `close` kept running until its 10-minute idle timeout and held `target/debug/pokit.exe`, and the next build failed with access denied (#17). Pinned by `an_attached_session_dropped_without_close_ends_and_leaves_the_app_running` (tests/fixture.rs), which expects the session gone within 5 s and the app alive; reddened 2026-10-12 with `Drop` closing only launched handles.
- **A second handle on a home leaves it alone** (`Pokit::on_home`, `owns_home` false): the `wait` tests drive their instance from a second thread, and that handle's drop used to remove the home, which on the shared instance is the running session's.
- **A test can talk to the debugging port directly** (`Pokit::cdp_call`), for what pokit does not do, such as forcing a collection (`HeapProfiler.collectGarbage`). It reads the `/json/list` reply up to its `Content-Length`, because the port keeps the connection open despite `Connection: close` (the trap is [Speaking CDP](speaking-cdp.md)'s), and connects to `ws://127.0.0.1:<port>/devtools/page/<id>` rather than the `webSocketDebuggerUrl`'s host, which was refused (2026-10-22, #103).

### Someone else at the keyboard

- **Keys someone else types are a `hold Backquote` over CDP from a second thread** (`Pokit::while_someone_types`, #78). CDP commands are not held back behind OS input, so it runs beside an OS `type` too, and it needs no person at the keyboard. The command under test starts once the first of its keys has reached the page. The page then takes 100 ms over the first keydown that is not one of them, so held keys queue up while the command is still waiting for its own (#81): without it, an OS `type abc` could take all its keys inside one 5 ms gap and see none of the others, which failed the #78 test in 2 of 11 runs on 2026-10-12. With the held keys 50 ms apart it failed 3 runs of 3 without the slow keydown and passed 3 of 3 with it. The hold is 1000 keys (about 5 s), and the helper fails with its own message unless held keys are still arriving once the command has returned (#97): at 600 keys an OS `type` once saw none of the others in a full run (1 of about 20 runs, 2026-10-22, not reproduced in 10 more), which read as a pokit failure. Reddened 2026-10-22: a hold of 1 key failed the helper's assertion, not the command's. A CDP hold cannot be stopped early, so each use waits out the rest of it.

### What only a quiet machine can judge

- **A test that judges only on a machine nobody is using measures on CI only** (`quiet_machine`, `cannot_judge`, `is_ci`, `on_ci`). It returns at once elsewhere, saying CI measures it, and on CI a case where it cannot judge (no app frontmost, the mouse in use, an input source that would not select) fails instead of passing. **Maintainer's call (2026-10-23, #112):** what CI can measure is measured only on CI. It came from #33, where on the maintainer's Mac in use the cursor check failed in 2 of 4 runs and the front-app check once with pokit not the cause: the cursor moved with no input sent, and System Settings was in front. Marked: on macOS the front app at launch, the front app and cursor around `type`, `key` and `click`, and the input-source switch, which also changes the user's own input source (tests/macos.rs); on Windows the `--route os`, `window activate` and OS drag tests, and the native UI tests whose menu or dialog holds the foreground (tests/os_input.rs, tests/native.rs). The rule for a new test: it takes the mark when a person at the machine can change its result, or it changes the person's own state. Pinned by `only_the_value_github_actions_sets_marks_a_run_as_ci` and `a_quiet_machine_test_runs_on_ci_and_is_skipped_elsewhere` (tests/ci.rs). On CI the input-source test enables 2-Set Korean when it is not enabled, and disables it again after (`InputSource::select`, tests/macos.rs).
- **Failures were counted before anything changed in how the tests run** (2026-10-08, `main` 55f227b, #47): 5 full runs and 10 runs of `tests/os_input.rs` alone, no input from the user during them. `tests/fixture.rs` failed nothing in 5 runs, 8 clean runs in a row counting the 3 after #59 that #47 records; before #59, most recorded runs had failed. 3 failures, all in `tests/os_input.rs`, none a dropped input (#7) or a time limit (#9): twice the CLI reported `no_session` (os error 10060) for a command the session's record shows succeeded (`window activate`, `hold --compare`), the session recording its next command 10 s and 2.8 s later, well inside the CLI's 30 s and 80 s, caused by the CLI reading the answer through a socket clone that kept a 3 s time-out (#63, [Starting the session process](starting-the-session-process.md)); once one OS wheel notch reached the page as two wheel events of 100 and scrolled 150 against the CDP notch's 100, caused by the cursor's move and the wheel going in one `SendInput` call (#64, [Sending OS input](sending-os-input.md)). **Maintainer's call (2026-10-08, #47):** shown that table and that none of the issue's three remedies (fewer tests at once, looser time limits, waiting for #7) matches a failure seen, they chose to change nothing in how the tests run, close #47, and track the two failures as their own issues.

### CI

- **CI runs `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings` and `cargo test --workspace --no-fail-fast` on `macos-latest` and `windows-2022`** (`.github/workflows/ci.yml`, job `test`), on pushes to `main` and on pull requests, with `fail-fast: false` and a newer run on the same ref cancelling the older. Each of the three runs whatever the one before it did (`if: !cancelled()`), so a lint does not hide the tests' result. A `Runner` step prints what the machine is: on macOS `sw_vers`, the frontmost app and the enabled input sources; on Windows the OS version and the machine-wide WebView2 runtime's version.
- **The toolchain is pinned in `rust-toolchain.toml` (`1.99.1`, with clippy and rustfmt), for local runs and CI alike** (CI installs it with `rustup toolchain install`). **Maintainer's call (2026-10-24, #112):** the first CI run followed stable (rustc 1.99.1) while the maintainer's Mac had 1.97.0, and clippy 1.99's new `chunks_exact_to_as_chunks` failed it on code no change had touched. Shown were pinning both, following stable and fixing what each new release brings, and pinning only CI to the local version.
- **Windows runs on `windows-2022`, not `windows-latest`, because its WebView2 runtime still reads `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` from an elevated app** (see Reference behaviour; the workflow's matrix comment points here). **Maintainer's call (2026-10-24, #112):** run Windows CI on `windows-2022` and take runtime 155 to an issue of its own (#116). Shown were that, digging into the cause in #112 before any merge, and keeping `windows-2025` red. How `launch` meets runtime 150 and later is [Launching a test instance](launching-a-test-instance.md).

## Reference behaviour

- **GitHub Actions sets `CI` to `true` on every run** (docs.github.com, Variables reference, read 2026-10-24). Settles `is_ci`.
- **WebView2 on `windows-2025` ignores `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`; on `windows-2022` it reads it** (measured 2026-10-24, #112). On `windows-2025` (Windows Server 2025, 10.0.26100, runtime 155.0.4283.62), with `--lang=ko-KR --remote-debugging-port=0` set, the browser's command line held neither and no `DevToolsActivePort` appeared, at high integrity and at medium integrity (a scheduled task in the interactive session), and the `AdditionalBrowserArguments` policy for `pokit-fixture.exe` and a fixed port did no better. Edge 155.0.4283.62 on the same runner opened its debugging port. On `windows-2022` (10.0.20348, runtime 131.0.2903.86) the same launch opened the port and the browser carried both switches. The cause is elevation, not the image: from runtime 150 WebView2 ignores the variable in an elevated app, and every hosted runner runs elevated (`runneradmin`, high integrity). With the runtime raised to 156 on `windows-2022`, every launching test failed the same way (#116, run 40257564629). Settles the runner choice.
- **An app started at medium integrity answers nothing on its port on the hosted runners** (runtime 156.0.4314.42, measured 2026-10-26, #116, run 40269554015): `DevToolsActivePort` is written but `/json/version` is refused, where a desktop with UAC answers. Settles why CI cannot measure `launch` on runtime 150+ (#125).
- **tauri-build 2.7.1 watches `<cwd>/capabilities`** (`acl.rs` 437–448), and cargo treats a watched path that does not exist as dirty on every check. Settles the `.gitkeep`.
- **On Windows a running executable cannot be replaced**: a shared instance or attached session left running made the next build fail with access denied on `pokit-fixture.exe` and `pokit.exe` (#17, #58). Settles closing at exit and on drop.

**None.**

## Blast radius

- [Reaching the page through the plugin](reaching-the-page-through-the-plugin.md) — every macOS test launches `fixture_test_build_exe`, which assumes the fixture's `pokit` feature adds the plugin and `activate_ignoring_other_apps(false)`, and `a_build_without_the_feature_has_no_plugin_and_opens_no_port` assumes the plugin's variable name appears in the binary.
- [Launching a test instance](launching-a-test-instance.md) — Windows CI assumes `launch` works on runtime 131 at high integrity; a change to how `launch` treats elevation or the runtime version is not measured on CI (#125), and the fixture's `focus: false` is what the foreground tests there rely on.
- [Starting the session process](starting-the-session-process.md) — the shared instance assumes a session outlives its commands, ends after `--idle-timeout` and is closed by `close`; a change to idle or close changes when the shared instance dies, and `sweep_homes` assumes the session file's `pid` field.
- [Sending input on macOS](sending-input-on-macos.md) — its front-app and cursor tests are `quiet_machine` tests and use the fixture's `#stall` and `#context-target`; a change to the mark or to those elements changes what is measured and where.
- [Sending OS input](sending-os-input.md) — its tests take the quiet-machine mark and `while_someone_types`, which assumes a CDP `hold` is not held back behind OS input.
- [Sending input over CDP](sending-input-over-cdp.md) — the shared instance's `reset` assumes a reload restores focus and listeners; the focus-guard tests went red without it.
- [Measuring the page](measuring-the-page.md) — the shared instance's clock was aligned at an earlier test's launch, and `reset` stops any measurement, trace or profile a test left running.
- [Reaching native UI](reaching-native-ui.md) — `reset` relaunches when `native list` reports a dialog or context menu, so it assumes that command's fields (`dialogs`, `context_menu`).

## Known holes / open

- CI cannot measure `launch` on WebView2 runtime 150 or later, elevated or not, while `windows-2022` carries runtime 131; an elevated `launch` there starts the app at medium integrity, which on the runners opens no usable port. When the image's runtime moves past 149, or `windows-2022` is retired, every launching test fails on CI. Tracked: #125.
- Not tested: relaunching the shared instance after a test left another window or a dialog, and the at-exit close beyond the access-denied failure it fixed.
- The turn's traps (a `Pokit` dropped on another thread, a spawned thread calling `Pokit::new`, `shared_fixture` twice in one test) hang the binary rather than fail it; nothing guards against them.
- On a machine in use, the quiet-machine tests check nothing; their result exists only on CI.
- No macOS test uses the shared instance; whether macOS tests could share one, as on Windows, is not decided.
