# Reaching an app's native UI

How `native list`, `native choose`, `native dismiss`, `native tray`, `native pick` and `native answer` read and operate a launched app's menu bars, context menus, tray icons, file dialogs and dialogs on Windows. Code: `native::menus`, `native::choose`, `native::context_menu`, `native::dismiss`, `native::click_tray`, `native::tray_icons`, `native::pick`, `native::dialogs`, `native::answer`, `native::clean_label`, `native::button_matches` (native.rs), `State::native_*_cmd`, `State::keep_foreground_after` (session/native.rs), `launch::keep_foreground`.

## Design model

- **Menu bars are read and chosen through Win32, not UI Automation.** Tauri's menus (muda 0.20.0) are ordinary Win32 menus: `CreateMenu` and `SetMenu` build them, and a click arrives as `WM_COMMAND` with the entry's id (`muda` `platform_impl/windows/mod.rs` 245, 280, 1051). pokit reads the tree with `GetMenu` / `GetMenuItemInfoW` without opening anything, and chooses an entry by posting that `WM_COMMAND`. So it needs no focus and opens no menu. A disabled entry, an entry that only opens a submenu, and any entry of a window that is disabled are refused (exit 1); a path no menu has is not found (exit 5). A window is disabled while one of its modal dialogs is open, and then a user cannot reach its menu; a posted `WM_COMMAND` still would, running the command in the middle of the app's modal state, so pokit checks `IsWindowEnabled` first. **Maintainer's call (2026-10-06, #5):** menus through Win32, dialogs and reading through UI Automation. The alternatives shown were all UI Automation, which opens menus and so needs the window in front, and all Win32, which cannot read custom-drawn UI or the file dialog.
- **Labels are shown as the user sees them.** The `&` access marks are dropped (`&&` stays `&`), and the shortcut after a tab is split off: `Say &hello\tCtrl+H` is listed as `Say hello (Ctrl+H)` and chosen as `File > Say hello`.
- **Dialogs are the app's `#32770` windows, read through UI Automation.** Their text and buttons come from the element tree; buttons in the title bar, such as Close, are left out.
- **A Win32 button is pressed by posting the dialog the `WM_COMMAND` its click sends.** UI Automation's Invoke on a Win32 button sends `BM_CLICK`, which "might fail" when the dialog is not active (`BM_CLICK` remarks, win32 docs, read 2026-10-06). The fix those docs give, `SetActiveWindow`, would take the user's focus. Measured: pressed as soon as the dialog appeared, Invoke left it open 4 times out of 5, and the posted `WM_COMMAND(id, BN_CLICKED)` closed it 5 times out of 5 (2026-10-06). Buttons of other kinds still go through Invoke. Before pressing, pokit waits until the dialog's thread takes a `WM_NULL` (`SendMessageTimeout`, 1 s). Afterwards it reports `closed`, from whether the dialog's window is gone within 1 s. A button that does not close its dialog is not pressed again.
- **A localised button answers to its name without the access key.** On a Korean system the fixture's buttons are `예(Y)` and `아니요(N)`, and `native answer 예` presses the first. `native list` gives the full names.
- **What pokit sets off in the app does not keep the foreground.** A dialog activates itself when it opens, and the app regains the foreground when it closes, both with the right inherited from the terminal in front ([[launching-a-test-instance]]). Measured 2026-10-06: after `native choose "Help > Ask"`, the fixture held the foreground for about 2.1 s. So from the start of `native choose` and `native answer` until 2 s after each returns, the session gives the foreground back whenever the app takes it, as it does during `launch`; after that change the fixture never showed up in front. *Derivation, not a maintainer's call:* this extends the launch give-back the maintainer chose (#1 story 42) to the native commands, with the same best-effort limit.
- **An attached session cannot reach the native UI** (exit 7). It does not know the app's process, and the native UI is found by process.
- **A page's own `alert`, `confirm` and `prompt` are not native UI here.** WebView2 draws them in its own browser process, not as the app's `#32770` windows, so `native` does not see them.
- **A context menu is read from its menu window, and chosen in by the keyboard's messages.** The app opens it (the fixture on a right-click, through `popup_menu`); it is a `#32768` window of the app, and `MN_GETHMENU` gives the menu it shows, read like a menu bar. `native list` reports it as `context_menu`.
  - muda shows it with `TPM_RETURNCMD` and acts on the id `TrackPopupMenu` returns (`muda` 0.20.0 `platform_impl/windows/mod.rs` 906–936), so a posted `WM_COMMAND`, as for a menu bar, does nothing: measured, the entry did not run. UI Automation found no entries under the menu window either.
  - pokit highlights each entry on the path with `MN_SELECTITEM` (its position, separators counted), opens a submenu with a posted Right key, and takes the last with a posted Enter, as the keyboard would. It works with the app behind (measured 2026-10-07).
  - While a context menu is open, `native choose` chooses in it, and a path that is not in it is not found (exit 5) rather than chosen in the menu bar.
  - A menu bar's dropped-down menu is also a `#32768` window; it is told apart by its menu being one of the bar's submenus, and left out. Not tested: dropping a bar menu down needs a click on the app in front.
  - The first level is the menu window whose menu is no other open menu's submenu, and a submenu's window is the one showing that entry's submenu, already open or opened with Right; neither relies on the windows' order. Each entry on the path must be enabled.
  - `native dismiss` closes it with Escape, a level at a time.
- **A context menu takes the foreground, and pokit gives it back after `native choose` or `native dismiss` closes it.** muda calls `SetForegroundWindow` before `TrackPopupMenu`, so a right-click that opens the menu, even over CDP, brings the app to the front when Windows lets it. **Maintainer's call (2026-10-07, #5):** give the foreground back, as after a dialog, rather than refuse context menus unless the app was activated first, or offer both.
  - The window given back to is the one in front at the last click (`foreground_at_click`), since by the time of the choice the app is. It is used only when a context menu is open, and forgotten once the menu has closed, so a refused choice in it does not lose it; `native answer` and a menu bar choice give back to the window in front when they start, as before.
  - The session's give-back starts only after the menu has closed: taking the foreground from the app while its menu is open could close the menu mid-choice.
  - A refused give-back is logged once until one succeeds, not every 50 ms.
  - The session could not do it: after the first time, Windows refused its `SetForegroundWindow` 66 times in a row, with or without attaching to the app's input. A process started from the terminal in front could, at once. So the session hands the window back in its answer (`give_back`), and the command line, started from that terminal, sets it, retrying for up to a second; the result says `foreground_given_back`.
  - Measured 2026-10-07 over six right-clicks in one session: the app took the foreground at the first two and was given it back each time; at the next four Windows did not let it take the foreground at all.
- **`capabilities` says it** for `native`: a context menu the app opens holds the foreground while it is open.
- **A page's own context menu is not native UI.** WebView2 draws it in its browser process; only a menu the app opens, after the page prevents the default, is the app's.
- **A tray icon is clicked by sending its own window the message the shell sends on a click, not by clicking the taskbar.** tray-icon, the crate behind Tauri's tray, makes a hidden `tray_icon_app` window for each icon and acts on its callback message `WM_USER_TRAYICON` (6002) with the mouse message as `lparam` (tray-icon 0.25.1 `platform_impl/windows/mod.rs` 43, 389–508). `native tray` posts that message with the down and up of a left or right click, or a double click.
  - The taskbar was the alternative, through UI Automation on `Shell_TrayWnd`. Measured 2026-10-07 on Windows 11: the fixture's new icon was in the hidden-icons overflow and was not in the taskbar's tree at all, so it could not be found without opening the overflow, which would take the user's focus.
  - So only tray icons made with tray-icon are reached; another app's own `Shell_NotifyIcon` callback message is its own, and pokit says it found no tray icon. `native list` gives how many there are (`tray_icons`); their tooltips live in the shell and are not read.
  - pokit cannot see whether the app acted on the click. tray-icon drops it silently when the shell gives no rectangle for the icon (`Shell_NotifyIconGetRect`), as for an icon the app hid; the message was still posted, so `native tray` reports the click. The app's effect is the evidence.
  - `--index` follows the order Windows lists the icons' windows, the most recently raised first, which can change between calls; there is no tooltip or id to pick an icon by.
  - tray-icon places its menu, and its event's position, at the user's real cursor (`GetCursorPos`), wherever that is.
  - The fixture adds its tray icon only with `--tray`: `pokit close` ends an app by its job, so the icon is never removed, and Windows drops a dead icon only when the mouse passes over it. Every fixture launch would leave one in the user's hidden icons. The same holds for any app with a tray icon that pokit closes.
  - A left click reached the fixture's click handler with the app behind, and the foreground stayed where it was. A right click opens the icon's menu, which tray-icon shows with `SetForegroundWindow` and `TrackPopupMenu` (`show_tray_menu`); it is a context menu like any other, read and chosen as above, and the foreground is given back the same way, the window in front at the click kept by `native tray`.
- **A file is picked in a file dialog as typing its path and pressing Open would.** A file dialog is a `#32770` with a file name box, the edit control of id 1148 (`cmb13`), in the common item dialog Tauri's dialog plugin opens; the older dialogs were not tried, and may number the box differently. `native list` marks it `file`, and a folder picker would be marked too. `native pick PATH` sets that box's text (`WM_SETTEXT`) and posts the dialog the `WM_COMMAND` of `IDOK`, as `native answer` presses a button, so it works with the dialog behind. The path is made absolute from where the command ran.
  - pokit then waits up to 3 s for the dialog to close, and otherwise says it stayed open, as an Open dialog may when given a path that does not exist (not tried).
  - The dialog takes the foreground when the app opens it, as any dialog does; `native pick` gives it back to the window in front at the click that opened it, like a context menu. `window activate` forgets that click, so a deliberate activation is not undone.
  - Measured 2026-10-07 on a Korean system: the plugin's dialog listed 28 buttons through UI Automation (toolbar, scroll and navigation buttons among them, `열기` twice), so `native list` is long for one; `native pick` does not use the buttons.
- **Not covered:** a save dialog's overwrite question, multi-select, and choosing a folder; none was tried.

## Testing
- `a_file_is_picked_in_the_apps_file_dialog`: with no dialog open `pick` is not found; with the fixture's open dialog, a file whose name has a space is picked, the page shows its path, and the dialog closes. Reddened 2026-10-07: the wrong control id, the Cancel button's id for Open's, and another path typed each turned it red. Its give-back check, like the others', checks something only when the app took the foreground.
- `the_tray_icon_is_clicked_and_its_menu_chosen_in`: a left click reaches the app without moving the foreground; a right click opens the menu, whose entry is chosen. Reddened 2026-10-07: sending only the button's down, sending a left click for a right one, and not finding the icon's window each turned it red. Its give-back check, like the context menu test's, checks something only when the app took the foreground at the menu.

- `a_context_menu_is_read_chosen_in_and_dismissed` checks the foreground came back only when the app took it at the menu's opening, observed rather than predicted, and so tests nothing about it in a run where Windows kept the app back at both openings (it prints which); it holds `FOCUS` with the dialog's focus test so neither moves the foreground under the other: `window::can_take_foreground` said it could not while it did ([[sending-os-input]], #48). Reddened 2026-10-07: falling through to the menu bar, Escape for Enter, no Escape on dismiss, choosing a disabled entry, and dropping the command line's give-back each turned it red.

- `tests/native.rs` takes button names from `native list`, because they follow the system's language.
- `a_dialog_the_app_opens_does_not_keep_the_foreground` only tests anything when it descends from the foreground app (`window::can_take_foreground`). With the terminal's window owned by a sibling process of the shell's ancestor, it returns; a mutation removing the give-back after `native choose` could not be tried that way (2026-10-07).
