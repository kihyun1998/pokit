# Tracing the page

## What it is
How `trace start` / `trace stop` record a Chromium trace of the current page on Windows, save it to the run record, and summarise the busiest renderer main thread's time by group (script, style, layout, paint, GC, other). It also holds the rules a trace and a CPU profile share — one recording at a time, a reload voids the run, the file goes to the run record unmasked, nothing cleans up a recording left running — which [Profiling the page](profiling-the-page.md) links. On macOS `trace` is refused: there is no scripted path to WebKit's Timeline (`NO_TIMELINE`, support.rs, #1).

## Governing decisions
- [ADR-0001](../adr/0001-commands-talk-to-a-session.md): a recording lives in the session between `start` and `stop` (`State::tracing`, `State::profiling`), on the connection the session holds.

[ADR-0002](../adr/0002-hand-written-cdp-client.md) is adjacent: it decides that pokit speaks CDP through its own client, which `Tracing.*` and `IO.*` go through, not how a trace is recorded or read.

## Design model
The rules come only from the source, from prior art read on a date (Puppeteer, Lighthouse), and from issues #4, #22 and #88; no maintainer's call is recorded for tracing. Size: nothing bounds how long a trace runs or how large it grows. The file is written as the stream arrives and summarised one event at a time, so memory no longer follows the file's size (#88), but `trace stop`'s time does, against a fixed CLI wait (see Known holes).

**Recording and reading the trace**
- **The trace comes back as a stream.** `State::trace_start_cmd` sends `Tracing.start` with `transferMode: ReturnAsStream`; `Tracing.end` is followed by a `Tracing.tracingComplete` event carrying an `IO` stream handle, which `read_stream` reads with `IO.read` (1 MiB at a time) until `eof` and then closes. The waiter for that event is registered before `Tracing.end` is sent (`State::expect_event`, session/pages.rs), so the event cannot arrive unheard; a waiter whose page is gone is dropped by the next target sync (`State::sync_targets`), so the wait fails at once instead of timing out. The browser has `TRACE_COMPLETE_WAIT` (30 s) to send the event. The stream is closed whether or not reading it succeeds. Each chunk is decoded and written to `trace-<n>.json` as it arrives, so the whole trace is never held; a stop whose read fails removes the part written, so no cut-short `trace-<n>.json` is left in the run record (not covered by a test: nothing in the fixture makes `IO.read` fail). The result carries the browser's `dataLossOccurred` as `data_loss`.
- **The categories are Puppeteer's defaults, trimmed, plus `v8`** (`trace::CATEGORIES`): `devtools.timeline`, `disabled-by-default-devtools.timeline`, `…timeline.frame`, `toplevel`, `v8`, `v8.execute`, `blink.user_timing`; everything else is excluded (`excludedCategories: ["*"]`). Dropped from Puppeteer's list: stacks, `cpu_profiler`, `latencyInfo` and `blink.console`, which no summary reads. `v8` is Lighthouse's, for compile events.
- **The CLI waits `TRACE_STOP_WAIT` (60 s, request.rs) on top of its own `--timeout`** for `trace stop` (`Request::extra_wait`).

**Summarising**
- **Time is split the way Lighthouse splits it.** Each event's self time is its duration less its children's. It goes to the group its own name claims, else its parent's group, else `other` (`trace::attribute`, `trace::group_of`). The names per group are Lighthouse's `task-groups.js`, and the inheritance is `main-thread-tasks.js` `_computeRecursiveTaskGroup` (main, read 2026-10-06). *Derivation, not a maintainer's call:* #4 asks for style, layout, paint, GC and the rest, so Lighthouse's `styleLayout` is split into `style` and `layout`, its two script groups are one `script`, and `parseHTML` falls into `other`. Pinned by `self_time_goes_to_the_named_group_and_unnamed_children_inherit_it` (trace.rs).
- **The summary is read back from the saved file, one event at a time** (`trace::summarize`, #88). A trace is never parsed into one JSON tree: each event is read into the few fields the summary uses (`ph`, `pid`, `tid`, `name`, `ts`, `dur`, `args.name`; `trace::Event`) and dropped, and a slice keeps the group its name claims instead of the name (`trace::Slice`). Top-level keys other than `traceEvents` are skipped unread, and a bare array of events is read too. Fields are read loosely (a missing or odd value counts as absent), but an `args` that is not an object, or a file that is not complete JSON, fails the stop with "the trace is not JSON". The read runs on a blocking thread (`summarize_trace`) so the session's other commands keep answering. Holding the bytes and then the tree, as before #88, peaked at about eight times the file's size (measured 2026-10-23, #88). The unit tests beside `trace::summarize` cover the object and the bare array, other top-level keys skipped (one holding its own `traceEvents`), odd field values read past, and a cut-short trace.
- **Memory stays under the trace's size.** `stopping_a_long_trace_holds_less_memory_than_the_trace_itself` (tests/profile.rs) traces 20 s of CDP input on a fixture of its own (a session's peak counts its whole life) and requires the session's peak working set to stay under the trace file's size, with the file over 50 MB. Measured: a 103 MB trace, peak 31 MB. Reddened 2026-10-23: the old code peaked at 941 MB on a 100 MB trace; holding the whole file in memory while streaming the parse peaked at 130 MB on 99 MB.
- **Only the busiest renderer main thread is summarised** (`trace::busiest_main_thread`). Of the threads named `CrRendererMain`, the one with the most time in top-level slices; `window_ms` is that thread's first slice to its last. Begin/end pairs are paired by order on their thread and counted like complete events (`Threads::add`; `begin_and_end_pairs_count_like_complete_events`). Slices are assumed to nest, as they do on a main thread: one that only partly overlaps another is not counted as top-level (`trace::top_level`), and its whole duration comes off the other's self time (`trace::attribute`). A trace with no such thread says so (`a_trace_with_no_renderer_main_thread_says_so`).

**Rules a trace and a profile share** ([Profiling the page](profiling-the-page.md) links these)
- **The file is saved in the run record, numbered like the record's next entry** (`State::record_file`, session/profiling.rs): `trace-<n>.json`, which opens in the DevTools Performance panel, or `profile-<n>.cpuprofile`. The result carries the path (`with_file`). The run record itself is [The run record](the-run-record.md).
- **A reload voids the run (exit 8, `page_reloaded`), as it does for `measure`.** `start` records `performance.timeOrigin` (`time_origin`); `stop` compares it after saving the file (`check_same_document`). The recording is still saved, and its path is in the error. Pinned by `a_reload_during_a_trace_or_profile_voids_the_run_and_keeps_the_file` (tests/profile.rs), which also requires a fresh `start` to work after the void run.
- **A recording stays running until its `stop` gets that far.** The state is cleared only once `Tracing.end` or `Profiler.stop` has succeeded (`State::trace_stop_cmd`, `State::profile_stop_cmd`), so a failed `stop` can be retried instead of leaving a recording pokit has forgotten.
- **A second `start` is refused by pokit, with what to do** ("already running; run `… stop` first", exit 1). Pinned by `stop_without_start_and_a_second_start_are_refused` (tests/profile.rs).
- **Two `start`s arriving together run one after the other** (`State::trace_starting`, `State::profile_starting`, held for the whole `start`), so the second finds the first running and gets pokit's refusal. Without it both passed the check, which comes before several awaited calls, and the loser of a trace got Chromium's "Tracing has already been started (possibly in another tab)" (1 try in 3, 2026-10-08, #22). A `start` that fails gives the lock back with the slot still empty, so nothing has to be undone. The same race was not seen for `profile` in 20 tries without the lock; its lock is there because the code has the same shape. Pinned by `two_starts_at_once_give_one_recording_and_pokits_own_refusal` (tests/profile.rs), ten rounds each.
- **The saved files are not masked.** Secret masking ([Masking secrets](masking-secrets.md)) covers text pokit prints and records; a trace or profile holds script and resource URLs (query strings included) and function names, not typed text.
- **Nothing cleans up a recording that was never stopped, on purpose:** the browser ends it when the session's CDP connection closes, and the session's exit closes its sockets. For a trace: when a CDP session detaches, Chromium's `TracingHandler::Disable` stops its trace (`content/browser/devtools/protocol/tracing_handler.cc` 594–598). `closing_an_attached_session_ends_its_trace` (tests/profile.rs) holds this: tracing is one per browser (`tracing_handler.cc` 836–839, "Tracing has already been started"), so a trace left running would refuse the next session's `trace start`. The profile's side is in [Profiling the page](profiling-the-page.md).

## Reference behaviour
- **Prior art for the stream:** Puppeteer's `Tracing.ts` and `getReadableFromProtocolStream` (`puppeteer-core`, main, read 2026-10-06) register for `tracingComplete`, read the stream to `eof` and close it, in the same order.
- **Prior art for the groups:** Lighthouse `task-groups.js` and `main-thread-tasks.js` `_computeRecursiveTaskGroup` (main, read 2026-10-06), as above.
- **Chromium ends a detached session's trace and allows one trace per browser:** `tracing_handler.cc` 594–598 and 836–839, as above.
- **`trace stop` after 60 s of CDP input** (`hold KeyA --count 3000 --interval 20 --into #stall`, debug build, 2026-10-23, #88). Before: a 290.5 MB trace (1,358,318 events), the session's working set peaked at 2,351.7 MB, and the CLI gave up at its 90 s wait (the default `--timeout` 30 s plus `TRACE_STOP_WAIT` 60 s) with no answer. After: a 291.7 MB trace answered in 36.3 s with the session peaking at 54.6 MB. Of those 36 s, parsing took 14.1 s in the debug build (1.4 s in release); the rest is reading the stream and the browser finishing the trace. 60 s idle: 2.5 MB, 371 ms both before and after, peak 38.5 MB before and 20.2 MB after.
- **The summary did not change across #88:** the idle and the input trace recorded before the change gave the same fields, value for value, from the old and the new code (release build, 2026-10-23).
- **Ten keys on the fixture, 60 ms stall each:** the trace held 5,233 events in 1.25 MB (two `IO.read` chunks of 1 MB). The busiest main thread was busy 623 ms, of which `script` was 606.8 ms (2026-10-06). `a_trace_of_a_stalling_page_attributes_the_time_to_script` (tests/profile.rs) checks the attribution on the fixture.

## Cross-cutting invariants
**None.**

## Blast radius
- [Profiling the page](profiling-the-page.md) — it relies on the shared rules here (`check_same_document`, `State::record_file`, the start lock, clearing state only after the browser's stop succeeds); a change to any of them changes the profile's behaviour too.
- [Measuring the page](measuring-the-page.md) — both treat a changed `performance.timeOrigin` as a reload that voids the run; a different reload test here would make the two disagree on the same page.
- [The run record](the-run-record.md) — `State::record_file` numbers the file from the record's next sequence number without taking it; a change to how the record numbers entries or where it lives moves or collides the saved trace.
- [The app's pages](the-apps-pages.md) — the `tracingComplete` wait depends on the target sync dropping waiters of gone pages, and on events being routed by target; a sync that stops dropping them turns a closed page into a 30 s timeout.
- [Speaking CDP](speaking-cdp.md) — each `IO.read` chunk (1 MiB, base64 when binary) is one CDP reply and must fit the client's message limit.
- [Masking secrets](masking-secrets.md) — masking assumes saved trace and profile files hold no typed text; a category that records input text would leak it unmasked.

## Known holes / open
- **`trace stop`'s time grows with the trace against a fixed 90 s CLI wait** (default `--timeout` 30 s plus `TRACE_STOP_WAIT` 60 s). A longer trace than 60 s of input is unmeasured; if linear, input traces past about 2.5 minutes would exceed it in a debug build. Where the non-parse time goes (the browser finishing vs `IO.read` round trips) is unsplit. Tracked: #108.
- **A failed `IO.read` mid-stream is untested:** nothing in the fixture makes it fail, so removing the cut-short file is read from the code only.
- **Nothing bounds a trace's length or size**; only time (#108) is known to grow with it.
- **macOS has no trace:** refused (`NO_TIMELINE`, #1).
