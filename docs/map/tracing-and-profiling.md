# Tracing and profiling the page

How `trace start` / `trace stop` and `profile start` / `profile stop` record the page on Windows, and how the results are summarised. Code: `State::trace_start_cmd`, `State::trace_stop_cmd`, `State::profile_start_cmd`, `State::profile_stop_cmd`, `read_stream` (session/profiling.rs), `State::expect_event` (session/pages.rs), `trace::summarize`, `profile::summarize`.

## Design model

- **The trace comes back as a stream.** `Tracing.start` asks for `transferMode: ReturnAsStream`; `Tracing.end` is followed by a `Tracing.tracingComplete` event carrying an `IO` stream handle, which is read with `IO.read` until `eof` and then closed. The waiter for that event is registered before `Tracing.end` is sent, so the event cannot arrive unheard; a waiter whose page is gone is dropped by the next target sync, so the wait fails at once instead of timing out. The stream is closed whether or not reading it succeeds. Prior art: Puppeteer's `Tracing.ts` and `getReadableFromProtocolStream` (`puppeteer-core`, main, read 2026-10-06), which do the same in the same order.
- **The categories are Puppeteer's defaults, trimmed, plus `v8`.** `devtools.timeline`, `disabled-by-default-devtools.timeline`, `…timeline.frame`, `toplevel`, `v8`, `v8.execute`, `blink.user_timing`; everything else is excluded. Dropped from Puppeteer's list: stacks, `cpu_profiler`, `latencyInfo` and `blink.console`, which no summary reads. `v8` is Lighthouse's, for compile events.
- **Time is split the way Lighthouse splits it.** Each event's self time is its duration less its children's. It goes to the group its own name claims, else its parent's group, else `other`. The names per group are Lighthouse's `task-groups.js`, and the inheritance is `main-thread-tasks.js` `_computeRecursiveTaskGroup` (main, read 2026-10-06). *Derivation, not a maintainer's call:* #4 asks for style, layout, paint, GC and the rest, so Lighthouse's `styleLayout` is split into `style` and `layout`, its two script groups are one `script`, and `parseHTML` falls into `other`.
- **Only the busiest renderer main thread is summarised.** Of the threads named `CrRendererMain`, the one with the most time in top-level slices; `window_ms` is that thread's first slice to its last. Begin/end pairs are paired by order on their thread and counted like complete events. Slices are assumed to nest, as they do on a main thread: one that only partly overlaps another is not counted as top-level, and its whole duration comes off the other's self time.
- **A recording stays running until its `stop` gets that far.** The state is cleared only once `Tracing.end` or `Profiler.stop` has succeeded, so a failed `stop` can be retried instead of leaving a recording pokit has forgotten.
- **A reload voids the run (exit 8, `page_reloaded`), as it does for `measure`.** `stop` compares `performance.timeOrigin` with the one at `start`. The recording is still saved, and its path is in the error.
- **Both recordings are saved in the run record.** `trace-<n>.json` opens in the DevTools Performance panel; `profile-<n>.cpuprofile` in its profiler. The result carries the path.
- **A profile's self time comes from sample spans, not hit counts.** Each sample runs from its own time to the next sample's, and the last one to the profile's end. Functions are named `name @url:line:col`, counted from 1, as DevTools shows them, so a minified build still points at a place. `(idle)`, `(program)` and `(garbage collector)` are reported apart from the page's functions.
- **Nothing cleans up a trace or profile that was never stopped, on purpose.** When a CDP session detaches, Chromium's `TracingHandler::Disable` stops its trace (`content/browser/devtools/protocol/tracing_handler.cc` 594–598). V8's session destructor disables the profiler agent, which stops its profiles (`v8-inspector-session-impl.cc` 164–173, `v8-profiler-agent-impl.cc` 234–248). The session's exit closes its sockets, so both end with it. `closing_an_attached_session_ends_its_trace` holds this: tracing is one per browser (`tracing_handler.cc` 836–839, "Tracing has already been started"), so a trace left running would refuse the next session's `trace start`.
- **The saved files are not masked.** Secret masking covers text pokit prints and records; a trace or profile holds script and resource URLs (query strings included) and function names, not typed text.
- **A second `start` is refused by pokit, with what to do.** V8 refuses a second profile on its own, but as "Cannot change sampling interval when profiling", which does not say a profile is running.

## Measured

- **Ten keys on the fixture, 60 ms stall each:** the trace held 5,233 events in 1.25 MB (two `IO.read` chunks of 1 MB). The busiest main thread was busy 623 ms, of which `script` was 606.8 ms. The profile gave `stallOnKey` 329 ms of self time and the native `now` it calls 261 ms (2026-10-06).
