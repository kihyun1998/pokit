# Reaching the page through the plugin

## What it is

How the macOS session reaches the page. `launch` starts the app's test build with a token and a port-file path in its environment, pokit's Tauri plugin inside the app opens a loopback channel and writes its port, and the session waits until the main webview's page has loaded. From then on `eval`, `read`, `wait`, clock alignment and the input commands reach the page through that channel. This note covers the plugin crate's shape (its gates, its channel, its `eval`), the session's start and readiness on macOS, the plugin side of the page-engine seam, and how the session ends the app. Measured against the fixture app on macOS 26.6.2 with Tauri 2.12.1, wry 0.57.0, objc2-web-kit 0.3.2 (2026-10-06, #11) unless marked.

## Governing decisions

- [ADR-0001](../adr/0001-commands-talk-to-a-session.md): the plugin is an engine behind the same background session as CDP, not a session of its own, so the listener, hello and token check, run record, `status`, watchdog and `shutdown` are the session's ([Starting the session process](starting-the-session-process.md)).

[ADR-0002](../adr/0002-hand-written-cdp-client.md) sits adjacent: it decides how pokit speaks CDP; the plugin's channel is pokit's own protocol, which that record does not cover.

## Design model

The rules come from maintainer's calls on #11 and #16, and otherwise from the source.

**Input bounds.** The channel reads one request line of at most `MAX_REQUEST` (4 MiB) per connection and waits at most `READ_TIMEOUT` (5 s) for it (`crates/tauri-plugin-pokit/src/channel.rs — serve`). It accepts any number of connections, one thread each (`channel::open`); nothing bounds how many are open at once. An `eval` waits the request's `timeout_ms`, `DEFAULT_TIMEOUT_MS` (30 s) when none is given; a `menu` request waits at most `MAX_MENU_WAIT_MS` (10 s). On pokit's side `Plugin::request` reads the reply line with no size bound.

### The plugin's shape

- **Three gates, each on its own.** The app compiles the plugin in only under a feature of its own (`pokit` in the fixture, `fixtures/app/Cargo.toml`), so a build without it carries no plugin at all; `a_build_without_the_feature_has_no_plugin_and_opens_no_port` (tests/macos.rs) checks the binary for `POKIT_PORT_FILE` and that it writes no port and listens nowhere. A build with it opens nothing unless `TOKEN_VAR` (`POKIT_TOKEN`) is non-empty and `PORT_FILE_VAR` (`POKIT_PORT_FILE`) is set (`channel::open`), which only `launch` does. The channel binds `127.0.0.1` only (`the_plugin_listens_on_loopback_only`), and every request must carry the launch's token, compared in time that depends only on length (`channel::same_token`, `a_token_matches_only_itself`); a refused request is answered `unauthorised` and not run (`a_request_without_the_token_is_refused`). The token is 16 random bytes as hex (`crates/pokit/src/home.rs — token`).
- **A connection that sends no request line within 5 s is dropped** (`READ_TIMEOUT`). Without it, 50 silent connections held 50 threads for as long as they stayed open, token or not (#11's review); with it, the 50 extra threads were gone 7 s later while the connections were still open (measured 2026-10-06, #11). No test pins it.
- **What the token guards against, and what it does not.** It keeps out other users, other machines and any local process that does not know it. It does not keep out a process of the same user that reads the app's environment: `ps eww -p <app>` printed `POKIT_TOKEN` with its value (measured 2026-10-06, #11). WebView2's debugging port takes no token at all ([Launching a test instance](launching-a-test-instance.md)).
- **Only the app's feature keeps the plugin out of a shipped build.** Nothing checks the build profile, so an app built for release with `pokit` among its features carries a channel any process of the same user can open by starting the app with the two variables set, and the page world it evaluates in can call the app's Tauri commands. **Maintainer's call (2026-10-06, #11):** keep the feature as the only gate, because #1 defines the test build as optimised like a release, which a `debug_assertions` gate would refuse. The alternatives shown were a second opt-in feature for release profiles, and gating on `debug_assertions`. An app keeps `pokit` out of its default features.
- **The port goes through a file, not a fixed number.** The plugin binds port 0 and writes the port it got to the port file in the instance directory, as WebView2 writes `DevToolsActivePort`. It writes a temporary file and renames it (`channel::write_port`), so `wait_port` never reads a half-written number.
- **The channel's other ops answer `unsupported` off macOS.** `channel::answer` takes `ping`, `webviews`, `eval`, `input` and `menu`; on another OS `eval`, `input` and `menu` reply `unsupported` (the `#[cfg(not(target_os = "macos"))]` bodies of `channel::evaluate`, `channel::deliver`, `channel::menu_closed`). pokit maps the reply's `js_error`, `timeout`, `not_found` and `unsupported` to its own kinds and every other kind, `unauthorised` and `bad_request` included, to `error` (`crates/pokit/src/plugin.rs — Plugin::request`). pokit waits `REPLY_MARGIN` (2 s) longer than the page's own timeout for a reply.
- **The test build also leaves the frontmost app alone.** The fixture's feature sets `activate_ignoring_other_apps(false)` (`fixtures/app/src/main.rs — main`); the measurement is under Reference behaviour. `launch_leaves_the_frontmost_app_frontmost` pins it; it runs only on CI (`quiet_machine`), and with no app frontmost it cannot judge, which fails on CI ([Testing against the fixture app](testing-against-the-fixture.md)).

### `eval`

- **It goes through `callAsyncJavaScript`, not Tauri's `eval_with_callback`** (`crates/tauri-plugin-pokit/src/eval.rs — call`), in the page world (`WKContentWorld::pageWorld`) of the main frame. wry's own macOS `eval` does not await a promise, drops the error and can abort the app (see Reference behaviour). `callAsyncJavaScript:arguments:inFrame:inContentWorld:` awaits and reports the exception, and the body hands back `JSON.stringify` text (`HELPERS`: `__pokitJson`, `__pokitThrown`), so nothing native is serialised. That matches the Windows contract (`Runtime.evaluate` with `awaitPromise` and `returnByValue`): a DOM node comes back as `{}`, `undefined` and a function as `null` (`eval_runs_in_the_page_and_close_ends_the_app`).
- **The expression is compiled in place first, and through `eval` only when that is a syntax error** (`eval::evaluate`, `expression_body`, `STATEMENTS_BODY`). A body `return await (<expression>)` runs whatever the page's CSP says; an `eval()` inside the page does not. Measured on the fixture with `script-src 'self'` added to the page: the page's own `eval` threw `EvalError: Refused to evaluate a string as JavaScript`, an expression (`40 + 2`) still answered 42, and a list of statements failed with that `EvalError` as a `js_error` (2026-10-06, #11). A list of statements (`var a = 20; a + 1`) is not an expression, fails to compile with a `SyntaxError` before anything runs, and is retried as `(0, eval)(expression)` for its completion value, within what is left of the timeout. So under a CSP without `'unsafe-eval'`, only expressions work. The fixture itself sets no CSP (`fixtures/app/tauri.conf.json`, `"csp": null`).
- **Only a compile error is retried, so nothing runs twice.** A `SyntaxError` can also be thrown while the code runs (`JSON.parse('{')`). When the retry looked only at the error's text, such an expression ran twice: a counter it bumped read 2 (#11's review). The body now catches whatever the code throws and hands it back as `{"thrown": …}`, marked `ran` (`reply_of`), so only a failure to compile reaches WebKit's own error, and only that is retried (`is_compile_error`; the mark is removed before pokit sees it, `without_ran`). Pinned by `eval_runs_in_the_page_and_close_ends_the_app` with a counter, and `what_the_code_threw_is_a_js_error`.
- **A promise WebKit dropped is a `timeout`.** WebKit can answer a never-settling promise at once (see Reference behaviour); `reply_of` reports its `UNREACHABLE` error as `timeout`, the kind Windows gives the same promise. `a_promise_webkit_dropped_is_a_timeout` pins the mapping, since the integration test cannot force the collection.
- **The reply carries an engine of its own.** Every command's output says `"engine": "plugin"` on macOS (`crates/pokit/src/output.rs — ENGINE`); the rest of the output's shape is [the command-line contract](the-command-line-contract.md).

### One session, two engines

- **The plugin is an engine behind the same session as CDP.** `through_plugin::start` launches and waits for readiness, then hands over a `State` whose `plugin` is set (`through_plugin::session`); the rest is the CDP session's ([Starting the session process](starting-the-session-process.md)). So a macOS launch writes `runs/<stamp>-<pid>/record.jsonl` and reports `session_pid`, `record_dir` and `clock` as Windows does (#16), plus `plugin_port` and `main.webview` (`State::status`). Pinned by `a_session_through_the_plugin_answers_eval_and_keeps_the_run_record` (unit, against a fake plugin) and `launch_reports_the_session_and_the_run_record_keeps_each_command`. Page discovery and the profile sweep do not run for a plugin session (the `state.plugin.is_none()` branch in `crates/pokit/src/session/mod.rs`). `attach` is refused on macOS (`through_plugin::start`).
- **The seam holds only what both engines do today: evaluate in the page.** `State::page` gives the plugin's main webview as a `Page::Plugin` (`crates/pokit/src/session/page.rs — PluginPage`, `Page::eval`); the seam itself and its CDP side are [The app's pages](the-apps-pages.md). Through it go `eval`, clock alignment, `wait` and `read` by selector (`read` and `wait` since #12); `type` and `key` (#33) check focus and delivery through it and send their keys through the plugin's `input` request, outside the seam; `click` (#34) finds its element through it and sends its mouse events the same way ([Sending input on macOS](sending-input-on-macos.md)). Snapshot, refs, logs, the probes and the failure screenshot stay CDP code, and `State::handle` refuses every request `support::plugin_answers` does not name before it reaches them ([Platform support](platform-support.md)). They do not fit evaluation as they stand: read, click and type over CDP call functions on a remote object, which the plugin's channel has no handle for; Windows refs are CDP `backendNodeId`s while a macOS snapshot is to come from the Accessibility API (#14, [Seeing the page on macOS](seeing-the-page-on-macos.md)); console messages arrive as CDP events while the channel only answers requests. **Maintainer's call (2026-10-13, #16):** each macOS ticket widens the seam with its real implementation. Shown were this narrow seam, all seven page commands behind the seam with the plugin side refusing, and deferring #16 until #12 and #13; the full seam's shape would have been guessed from CDP alone.
- **`read` through the plugin finds and reads the element in one evaluation**, with no remote object to hold or release (`State::read_cmd`, the `Page::Plugin` arm). The page tags what it found, so a selector `querySelector` throws on is reported as an invalid selector (`error`, `invalid_selector`) and one that matches nothing as `not_found` (`no_match`), as over CDP, instead of both arriving as the page's `js_error`. Both engines read the same fields with the same function (`READ_ELEMENT`). Pinned by `read_by_selector_returns_the_fields_windows_does`.
- **A ref is refused as unsupported through the plugin, not as a stale ref** (`refs_unsupported`). A stale ref says to take a new snapshot, which macOS cannot do yet (#14). A failed `read` or `wait` leaves no screenshot in the record: `failure_screenshot` reads the current CDP target, which a plugin session has none of ([The run record](the-run-record.md)); macOS capture is #35.
- **`wait` polls through the seam, so `--text` and `--expr` came with `--selector`** (`State::wait_cmd`). Each poll is one plugin eval, 100 ms apart. A broken `--expr` fails at once as `js_error`: it does not compile in place, is retried through `eval` and throws there. Pinned by `wait_holds_until_an_element_appears_and_times_out_on_one_that_never_comes`.

### Readiness

- **Ready means the main webview answered and its document has loaded, nothing more.** `wait_ready` asks the plugin for its webviews every 50 ms, picks the main one (`pick_main`: the one whose URL contains `--main-url`, else the one labelled `main`, else the first), and evaluates `ready_probe`: `location.href !== 'about:blank' && document.readyState === 'complete'`, plus `location.href.includes(<main-url>)` when one was given. The `about:blank` term is there because a fresh fixture reports `about:blank` as complete for a few ms first (see Reference behaviour); no test pins it, as the window is too short to land in on purpose. It does not wait for the page to be visible and paint two frames as the Windows session does ([Launching a test instance](launching-a-test-instance.md)): a test build launched behind a window that covers it is occluded, a WKWebView page then paints no frames at all ([Measuring the page](measuring-the-page.md)), and that wait would never end. Input reaches such a page anyway ([Sending input on macOS](sending-input-on-macos.md)).
- **An app that never opens the channel fails `launch` early.** If the app exits before the port file appears, `wait_port` says so and asks whether it is a test build; otherwise it waits up to the ready timeout. Either way the app is ended and the instance directory removed (`through_plugin::start`, its `fail` closure). Pinned by `launching_a_build_without_the_plugin_fails_and_leaves_nothing`.
- **pokit's own variables win over `--env`.** `spawn_app` sets them after the caller's, so a caller passing `POKIT_TOKEN` cannot leave `launch` waiting on a token it does not hold (`launch_keeps_its_own_token_over_a_callers_env`).

### Ending

- **There is no job object, so the session kills the app itself.** `close`, the idle timeout and the app's exit all end in `State::shutdown`, which removes the session file, kills the app's process (`crates/pokit/src/proc.rs — kill_tree`, `kill -9` off Windows) and removes the instance directory, which the session owns (`owned_data_dir`, set by `through_plugin::session`) as it owns a WebView2 profile it created. When the app has already exited, the watchdog has reaped it and set `app_exited`, so `shutdown` does not kill that pid again: the number may belong to another process by then. If the session process itself dies, the app is left running with its channel open; the stale clearing that would end it works only on Windows ([Starting the session process](starting-the-session-process.md), Known holes).

## Reference behaviour

- **On macOS the opt-out is the builder's `activate_ignoring_other_apps(false)`, and it is enough.** tao passes it to `activateIgnoringOtherApps:` once the app has launched (`tao` 0.37.1, `platform_impl/macos/app_state.rs` 291–293); Tauri's default is `true` (`app.rs` 1685). With the fixture launched while another app was frontmost: default, the fixture came to the front 3 times out of 3; with `false`, the other app stayed in front 3 times out of 3, and the fixture still had a focused window and painted at 60 fps (macOS 26.6.2, Tauri 2.12.1, 2026-10-06, throwaway probe in #10). Starting it without activation as well (`open -g`) is therefore not needed. Not measured: a launch while no app is active, when `false` still activates. The Windows counterpart, the window's `focus: false`, is in [Launching a test instance](launching-a-test-instance.md).
- **wry's macOS `eval`** uses `evaluateJavaScript`, which does not await a promise, ignores the error (its handler drops `_err`), and turns the result into JSON with `NSJSONSerialization ... .unwrap()`, which aborts the app on a value JSON cannot hold (`wry` 0.57.0, `src/wkwebview/mod.rs` 723–756, read 2026-10-06, #11). Settles why the plugin calls `callAsyncJavaScript` itself.
- **WebKit drops a call whose promise nothing can resolve.** `new Promise(() => {})` came back immediately with "Completion handler for function call is no longer reachable" in one run, and ran into the 1 s timeout in another; which one depends on garbage collection (2026-10-06, #11). Settles the `timeout` mapping.
- **A fresh fixture reported `about:blank` with `readyState` `complete` for about 7 ms before its own page**, in 3 starts out of 3 (#11's review, 2026-10-06); the WebView2 launch has the same trap ([Launching a test instance](launching-a-test-instance.md)). Settles the `about:blank` term in `ready_probe`.
- **macOS shows a process's environment to the same user**: `ps eww -p <app>` printed `POKIT_TOKEN` (2026-10-06, #11). Settles what the token does not guard.

## Cross-cutting invariants

**None.**

## Blast radius

- [The app's pages](the-apps-pages.md) — `eval`, `wait`, `read` and clock alignment assume `Page::eval` keeps one contract on both engines: the promise awaited, the value by JSON, a throw as `js_error`, an unsettled promise as `timeout`. A change to the plugin's `eval` or its error mapping changes what those commands report on macOS only.
- [Sending input on macOS](sending-input-on-macos.md) — input rides the same channel, token, webview label and `INPUT_TIMEOUT`, and its focus guard, key notes and delivery check are plugin evals. It also assumes readiness has waited for the main webview: the plugin writes its port before that webview exists.
- [Starting the session process](starting-the-session-process.md) — the plugin session reuses `State::shutdown` and the watchdog, and assumes `shutdown` kills `app_pid` and deletes `owned_data_dir`; a change there that assumes a job object or a WebView2 profile leaves the macOS app or its instance directory behind.
- [Launching a test instance](launching-a-test-instance.md) — both launches put their per-launch directory under `instances/<stamp>-<session pid>`, the name `sweep_profiles` parses; the sweep does not run for a plugin session, so a naming or sweep change there decides whether macOS instance directories are ever cleared.
- [Platform support](platform-support.md) — a command made to work through the plugin is still refused until `support::ON_MACOS` names it, since `State::handle` checks `plugin_answers` first.
- [The run record](the-run-record.md) — the record assumes a failed command can attach a screenshot; `failure_screenshot` is CDP-only, so every macOS failure lacks one until #35.
- [Testing against the fixture app](testing-against-the-fixture.md) — the macOS tests launch `fixture_test_build_exe`, built with the fixture's `pokit` feature; renaming the feature or the variables breaks the build and the binary check in `a_build_without_the_feature_has_no_plugin_and_opens_no_port`.
- [Seeing the page on macOS](seeing-the-page-on-macos.md) — snapshot and capture will widen the seam (#16's call); refs refused today by `refs_unsupported` assume no snapshot exists.

## Known holes / open

- The token lives in the app's environment for its whole life, and the home and `instances/` are created with the default mode, so another local user could plant a port file where the home is shared (reasoned from the code in #11's review, not run end to end). Tracked: #39.
- Ending is `kill -9` of one pid: whatever the app starts outlives the session, an app whose session died keeps its channel open (seen in #11: a fixture with parent pid 1 still listening 13 minutes later), and the next `launch` cannot clear it. Tracked: #40.
- A macOS instance directory left by a session that died is never removed: `sweep_profiles` runs only when `state.plugin` is `None` (read from `crates/pokit/src/session/mod.rs`, not measured).
- Nothing bounds how many connections the channel serves at once, each on its own thread for up to 5 s; nothing bounds the reply line `Plugin::request` reads.
- No test pins the 5 s drop of a silent connection, or the `about:blank` term in `ready_probe`.
- Whether `launch` draws the window above the frontmost app's windows, though it leaves that app frontmost, is not measured. Tracked: #121.
- `attach` is not built on macOS (`through_plugin::start`). The macOS backend as a whole: #6.
