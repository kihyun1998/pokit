# Reaching the page through the plugin

How the macOS session reaches the page: `launch` starts the app's test build, the plugin opens a loopback channel, and `eval` runs through it. Code: `tauri_plugin_pokit` (`channel::open`, `channel::serve`, `eval::evaluate`), `plugin::Plugin`, `session::through_plugin` (`serve`, `spawn_app`, `wait_port`, `wait_ready`), `output::ENGINE`. Measured against the fixture app on macOS 26.6.2 with Tauri 2.12.1, wry 0.57.0, objc2-web-kit 0.3.2 (2026-10-06, #11).

## The plugin's shape

- **Three gates, each on its own.** The app compiles the plugin in only under a feature of its own (`pokit` in the fixture), so a build without it carries no plugin at all; `a_build_without_the_feature_has_no_plugin_and_opens_no_port` checks the binary for the plugin's variable name. A build with it opens nothing unless `POKIT_TOKEN` and `POKIT_PORT_FILE` are both set, which only `launch` does. The channel binds `127.0.0.1` only, and every request must carry the launch's token, compared in constant time; a refused request is not run. A connection that sends no request line within 5 s is dropped: without that, 50 silent connections held 50 threads for as long as they stayed open, token or not (#11's review); with it, the 50 extra threads were gone 7 s later while the connections were still open.
- **What the token guards against, and what it does not.** It keeps other users and other machines out, and any local process that does not know it. It does not keep out a process of the same user that reads the app's environment: `ps eww -p <app>` printed `POKIT_TOKEN` with its value. That is still more than Windows gives: WebView2's debugging port takes no token at all ([[launching-a-test-instance]]).
- **Only the app's feature keeps the plugin out of a shipped build.** Nothing checks the build profile, so an app built for release with `pokit` among its features carries a channel any process of the same user can open by starting the app with the two variables set, and the page world it evaluates in can call the app's Tauri commands. **Maintainer's call (2026-10-06, #11):** keep the feature as the only gate, because #1 defines the test build as optimised like a release, which a `debug_assertions` gate would refuse. The alternatives shown were a second opt-in feature for release profiles, and gating on `debug_assertions`. An app keeps `pokit` out of its default features.
- **The port goes through a file, not a fixed number.** The plugin binds port 0 and writes the port it got to `POKIT_PORT_FILE` in the instance directory, as WebView2 writes `DevToolsActivePort`. It writes a temporary file and renames it, so `wait_port` never reads a half-written number.
- **The test build also leaves the frontmost app alone.** The fixture's feature sets `activate_ignoring_other_apps(false)`; see [[launching-a-test-instance]] for the measurement. `launch_leaves_the_frontmost_app_frontmost` pins it, and returns without checking when no app is frontmost.

## `eval`

- **It goes through `callAsyncJavaScript`, not Tauri's `eval_with_callback`.** wry's macOS `eval` uses `evaluateJavaScript`, which does not await a promise, ignores the error (its handler drops `_err`), and turns the result into JSON with `NSJSONSerialization ... .unwrap()`, which aborts the app on a value JSON cannot hold (`wry` 0.57.0, `src/wkwebview/mod.rs` 723–756). `callAsyncJavaScript:arguments:inFrame:inContentWorld:` awaits, reports the exception, and the plugin hands back `JSON.stringify` text, so nothing native is serialised. That matches the Windows contract (`Runtime.evaluate` with `awaitPromise` and `returnByValue`): a DOM node comes back as `{}`, `undefined` as `null`.
- **The expression is compiled in place first, and through `eval` only when that is a syntax error.** A body `return await (<expression>)` runs whatever the page's CSP says; an `eval()` inside the page does not. Measured on the fixture with `script-src 'self'` added to the page: the page's own `eval` threw `EvalError: Refused to evaluate a string as JavaScript`, an expression (`40 + 2`) still answered 42, and a list of statements, which needs `eval`, failed with that `EvalError` as a `js_error`. A list of statements (`var a = 20; a + 1`) is not an expression, fails to compile with a `SyntaxError` before anything runs, and is retried as `(0, eval)(expression)` for its completion value, within what is left of the timeout. So under a CSP without `'unsafe-eval'`, only expressions work.
- **Only a compile error is retried, so nothing runs twice.** A `SyntaxError` can also be thrown while the code runs (`JSON.parse('{')`). When the retry looked only at the error's text, such an expression ran twice: a counter it bumped read 2 (#11's review). The body now catches whatever the code throws and hands it back as `{"thrown": …}`, so only a failure to compile reaches WebKit's own error, and only that is retried. `eval_runs_in_the_page_and_close_ends_the_app` pins it with a counter.
- **WebKit can answer a never-settling promise at once.** `new Promise(() => {})` came back immediately with "Completion handler for function call is no longer reachable" in one run, and ran into the 1 s timeout in another: WebKit drops the call once nothing can resolve the promise, which depends on garbage collection. The plugin reports that error as `timeout`, the kind Windows gives the same promise; `a_promise_webkit_dropped_is_a_timeout` pins the mapping, since the integration test cannot force the collection.
- **The reply carries an engine of its own.** Every command's output says `"engine": "plugin"` on macOS (`output::ENGINE`).

## Readiness

- **Ready means the main webview answered and its document has loaded, nothing more.** `wait_ready` asks the plugin for its webviews, picks the main one (`--main-url`, else the one labelled `main`, else the first), and evaluates `location.href !== 'about:blank' && document.readyState === 'complete'`, plus `location.href.includes(<main-url>)` when one was given. A fresh fixture reported `about:blank` with `readyState` `complete` for about 7 ms before its own page, in 3 starts out of 3 (#11's review); this is the trap the WebView2 launch has too. No test pins it: the window is too short to land in on purpose. It does not wait for the page to be visible and paint two frames as the Windows session does ([[launching-a-test-instance]]): a test build launched behind a window that covers it is occluded, a WKWebView page then paints no frames at all ([[measuring-the-page]]), and that wait would never end. Input reaches such a page anyway ([[sending-input-on-macos]]).
- **An app that never opens the channel fails `launch` early.** If the app exits before the port file appears, `launch` says so and asks whether it is a test build; otherwise it waits up to the ready timeout. Either way the app is ended and the instance directory removed (`launching_a_build_without_the_plugin_fails_and_leaves_nothing`).
- **pokit's own variables win over `--env`.** They are set after the caller's, so a caller passing `POKIT_TOKEN` cannot leave `launch` waiting on a token it does not hold (`launch_keeps_its_own_token_over_a_callers_env`).

## Ending

- **There is no job object, so the session kills the app itself.** `close`, the idle timeout and the app's exit all end in `PluginSession::shutdown`, which kills the app's process (`kill -9`), removes the instance directory and the session file. When the app has already exited, the session reaped it, so it does not kill that pid again: the number may belong to another process by then. If the session process itself dies, the app is left running; the next `launch` does not yet clear such an orphan, because `process_start_time` and `image_name` are Windows-only.
