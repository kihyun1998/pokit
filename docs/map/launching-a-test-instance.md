# Launching a test instance

## What it is
How `pokit launch` gets a WebView2 app running on Windows with a profile of its own and a debugging port, at medium integrity where WebView2 needs that, when it counts the main page as ready, how it keeps the user's foreground where it was while the app starts, and how the profiles it creates are removed. How the session process that does this is started and ended is [Starting the session process](starting-the-session-process.md).

## Governing decisions
**None.** [ADR-0001](../adr/0001-commands-talk-to-a-session.md) decides that a session holds the instance, not how the instance is started; [ADR-0002](../adr/0002-hand-written-cdp-client.md) decides how pokit speaks CDP once the port is open. The rules here are maintainer's calls on issues (#3, #9, #116, #48, and 2026-10-06 on the give-back), carried in Design model.

## Design model
The rules come from maintainer's calls on #3, #9, #48 and #116 and one on 2026-10-06, and otherwise from the source and the measurements cited beside them.

Input from outside: the app's stdout and stderr, read line by line into the session log with no bound on a line's length ([Collecting logs](collecting-logs.md)); the first line of `DevToolsActivePort`, parsed as a port number (`launch::active_port`); and the caller's arguments and `--env` pairs, passed to the app as given.

**Isolation: what pokit can and cannot separate**

- **The WebView2 profile and the debugging port, yes.** `launch::spawn_app` sets `WEBVIEW2_USER_DATA_FOLDER` to the profile and `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` to `--remote-debugging-port=<port>`; the first replaces and the second is appended to what the app passes (Reference behaviour).
- **A debugging port on a profile that is already in use, no** (Reference behaviour). A test instance therefore always gets a fresh folder: without `--data-dir`, `instances/<stamp>-<session pid>` under the pokit home (`launch::spawn_app`, `home::stamp`).
- **The app's own data, no** (Reference behaviour: Tauri resolves it through `SHGetKnownFolderPath`). **Maintainer's call (2026-10-01, #3):** pokit isolates only the WebView2 profile and the port; the caller isolates app data through `launch --env` or app arguments. The alternative shown was pokit redirecting `USERPROFILE`, which does move them on a default machine but is undocumented, breaks under folder-redirection policy, and moves `~/.ssh` too.
- **A profile pokit created is removed in two steps.** `close` makes one attempt and returns (`State::try_remove_owned_data_dir_after`, from `State::shutdown`); unloaded, the instance's six WebView2 processes are gone 0.4 s after `close` (measured 2026-10-01), so that attempt usually comes too early. Whatever WebView2 still holds is removed by the next session that reaches the page over CDP, `launch` or `attach`, which sweeps `instances/` in the background, retrying every 500 ms for up to 30 s (`launch::sweep_profiles`, started from `serve`). Profiles are named `<stamp>-<session pid>` (`launch::profile_session_pid` reads them back); the sweep skips its own and those whose pid is a running process with pokit's image name. A `--data-dir` the caller supplied is never touched (`owned_data_dir` is set only without it, `start_over_cdp`). Pinned by `launch_removes_profiles_left_by_ended_sessions_and_keeps_its_own` (tests/fixture.rs). **Maintainer's call (2026-10-01, #9):** the alternative shown was keeping `close` retrying until the profile was gone. Under 25 parallel instances that retrying took 5–10 s per `close` (measured from the run records), and the last profile now stays on disk (~8 MB) until the next session starts.

**The debugging port**

- **By default the browser picks the port.** `--port` defaults to none, and `session::Config::cdp_port` 0 becomes `--remote-debugging-port=0`. WebView2 writes the port it bound to the first line of `<profile>/EBWebView/DevToolsActivePort` (probe, 2026-10-01), which `launch::active_port` reads every 100 ms until `--ready-timeout`, failing early if the app exits. `launch::spawn_app` deletes that file before starting the app, so a reused `--data-dir` cannot hand over a previous run's port. Picking a free port in pokit and handing its number over leaves a gap in which another process can take it. 14 parallel launches got 14 distinct ports and browsers.
- **The port has no authentication.** Any local process can drive the instance while it runs. This comes with WebView2 remote debugging; a pipe instead of a port is not available, because the WebView2 loader, not pokit, starts the browser process. Which page sockets the session itself follows on that port is [The app's pages](the-apps-pages.md).
- **An elevated app gets no port from WebView2 150 on, so an elevated `launch` starts the session, and with it the app, at medium integrity** (Reference behaviour for the runtime's side). `proc::launch_needs_medium` decides it: pokit is elevated and the runtime's major version is 150 or later, or cannot be read. `proc::webview2_runtime` reads the Evergreen runtime's `pv` from the EdgeUpdate client key under HKLM (`WOW6432Node`) and HKCU and takes the newer (`proc::runtime_major`). Only `launch` is lowered, not `attach` (`main::start_session`). Below 150 an elevated launch keeps working elevated, as Windows CI does on runtime 131. How the session is started at medium integrity is in [Starting the session process](starting-the-session-process.md); the explicit-stdio and inherit-nothing rules there, and the chain the foreground right comes down (below), stay as they were. `launch` then answers `integrity: "medium"`, and when the session fails, its message says the app was lowered and why (`main::start_session`). An app that needs elevation by its manifest cannot start from it (`ERROR_ELEVATION_REQUIRED`); elevated it would have no port either (#116). Pinned by `launch_needs_medium_only_when_elevated_on_runtime_150_or_later_or_an_unknown_one` (proc.rs) and `an_elevated_launch_opens_the_port_starting_the_app_at_medium_integrity_where_webview2_needs_it` (tests/fixture.rs), which skips unless the test run is elevated. **Maintainer's call (2026-10-26, #116):** lower to medium where WebView2 needs it, and say why where that fails. Shown with it: an HKLM `AdditionalBrowserArguments` policy keyed by the exe name (machine-wide, persistent, the user's own runs expose the port; unmeasured), failing with the reason alone, moving only CI to medium through `gsudo`, and routes through a test build.

**Readiness at launch**

When a page counts as ready, and the check before the first input to a page whose document has changed, are [The app's pages](the-apps-pages.md)'s. At launch, `launch::wait_ready` reads the page list every 200 ms until a page matches `--main-url` (a substring of its URL; the first page without it), syncs the targets, makes that page the main and current one, and polls `launch::probe_ready` (`READY_PROBE`, every 100 ms) until `--ready-timeout` (30 s for `launch`, 10 s for `attach`). If the app exits meanwhile, the launch fails with the last lines of its output (`State::backend_tail`). The main page's `performance.timeOrigin` at that moment is kept and reported as `main.time_origin` (`main_origin`, `State::cdp_status`). Three traps sit behind it:

- **The page target starts on `about:blank`.** About 100 ms later it navigates to the app's URL *under the same target id* (seen in 3 out of 3 launches). `about:blank` reports `readyState === "complete"`, so a check on load state alone declares the wrong document ready. `READY_PROBE` reads URL and state in one evaluation so they describe the same document, and `launch::probe_ready` refuses `about:blank` and a URL without `--main-url` in it.
- **Once the main page is ready, the page list is read again and the targets synced** (`launch::wait_ready`, #27). The targets were synced when the page was first listed, still on `about:blank`, and `launch` answers from them: its `main` said `"url": "about:blank"` and an empty title in 4 launches of 4 (2026-10-12), while `targets` straight after showed the real page. The `discover` loop would only have caught up after `launch` answered. A failed read leaves the old entry and does not fail the launch. `launch_lists_the_main_page_and_close_removes_the_instance` (tests/fixture.rs) checks `main`'s URL and title; it failed on `about:blank` without the second read.
- **Input sent before the first frames is dropped, and CDP still reports success.** Under load (14 parallel launches), the first `type` after `launch` sometimes delivered no `keydown` at all. The fixture's event log showed `focusin` and then nothing. `performance.timeOrigin` was unchanged, so this was not a reload after ready (ruled out). Waiting for `visibilityState === "visible"` and two `requestAnimationFrame` callbacks before reporting ready (`READY_PROBE`, which gives up on painting after 1 s and is asked again) took the suite from failing about one run in four to 15 clean runs in a row. Reverting the wait made it fail on the first run. The Chromium mechanism (input dropped while the first paint is held) is inferred, not read from source. Ruled out while finding it: another window taking OS focus mid-typing (Reference behaviour).

**Keeping the foreground during launch**

- **The right to take the foreground is inherited** (Reference behaviour). When the user is looking at the terminal that runs the agent, pokit, its session and the app all descend from the foreground process, so a Tauri app that takes the foreground at start gets it.
- **Starting the app with `SW_SHOWNOACTIVATE` does not help, and pokit does not do it** (Reference behaviour). `launch::spawn_app` passes only `CREATE_NO_WINDOW`.
- **The fixture opts out, as a test build should.** Its window sets `focus: false` (`fixtures/app/tauri.conf.json`), which turns off both ways a Tauri app takes it (Reference behaviour). `launch` then left the terminal in front 3 times out of 3 (2026-10-06). This is the Windows counterpart of the macOS test build's `activate_ignoring_other_apps(false)` (#6), which is in [Reaching the page through the plugin](reaching-the-page-through-the-plugin.md).
- **For an app that does not opt out, the session gives the foreground back.** From the start of the launch until `LAUNCH_FOCUS_GRACE` (500 ms) after the page is ready, every 50 ms the session checks whether the app owns the foreground window (`launch::keep_foreground`, `start_over_cdp`). When it does, the session puts back the window that was in front before the launch (`proc::set_foreground`); it does nothing when nothing was in front or the app already was. The session still holds the inherited right, so this worked 3 times out of 3. Each give-back is noted in the session log (`gave` or `could not give … back to pid <n>`); a refusal right after a refusal is counted but not noted again. `launch` reports the count as `foreground_given_back`, and the refusals as `foreground_give_back_refused` (`State::cdp_status`). **It is best effort.** Windows withdraws the inherited right once the user gives input, and then refuses: in 1 run of 5 every attempt (14 of them) was refused and the app kept the foreground (2026-10-06). The test then reports the refusal instead of failing, but still requires that the session noticed and tried. **Maintainer's call (2026-10-06):** best effort now; a stronger way back in (`AttachThreadInput`, or a synthetic Alt key as tao uses) is measured with #5's activation command instead ([Sending OS input](sending-os-input.md)). Sampled every 20 ms over 10 launches of the fixture with `--take-focus` (2026-10-12, #28): where the give-back worked (5), the app was in front for at most 3 samples, about 60 ms; where it held the foreground longer (5), every attempt had been refused (11–12 each, `could not give` in the session log) and it kept it. The first refusal followed possible input by the user; the four after it started from a window that was not an ancestor of the test, which the previous run's app had left in front when it closed. No run held the foreground long and then had it given back. An earlier run sampled every 100 ms held it about 1.4 s and then lost it (2026-10-06); its log was not kept, and a refusal followed by a later attempt that worked would explain it. What this leaves: the app is in front for up to 50 ms, and keys typed in that moment reach it. A user who clicks the app during the launch also has the foreground taken back once. **Maintainer's call (2026-10-06):** the alternatives shown were the app-side setting alone, and also keeping the `SW_SHOWNOACTIVATE` start, for which nothing was measured that it helps.
- **The focus tests observe whether the app took the foreground; they do not predict it.** Whether it may at a given moment depends on more than who started whom (Reference behaviour). An ancestor check (`can_take_foreground`) was wrong both ways and is gone. Each test checks `after == before` unconditionally and prints whether the app took the foreground (`the app took the foreground at …`); where Windows kept the app back, the run tests nothing about the give-back and passes. **Maintainer's call (2026-10-08, #48):** observe and report. Shown with it: a helper that tries `SetForegroundWindow` first (not measured; it takes the user's foreground, and is still a check made before the action); granting the app `AllowSetForegroundWindow` before the action (the grant failed with access denied exactly in the 2 of 5 runs where the app could not take it, and never made it take it more often); and failing a run in which the app did not take it (red 1 in 5 to 3 in 3 on this machine, for no fault of pokit's). So #48's "says can-take exactly when a launched process could" cannot be met by any check made before the action.
- **`launch_leaves_the_foreground_where_it_was`** (tests/window.rs) launches the opted-out fixture, then the fixture with `--take-focus`, which calls `set_focus` from its own setup (`fixtures/app/src/main.rs`), and checks after each that the foreground is where it was. The two run in one test, in order, because a fixture taking the foreground fails any check running beside it (seen when they were two tests: both failed on the same pid). Reddened 2026-10-08: a give-back that reports success without calling `SetForegroundWindow`, and no give-back at all, each turned it red 2 times out of 2.

## Reference behaviour
- **WebView2's environment variables** (`WebView2.idl` lines 8873–8886 in SDK 1.0.4258.31, and a probe on runtime 154.0.4258.37, 2026-10-01): `WEBVIEW2_USER_DATA_FOLDER` *replaces* the folder the app passes to `CreateCoreWebView2EnvironmentWithOptions`; `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` is *appended* to the arguments the app passes. Tauri passes both explicitly (`app_local_data_dir`, and wry's `--disable-features=msWebOOUI,…`), and neither blocks the variables.
- **A second controller on a profile already in use** fails with `0x8007139F` (`ERROR_INVALID_STATE`), and the port never opens (2026-10-01).
- **Tauri's app data folders** resolve through `SHGetKnownFolderPath`, so `APPDATA` and `LOCALAPPDATA` have no effect; redirecting `USERPROFILE` moves them on a default machine (#3, 2026-10-01).
- **WebView2 150's hardening for elevated hosts:** `WEBVIEW2_*` variables and HKCU overrides are ignored, while HKLM policy and the app's own `CoreWebView2EnvironmentOptions.AdditionalBrowserArguments` are honored (`webview2/concepts/security.md`, "For an elevated host app, use appropriate override flags", read 2026-10-26; WebView2Feedback #5640 and #5645 put the boundary at 149 to 150). Measured 2026-10-26 (#116) on runtime 156.0.4314.42: elevated, the browser's command line lacked `--remote-debugging-port` and no port opened, on a desktop (Windows 11 26200, through UAC) and on both runner images; unelevated on the same desktop it opened. WebView2 goes by the integrity level, not the elevation flag: an app at medium integrity whose token still had the full admin elevation type opened the port. `WEBVIEW2_USER_DATA_FOLDER` stayed honored when elevated, against the documentation (here and in #5640), and the profile isolation above rests on it.
- **On GitHub's runners a medium-integrity app answers nothing on its port:** started at medium there (no split token, elevation type default), the app wrote `DevToolsActivePort` but nothing answered on it, on `windows-2022` and `windows-2025` alike (#116, run 40269554015).
- **The right to take the foreground is inherited:** Windows lets a process set the foreground window if it was started by the foreground process (`SetForegroundWindow` remarks, sdk-api docs, read 2026-10-06), and that passes down a chain of starts. Measured 2026-10-06 on the fixture with Tauri's default `focus: true`: run from this repo's terminal while it was in front, `launch` made the fixture the foreground window 3 times out of 3; with the screen locked, 0 out of 3.
- **Two things in a Tauri app take it.** tao shows the window with `SW_SHOW` unless the window's `focus` is false (`tao` 0.37.1, `platform_impl/windows/window_state.rs` 457–466). wry then calls the controller's `MoveFocus` when the webview is focused, which is also the default (`wry` 0.57.0, `src/webview2/mod.rs` 612–615).
- **`SW_SHOWNOACTIVATE` at start does not stop it.** The first `ShowWindow` an app makes uses the starter's show state (`ShowWindow` remarks), but `MoveFocus` activates the window anyway: with the app started that way through `CreateProcessW`, `launch` still took the foreground 3 times out of 3 (2026-10-06).
- **Whether a process may take the foreground** also weighs the last input, open menus and the foreground lock, and Windows may deny the right even when they are met (sdk-api remarks, read 2026-10-08). Measured: with an ancestor of the test in front, the fixture's dialog took the foreground 0 times out of 3; with another Orca process in front, which started nothing here, 4 out of 5 (2026-10-08); in one session, 2 context menus out of 6 (2026-10-07).
- **The foreground lock keeps a background-launched window from taking focus at all:** ruled out as the cause of input dropped after launch; `document.hasFocus()` stayed true.

## Cross-cutting invariants

- [A pid may be reused](a-pid-may-be-reused.md) — `launch::sweep_profiles` removes a profile only when its session pid is not a running pokit process.

Not a site of [Capabilities match behaviour](capabilities-match-behaviour.md): the launch give-back is reported in `launch`'s answer, not declared in `capabilities` (`main::capabilities` gives `launch` only `supported` and `route`).

## Blast radius
- [Starting the session process](starting-the-session-process.md) — the app is ended through the job object the session assigns it to right after `launch::spawn_app`; an app started some other way, or by a launcher that exits, escapes the job and outlives the session.
- [The app's pages](the-apps-pages.md) — `launch` answers from the targets as synced at launch, and marks the main page ready; a change to what counts as ready, or to when targets are synced, changes what `launch` reports and whether the first input is dropped.
- [Collecting logs](collecting-logs.md) — the app's stdout and stderr are the backend log and the tail a failed launch prints; starting the app without piping them empties both.
- [Measuring the page](measuring-the-page.md) — the page clock is aligned, once the start returns, on the page `launch::wait_ready` made current, and `main.time_origin` is taken from the probe that passed; a readiness check that let `about:blank` through would align and record a document about to be replaced.
- [Sending OS input](sending-os-input.md) — the give-back here and `window activate` both depend on Windows letting pokit's processes set the foreground; a change to who starts whom changes both.
- [Testing against the fixture app](testing-against-the-fixture.md) — the fixture's `focus: false` and `--take-focus` are what the focus test launches; changing either changes what the test can observe.

## Known holes / open
- Why a medium-integrity app answers nothing on its port on GitHub's runners is unknown, so CI cannot measure `launch` on WebView2 150 or later. Tracked: #125.
- The Chromium mechanism behind input dropped before the first frames is inferred, not read from source.
- An app that keeps the foreground after Windows refuses every give-back stays in front; nothing stronger is tried during launch (see the maintainer's call above).
- Nothing bounds the length of a line of the app's output the session reads.
