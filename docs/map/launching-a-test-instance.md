# Launching a test instance

How `pokit launch` gets a WebView2 app running with its own profile and a debugging port, and when it counts a page as ready. Code: `session::launch::spawn_app`, `session::launch::sweep_profiles`, `session::launch::active_port`, `session::launch::wait_ready`, `State::ensure_ready` (session/pages.rs), `launch::READY_PROBE`, `devtools::get_json`.

## Isolation: what pokit can and cannot separate

- **The WebView2 profile and the debugging port, yes.** `WEBVIEW2_USER_DATA_FOLDER` *replaces* the folder the app passes to `CreateCoreWebView2EnvironmentWithOptions`. `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` is *appended* to the arguments the app passes. Tauri passes both explicitly (`app_local_data_dir`, and wry's `--disable-features=msWebOOUI,…`), and neither blocks the variables. Source: `WebView2.idl` lines 8873–8886 in SDK 1.0.4258.31, and a probe on runtime 154.0.4258.37 (2026-10-01).
- **A debugging port on a profile that is already in use, no.** Creating the second controller fails with `0x8007139F` (`ERROR_INVALID_STATE`), and the port never opens. A test instance therefore always gets a fresh folder.
- **The app's own data, no.** Tauri resolves `app_data_dir` and the related folders through `SHGetKnownFolderPath`, so `APPDATA` and `LOCALAPPDATA` have no effect. Redirecting `USERPROFILE` does move them on a default machine, but that behaviour is undocumented, breaks under folder-redirection policy, and moves `~/.ssh` too. **Maintainer's call (2026-10-01, #3):** pokit isolates only the WebView2 profile and the port; the caller isolates app data through `launch --env` or app arguments. The alternative shown was pokit redirecting `USERPROFILE`.
- **A profile pokit created is removed in two steps.** `close` makes one attempt and returns; unloaded, the instance's six WebView2 processes are gone 0.4 s after `close` (measured 2026-10-01), so that attempt usually comes too early. Whatever WebView2 still holds is removed by the next `launch`, which sweeps `instances/` in the background for up to 30 s. Profiles are named `<stamp>-<session pid>`; the sweep skips its own and those of any running pokit process. A `--data-dir` the caller supplied is never touched. **Maintainer's call (2026-10-01, #9):** the alternative shown was keeping `close` retrying until the profile was gone. Under 25 parallel instances that retrying took 5–10 s per `close` (measured from the run records), and the last profile now stays on disk (~8 MB) until the next `launch`.

## The debugging port

- **By default the browser picks the port.** pokit passes `--remote-debugging-port=0`, and WebView2 writes the port it bound to the first line of `<profile>/EBWebView/DevToolsActivePort` (probe, 2026-10-01). Picking a free port in pokit and handing its number over leaves a gap in which another process can take it.
- `/json/version` on WebView2 returns a browser-level `webSocketDebuggerUrl`. `Target.getTargets`, `Browser.getVersion` and `Target.attachToTarget` with `flatten` all work there (probe, 2026-10-01). pokit still connects to each page's own WebSocket from `/json/list`, and follows only sockets on the instance's own port.
- The DevTools HTTP server can keep the connection open after answering, even when asked to close it. A reader that waits for end-of-stream hangs until its timeout. The body has to be cut at `Content-Length`.
- **An elevated app gets no port from WebView2 150 on, so an elevated `launch` starts the session, and with it the app, at medium integrity** (`proc::launch_needs_medium`, `proc::spawn_detached`, `main::start_session`). Runtime 150 added security hardening for elevated (High-integrity) hosts: `WEBVIEW2_*` variables and HKCU overrides are ignored, while HKLM policy and the app's own `CoreWebView2EnvironmentOptions.AdditionalBrowserArguments` are honored (`webview2/concepts/security.md`, "For an elevated host app, use appropriate override flags", read 2026-10-26; WebView2Feedback #5640 and #5645 put the boundary at 149 to 150). Measured 2026-10-26 (#116) on runtime 156.0.4314.42: elevated, the browser's command line lacked `--remote-debugging-port` and no port opened, on a desktop (Windows 11 26200, through UAC) and on both runner images; unelevated on the same desktop it opened. WebView2 goes by the integrity level, not the elevation flag: an app at medium integrity whose token still had the full admin elevation type opened the port. `WEBVIEW2_USER_DATA_FOLDER` stayed honored when elevated, against the documentation (here and in #5640), and the profile isolation above rests on it. The session runs on a duplicate of pokit's own token lowered to `S-1-16-8192`, so the chain the foreground right comes down (below) and the explicit-stdio and inherit-nothing rules ([[starting-the-session-process]]) stay as they were. It applies only to `launch` on a runtime of 150 or later, or one whose version cannot be read; below 150 an elevated launch keeps working elevated, as Windows CI does on runtime 131. `launch` then answers `integrity: "medium"`, and when the session fails, its message says the app was lowered and why. An app that needs elevation by its manifest cannot start from it (`ERROR_ELEVATION_REQUIRED`); elevated it would have no port either. **Maintainer's call (2026-10-26, #116):** lower to medium where WebView2 needs it, and say why where that fails. Shown with it: an HKLM `AdditionalBrowserArguments` policy keyed by the exe name (machine-wide, persistent, the user's own runs expose the port; unmeasured), failing with the reason alone, moving only CI to medium through `gsudo`, and routes through a test build. **Not working on GitHub's runners:** started at medium there (no split token, elevation type default), the app wrote `DevToolsActivePort` but nothing answered on it, on `windows-2022` and `windows-2025` alike (#116, run 40269554015); why is unknown.
- **The port has no authentication.** Any local process can drive the instance while it runs. This comes with WebView2 remote debugging; a pipe instead of a port is not available, because the WebView2 loader, not pokit, starts the browser process.

## Focus

- **The right to take the foreground is inherited.** Windows lets a process set the foreground window if it was started by the foreground process (`SetForegroundWindow` remarks, sdk-api docs, read 2026-10-06), and that passes down a chain of starts. When the user is looking at the terminal that runs the agent, pokit, its session and the app all descend from the foreground process. Measured 2026-10-06 on the fixture with Tauri's default `focus: true`: run from this repo's terminal while it was in front, `launch` made the fixture the foreground window 3 times out of 3; with the screen locked, 0 out of 3.
- **Two things in a Tauri app take it.** tao shows the window with `SW_SHOW` unless the window's `focus` is false (`tao` 0.37.1, `platform_impl/windows/window_state.rs` 457–466). wry then calls the controller's `MoveFocus` when the webview is focused, which is also the default (`wry` 0.57.0, `src/webview2/mod.rs` 612–615).
- **Starting the app with `SW_SHOWNOACTIVATE` does not help, and pokit does not do it.** The first `ShowWindow` an app makes uses the starter's show state (`ShowWindow` remarks), but `MoveFocus` activates the window anyway: with the app started that way through `CreateProcessW`, `launch` still took the foreground 3 times out of 3 (2026-10-06).
- **The fixture opts out, as a test build should.** Its window sets `focus: false`, which turns off both. `launch` then left the terminal in front 3 times out of 3. This is the Windows counterpart of the macOS test build's `activate_ignoring_other_apps(false)` (#6).
- **On macOS the opt-out is the builder's `activate_ignoring_other_apps(false)`, and it is enough.** tao passes it to `activateIgnoringOtherApps:` once the app has launched (`tao` 0.37.1, `platform_impl/macos/app_state.rs` 291–293); Tauri's default is `true` (`app.rs` 1685). With the fixture launched while another app was frontmost: default, the fixture came to the front 3 times out of 3; with `false`, the other app stayed in front 3 times out of 3, and the fixture still had a focused window and painted at 60 fps (macOS 26.6.2, Tauri 2.12.1, 2026-10-06, throwaway probe in #10). Starting it without activation as well (`open -g`) is therefore not needed. Not measured: a launch while no app is active, when `false` still activates. How the macOS session then finds the page is in [[reaching-the-page-through-the-plugin]].
- **For an app that does not opt out, the session gives the foreground back.** From the start of the launch until 500 ms after the page is ready (`LAUNCH_FOCUS_GRACE`), every 50 ms the session checks whether the app owns the foreground window. When it does, the session puts back the window that was in front before the launch; the session still holds the inherited right, so this worked 3 times out of 3. `launch` reports the count as `foreground_given_back`, and the refusals as `foreground_give_back_refused`. **It is best effort.** Windows withdraws the inherited right once the user gives input, and then refuses: in 1 run of 5 every attempt (14 of them) was refused and the app kept the foreground (2026-10-06). The test then reports the refusal instead of failing, but still requires that the session noticed and tried. **Maintainer's call (2026-10-06):** best effort now; a stronger way back in (`AttachThreadInput`, or a synthetic Alt key as tao uses) is measured with #5's activation command instead. Sampled every 20 ms over 10 launches of the fixture with `--take-focus` (2026-10-12, #28): where the give-back worked (5), the app was in front for at most 3 samples, about 60 ms; where it held the foreground longer (5), every attempt had been refused (11–12 each, `could not give` in the session log) and it kept it. The first refusal followed possible input by the user; the four after it started from a window that was not an ancestor of the test, which the previous run's app had left in front when it closed. No run held the foreground long and then had it given back. An earlier run sampled every 100 ms held it about 1.4 s and then lost it (2026-10-06); its log was not kept, and a refusal followed by a later attempt that worked would explain it. What this leaves: the app is in front for up to 50 ms, and keys typed in that moment reach it. A user who clicks the app during the launch also has the foreground taken back once. **Maintainer's call (2026-10-06):** the alternatives shown were the app-side setting alone, and also keeping the `SW_SHOWNOACTIVATE` start, for which nothing was measured that it helps.
- **The focus tests observe whether the app took the foreground; they do not predict it.** Whether it may at a given moment depends on more than who started whom: `SetForegroundWindow` also weighs the last input, open menus and the foreground lock, and Windows may deny the right even when they are met (sdk-api remarks, read 2026-10-08). Measured: with an ancestor of the test in front, the fixture's dialog took the foreground 0 times out of 3; with another Orca process in front, which started nothing here, 4 out of 5 (2026-10-08); in one session, 2 context menus out of 6 (2026-10-07). An ancestor check (`can_take_foreground`) was wrong both ways and is gone. Each test checks `after == before` unconditionally and prints whether the app took the foreground (`the app took the foreground at …`); where Windows kept the app back, the run tests nothing about the give-back and passes. **Maintainer's call (2026-10-08, #48):** observe and report. Shown with it: a helper that tries `SetForegroundWindow` first (not measured; it takes the user's foreground, and is still a check made before the action); granting the app `AllowSetForegroundWindow` before the action (the grant failed with access denied exactly in the 2 of 5 runs where the app could not take it, and never made it take it more often); and failing a run in which the app did not take it (red 1 in 5 to 3 in 3 on this machine, for no fault of pokit's). So #48's "says can-take exactly when a launched process could" cannot be met by any check made before the action.
- **`launch_leaves_the_foreground_where_it_was`** launches the opted-out fixture, then the fixture with `--take-focus`, which calls `set_focus` from its own setup, and checks after each that the foreground is where it was. The two run in one test, in order, because a fixture taking the foreground fails any check running beside it (seen when they were two tests: both failed on the same pid). Reddened 2026-10-08: a give-back that reports success without calling `SetForegroundWindow`, and no give-back at all, each turned it red 2 times out of 2.

## Readiness

A page is ready when its real document has loaded, is visible, and has painted two frames. It is checked for the main page at launch, and again before the first input to any page whose document has changed since. A new default execution context for the page's main frame (`Runtime.executionContextCreated`) marks the page not ready. Two traps sit behind that definition:

- **The page target starts on `about:blank`.** About 100 ms later it navigates to the app's URL *under the same target id* (seen in 3 out of 3 launches). `about:blank` reports `readyState === "complete"`, so a check on load state alone declares the wrong document ready. URL and state are read in one evaluation so they describe the same document.
- **Once the main page is ready, the page list is read again and the targets synced** (`wait_ready`, #27). The targets were synced when the page was first listed, still on `about:blank`, and `launch` answers from them: its `main` said `"url": "about:blank"` and an empty title in 4 launches of 4 (2026-10-12), while `targets` straight after showed the real page. The `discover` loop would only have caught up after `launch` answered. A failed read leaves the old entry and does not fail the launch. `launch_lists_the_main_page_and_close_removes_the_instance` checks `main`'s URL and title; it failed on `about:blank` without the second read.
- **Input sent before the first frames is dropped, and CDP still reports success.** Under load (14 parallel launches), the first `type` after `launch` sometimes delivered no `keydown` at all. The fixture's event log showed `focusin` and then nothing. `performance.timeOrigin` was unchanged, so this was not a reload. Waiting for `visibilityState === "visible"` and two `requestAnimationFrame` callbacks before reporting ready took the suite from failing about one run in four to 15 clean runs in a row. Reverting the wait made it fail on the first run. The Chromium mechanism (input dropped while the first paint is held) is inferred, not read from source.

## Ruled out

Tested while finding the above, and they did not hold:

- Another window taking OS focus mid-typing. Windows' foreground lock keeps a background-launched window from taking focus at all; `document.hasFocus()` stayed true.
- A page reload after ready. `timeOrigin` was unchanged at the point of failure.
- Two instances sharing a debugging port. 14 parallel launches got 14 distinct ports and browsers.
