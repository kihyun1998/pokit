# Starting the session process

## What it is
How `launch` and `attach` start the background session, how every later command finds that session and proves it is talking to it, and how the session ends: on `close`, when it has been idle too long, when the app it launched exits, or when a later `launch` finds it dead. The session itself is [ADR-0001](../adr/0001-commands-talk-to-a-session.md)'s. How the Windows session gets the app running and ready is [Launching a test instance](launching-a-test-instance.md); how the macOS session reaches the app's test build is [Reaching the page through the plugin](reaching-the-page-through-the-plugin.md).

## Governing decisions
- [ADR-0001](../adr/0001-commands-talk-to-a-session.md): commands talk to a background session, not to the app, and pokit takes on owning that process's lifecycle and cleaning it up when an agent stops midway. Everything below is that lifecycle.

## Design model
That there is a session comes from ADR-0001; one rule (when the idle clock starts) is a maintainer's call on #4; the rest comes from the source and from the measurements cited beside each rule.

Input from outside: the session reads one request line per connection, at most `MAX_REQUEST` (4 MiB, `session/mod.rs`) through `take`. Nothing bounds how many connections it accepts: each gets its own task (`serve`). The command line reads the session's answer line with no size bound (`client::request`). See Known holes.

**Starting**

- **The command line starts the session as a second pokit process and waits for its session file.** `main::start_session` refuses where `support::answers` says the platform does not answer `launch` or `attach` ([Platform support](platform-support.md)), clears a stale session (below), and starts `pokit __session <config>` (the hidden `Command::Session`), the `session::Config` written as JSON in URL-safe base64 (`main::base64_encode`). It then reads the session file every 100 ms, for the session's pid, until it says `Ready` or `Failed`, for up to `--ready-timeout` plus `--timeout`. `Ready`: it asks the session `Request::Status` and prints that as the result. `Failed`: it removes the session file and fails with the session's own error. Deadline passed: it kills the session (`proc::kill_tree`) and fails with `timeout`.
- **A launch's `--env` values ride on the session's command line**, inside that config. `Command::Launch` documents `--env` as not masked and not for secrets.
- **The session inherits no handles at all.** A child started through `std::process::Command` inherits every handle the parent can pass on. That includes handles the CLI itself inherited from whoever ran it, such as a test harness's or an agent shell's stdout pipe. The session, and then the app it starts, kept that pipe open, so the caller waited for end-of-output until the session died. It was seen as `launch` returning only after the 600 s idle timeout (the default of `--idle-timeout`, `Command::Launch`). Marking only the CLI's own std handles non-inheritable was not enough: a handle cargo had passed down still reached the app, and `grep` downstream hung. `CreateProcessW` with `bInheritHandles = FALSE` is what fixed it: `proc::spawn_detached` passes `inherit_handles` 0, with `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP`, first with `CREATE_BREAKAWAY_FROM_JOB` and, where the caller's job refuses breakaway, again without it. Off Windows it is `std::process::Command` with stdin, stdout and stderr null.
- **An elevated `launch` starts the session at medium integrity where WebView2 needs it.** `proc::medium_token` duplicates pokit's own token (`DuplicateTokenEx`, primary) and sets its `TokenIntegrityLevel` to `MEDIUM_SID` (`S-1-16-8192`); `proc::spawn_detached` then starts the session with `CreateProcessAsUserW` on it. `proc::elevated` is an integrity level of `0x3000` or above (`proc::integrity_level`). When this applies and why is in [Launching a test instance](launching-a-test-instance.md). Everything else in this section holds for both: the same flags, no inherited handles, the same parent. A failure to start that way fails `launch` saying the session could not start at medium integrity, why it had to, and that `launch` then needs pokit run unelevated (`main::start_session`).
- **The session has no standard handles, so every child it starts gets explicit stdio.** `taskkill` started with inherited stdio failed silently, and `close` left the app running. It was caught by `launch_lists_the_main_page_and_close_removes_the_instance` (tests/fixture.rs). `proc::kill_tree` and `proc::image_name` run their tool with stdin null and `output()`; the app is started with stdin null and stdout and stderr piped (`launch::spawn_app`).
- **The session file is how a command finds the session.** `home::session_file` is `session.json` in `home::home`: `POKIT_HOME`, else `%LOCALAPPDATA%\pokit`, else a `pokit` folder in the temp directory. `home::write_session` writes it through a `.json.tmp` file and a rename. It carries the session's pid, `Status` (`Starting`, `Ready`, `Failed`), its error, the loopback port and token, the `Mode`, the app's pid, executable and start time, the debugging port and the `proof` (`home::SessionInfo`). One home holds one session: a `launch` or `attach` while a ready session answers a ping is refused with `session_exists` (`main::clear_stale_session`, `client::alive`).
- **A start that fails says so in the session file.** `fail_start` (session/mod.rs) writes `Failed` with the error and an empty token and proof, and kills the app first when it is given the app's pid.
- **The token, the `proof` and the plugin token are 16 bytes from the OS random source** (`home::token`, through `getrandom` 0.2: `BCryptGenRandom` on Windows, `getentropy` on macOS). The session makes the token and the proof in `serve`; the macOS start makes the plugin token in `through_plugin::start`. They were built from std's `RandomState` until #41: a SipHash key seeded once per process and stepped on each call, so the three were related values from one key while `proof` goes to anyone who sends `hello`. No attack on that was known; the hasher was simply not made for tokens. `getrandom` 0.2 was already in pokit's tree through `tokio-tungstenite`, so the change added no crate (#41). Pinned by `a_token_is_32_lowercase_hex_digits_and_differs_each_call` (home.rs).

**Reaching the session**

- **A command proves the listener is the session before sending anything.** The session file holds a `proof`. A command first sends `hello` and must get that proof back; only then does it send the token and the arguments, which may hold a secret (`client::request`). A session file left behind by a dead session could otherwise send them to whatever process took over its loopback port. Pinned by `a_process_squatting_on_the_session_port_never_receives_the_token_or_a_secret` (tests/fixture.rs): the command fails with exit 5 and the squatter receives neither.
- **The session answers `hello` with its proof, then checks the token on the next line** (`serve`). A first line that is not `hello` is taken as the request itself. A wrong token gets `bad token` (exit 1) and nothing runs. A request that does not parse as a `Request` is answered `unknown command` (`error`) and still recorded. Every request with the right token resets the idle clock (`last_activity`).
- **A command reads and writes through one socket, never a clone of it** (`client::request`). It waits `HELLO_TIMEOUT` (3 s) to connect and for `hello`, then sets the command's own time-out before reading the answer. Until #63 the answer was read through `try_clone()`, and on Windows a clone kept the read time-out it had when it was made (Reference behaviour). So every command the session took longer than 3 s over was reported as `no answer from the session within <its time-out>s` although the session had run it, as `window activate` and `hold --compare` were in #47. Pinned by `an_answer_slower_than_the_hello_timeout_is_still_read` and `an_answer_slower_than_the_command_timeout_is_given_up_on` (client.rs).

**Ending**

- **The launched app runs inside a job object that kills on close.** `proc::Job::kill_on_close` sets `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, and `start_over_cdp` assigns the app to it right after starting it (`proc::Job::assign`). Ending the session terminates the job (`proc::Job::terminate`), which ends the app and every process it started, grandchildren included, at once. If the session itself dies, its job handle closes and the app goes with it, so no orphan is left. Pinned by `a_session_that_dies_takes_the_instance_it_launched_with_it` (tests/fixture.rs). `taskkill /T /F` (`proc::kill_tree`) ends the app at shutdown only where the job could not be set up: under 25 parallel test instances it took 4–8 s to return (measured 2026-10-01), against a 5 s test budget. It is also what ends the app on a failed start (`fail_start`, `State::try_remove_owned_data_dir_after`), an orphan of a stale session (below), and the session itself when the command line's start deadline passes (`main::start_session`).
- **Shutdown runs in this order** (`State::shutdown`): keys `hold --route os` still holds down are released (`os_input::release`, [Sending OS input](sending-os-input.md)); an attached session removes the `measure` probes never stopped; the user's clipboard is given back ([Using the user's clipboard](using-the-clipboard.md)); the session file is removed if it is still this session's (`home::remove_session_if`), so no command reaches a session that is shutting down; a launched app is ended; one attempt is made to remove the profile pokit created ([Launching a test instance](launching-a-test-instance.md)); a `shutdown` line goes into the run record with how the app was ended (`kill`) and whether the profile is still there (`profile_left`); the process exits.
- **Where there is no job and the app has already exited, the session does not kill its pid** (`app_exited`, set by `watchdog`). On macOS the session has reaped it and the number may be another process's by then; on Windows the session still holds the app's process handle, so the number is not reused while it runs, and the skip only saves a `taskkill` on a process that has already ended.
- **`close` is answered before the session ends.** The connection's task writes the answer, flushes it, and only then calls `State::shutdown` (`serve`). The answer's `closed` is true only for a launched session (`State::handle`).
- **Idle time counts from the moment the session is ready.** `last_activity` is reset when the session reports Ready, not when it starts (`serve`). Under a full parallel test run, startup took 4.4–8.3 s, and with the idle clock running from the start, a session launched with `--idle-timeout 2` was ended by the watchdog's first tick 0.7–0.8 s after Ready, before the CLI's first request reached it (2 of 3 runs of `an_idle_session_ends_and_closes_the_instance_it_launched`, 2026-10-06). **Maintainer's call (2026-10-06, #4):** fixed in #4's first change, which had lengthened startup by aligning the page clock; the alternative shown was a separate issue.
- **The watchdog ticks every 500 ms** (`watchdog`): past `--idle-timeout` it notes `idle for <n>s; ending the session` in the session log and shuts down; a launched app that has exited (`try_wait`) is noted and shuts the session down too. It watches only an app the session started: an attached session has no child, so it ends on `close` or the idle timeout, not when the app exits.
- **An attached session removes what it installed before it exits.** The app outlives an attached session, so `close` and the idle timeout both run the same async shutdown, which removes `measure` probes that were never stopped (`REMOVE_WAIT`, 2 s, session/measure.rs) before the process exits. Pinned by `closing_an_attached_session_without_stop_leaves_no_probe` (tests/measure.rs). See [Measuring the page](measuring-the-page.md).
- **A stale session is cleared by the next `launch` or `attach`** (`main::clear_stale_session`). A session file whose session is not ready, or does not answer a ping, is removed. Its orphaned app, which can only exist where the job could not be set up, is closed only if it is provably the same process: the image name must match the recorded executable, *and* the process start time must match the one recorded at launch (`proc::image_name`, `proc::process_start_time`, `SessionInfo::app_started`). A pid can be reused, for example after a reboot, by the user's own copy of the same app, and image name alone would get that copy killed. Pinned by `a_stale_session_file_never_gets_a_process_pokit_did_not_start_killed` (tests/fixture.rs). Off Windows both reads return `None`, so no orphan is ever killed there.

**Attach mode**

- **A plugin session (`state.plugin` set, macOS) spawns neither page discovery (`pages::discover`) nor the profile sweep (`launch::sweep_profiles`)** (`serve`, session/mod.rs); everything else here is shared with it ([Reaching the page through the plugin](reaching-the-page-through-the-plugin.md)).
- **`attach` starts the same session on an instance that is already running with its port open** (`Command::Attach`, `Mode::Attach`). It starts no app, so it has no app pid, no job and no profile of its own; its `--ready-timeout` defaults to 10 s, against `launch`'s 30 s. The instance outlives the session: `close` answers `closed: false` and leaves the app running. Pinned by `closing_an_attached_session_leaves_the_app_running` and `an_attached_session_dropped_without_close_ends_and_leaves_the_app_running` (tests/fixture.rs). macOS does not answer `attach` (`support::answers`; `through_plugin::start` also fails it as not built).

## Reference behaviour
- **Windows socket clones keep their own read time-out** (probe, 2026-10-08, #63): on a socket whose clone was made with a 3 s read time-out, the original then set to 30 s reported 30 s, the clone 3 s, and an answer 4 s or 6 s away failed at 3.0 s with os error 10060.
- **`std::process::Command` on Windows passes inheritable handles down**, including ones the parent itself inherited: a handle cargo had passed to the CLI still reached the app until `CreateProcessW` was called with `bInheritHandles = FALSE` (seen as `launch` returning only after the idle timeout, and a downstream `grep` hanging).
- **`taskkill /T /F` under load:** 4–8 s to return under 25 parallel test instances (measured 2026-10-01).
- **`getrandom` 0.2's sources:** `BCryptGenRandom` on Windows, `getentropy` on macOS (#41).

## Cross-cutting invariants

- [A pid may be reused](a-pid-may-be-reused.md) — `main::clear_stale_session` (image name and start time), `State::shutdown` (`app_exited`).

## Blast radius
- [Launching a test instance](launching-a-test-instance.md) — the right to take the foreground comes down the chain of starts, terminal to CLI to session to app; a change to how the session is started (token, flags, breakaway) changes whether the session can give the foreground back during launch, and whether the app runs at the integrity WebView2 opens the port at.
- [The command-line contract](the-command-line-contract.md) — every failure to reach the session, the command line's own wait running out included, is reported as `no_session`; a change to `client::request`'s errors or time-outs changes what a caller sees there.
- [Masking secrets](masking-secrets.md) — a secret is safe on the wire only because nothing is sent before the proof comes back; a change to the hello exchange decides whether a squatter on the port receives it.
- [The run record](the-run-record.md) — the record folder is named after the session's pid and start, and the last line is written by `State::shutdown`; a session that dies writes none.
- [Measuring the page](measuring-the-page.md) — an attached app keeps whatever the session installed unless shutdown removes it within `REMOVE_WAIT`.
- [Using the user's clipboard](using-the-clipboard.md) — the give-back runs only on a shutdown that gets that far; a session that dies does not give it back.
- [Sending OS input](sending-os-input.md) — keys held down by `hold --route os` are released only by shutdown.
- [Reaching the page through the plugin](reaching-the-page-through-the-plugin.md) — the macOS session uses this listener, hello and token check, watchdog and shutdown, but has no job object, so the "no orphan" rule here does not hold there.
- [Platform support](platform-support.md) — `start_session` refuses by `support::answers`; a command made to answer on a platform must also start there.

## Known holes / open
- On macOS there is no job object: if the session process dies, the launched app is left running, and the next `launch` does not clear it, because `proc::image_name` and `proc::process_start_time` are Windows-only. Tracked: #40.
- A launch whose main page never becomes ready, with a caller's `--data-dir` and no job, does not end the app: `State::try_remove_owned_data_dir_after` returns before killing when pokit owns no profile, and `start_over_cdp` passes no pid to `fail_start` there. From reading the code; no test covers it.
- Nothing bounds how many connections the session serves at once, or the size of the answer line the command line reads.
- A session killed outright writes no `shutdown` line and runs none of the shutdown steps above beyond what the job object does.
