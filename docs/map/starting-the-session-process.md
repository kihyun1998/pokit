# Starting the session process

How `launch` and `attach` start the background session (ADR-0001), how a command finds it, and how it ends. Code: `proc::spawn_detached`, `proc::Job`, `proc::kill_tree`, `proc::process_start_time`, `main::start_session`, `main::clear_stale_session`, `client::request`, `client::HELLO_TIMEOUT`, `State::shutdown` (session/mod.rs).

- **The session inherits no handles at all.** A child started through `std::process::Command` inherits every handle the parent can pass on. That includes handles the CLI itself inherited from whoever ran it, such as a test harness's or an agent shell's stdout pipe. The session, and then the app it starts, kept that pipe open, so the caller waited for end-of-output until the session died. It was seen as `launch` returning only after the 600 s idle timeout. Marking only the CLI's own std handles non-inheritable was not enough: a handle cargo had passed down still reached the app, and `grep` downstream hung. `CreateProcessW` with `bInheritHandles = FALSE` is what fixed it.
- **The session has no standard handles, so every child it starts gets explicit stdio.** `taskkill` started with inherited stdio failed silently, and `close` left the app running. It was caught by `launch_lists_the_main_page_and_close_removes_the_instance`.
- **A command proves the listener is the session before sending anything.** The session file holds a `proof`. A command first sends `hello` and must get that proof back; only then does it send the token and the arguments, which may hold a secret. A session file left behind by a dead session could otherwise send them to whatever process took over its loopback port.
- **A command reads and writes through one socket, never a clone of it** (`client::request`). It waits `HELLO_TIMEOUT` (3 s) for `hello`, then sets the command's own time-out before reading the answer. Until #63 the answer was read through `try_clone()`, and on Windows a clone is a separate socket handle that keeps the read time-out it had when it was made: the time-out set afterwards on the original never reached it (probe, 2026-10-08: the original reported 30 s, the clone 3 s, and an answer 4 s or 6 s away failed at 3.0 s with os error 10060). So every command the session took longer than 3 s over was reported as `no answer from the session within <its time-out>s` although the session had run it, as `window activate` and `hold --compare` were in #47.
- **The token, the `proof` and the plugin token are 16 bytes from the OS random source** (`home::token`, through `getrandom` 0.2: `BCryptGenRandom` on Windows, `getentropy` on macOS). They were built from std's `RandomState` until #41: a SipHash key seeded once per process and stepped on each call, so the three were related values from one key while `proof` goes to anyone who sends `hello`. No attack on that was known; the hasher was simply not made for tokens. `getrandom` 0.2 was already in pokit's tree through `tokio-tungstenite`, so the change added no crate.
- **The launched app runs inside a job object that kills on close.** Ending the session terminates the job, which ends the app and every process it started, grandchildren included, at once. If the session itself dies, its job handle closes and the app goes with it, so no orphan is left. `taskkill /T /F` is used only where the job could not be set up: under 25 parallel test instances it took 4–8 s to return (measured 2026-10-01), against a 5 s test budget. The session file is removed first, so no command reaches a session that is shutting down.
- **Idle time counts from the moment the session is ready.** `last_activity` is reset when the session reports Ready, not when it starts. Under a full parallel test run, startup took 4.4–8.3 s, and with the idle clock running from the start, a session launched with `--idle-timeout 2` was ended by the watchdog's first tick 0.7–0.8 s after Ready, before the CLI's first request reached it (2 of 3 runs of `an_idle_session_ends_and_closes_the_instance_it_launched`, 2026-10-06). **Maintainer's call (2026-10-06, #4):** fixed in #4's first change, which had lengthened startup by aligning the page clock; the alternative shown was a separate issue.
- **An attached session removes what it installed before it exits.** The app outlives an attached session, so `close`, the idle timeout and the app-exit watchdog all run the same async shutdown, which removes `measure` probes that were never stopped (2 s budget) before the process exits. See [[measuring-the-page]].
- **A stale session is cleared by the next `launch`.** Its orphaned app, which can only exist where the job could not be set up, is closed only if it is provably the same process: the image name must match the recorded executable, *and* the process start time must match the one recorded at launch. A pid can be reused, for example after a reboot, by the user's own copy of the same app, and image name alone would get that copy killed.
