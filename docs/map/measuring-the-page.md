# Measuring the page

How `hold`, `measure start` / `measure stop` and the page clock work on Windows, and what the numbers mean. Code: `State::hold_cmd`, `State::measure_start_cmd`, `State::measure_stop_cmd`, `State::align_clock`, `State::stamp`, `State::remove_probes` (session/measure.rs), `measure::install_script`, `measure::summarize`, `clock::align`, `Cdp::send` / `Reply::wait`.

## Design model

- **`hold` sends without waiting for replies.** Chromium answers `Input.dispatchKeyEvent` only after the renderer has handled the key (see [[sending-input-over-cdp]]). Awaiting each reply would space the keys by the page's own speed and hide the backlog `hold` exists to produce. `Cdp::send` returns a `Reply` that is awaited after the last key, all against one 15 s deadline (`HOLD_ACK_WAIT`, which the CLI adds to its own wait); `acknowledged` counts the replies. A `Reply` dropped unanswered removes itself from the pending map. Every key-down after the first carries `autoRepeat: true`, which the page sees as `KeyboardEvent.repeat`.
- **The probes are page JavaScript, not CDP domains.** Frames (`requestAnimationFrame`), keydowns (a capture listener and a bubble listener on `window`), the watched element (`MutationObserver`) and visibility (`visibilitychange`) are installed by one `Runtime.evaluate` as `window.__pokitMeasure`, tagged with an id for that measurement. Reading and removing go by the id, so a session that ends late can never remove a newer session's probes. The page can read and change the global; that is accepted, because pokit measures the maintainer's own app. A second engine that can only evaluate JavaScript, such as the macOS plugin, can install the same probes (#16).
- **The probes record raw times; Rust summarises them.** The page returns frame timestamps, `[received, dispatched, ended, repeat]` per key, `[time, value]` per change, and hidden spans. `measure::summarize` turns them into the result, so the arithmetic is unit-tested without a page.
- **A key is handled from the capture listener to the bubble listener.** The handled span runs from the first key's capture to the last key's bubble. A page handler that stops propagation hides the bubble; the span then ends at that key's capture, and that key no longer pushes back the settle point.
- **The page counts as settled when it has gone `quiet_ms` without a long frame or a key ending.** `stop` polls that every 100 ms, up to `ceiling_ms`, and reports `settled: false` past it. `settle_ms` is the time from the last key the page received (or `start`, with no keys) to the last long frame or key end; `settle_wait_ms` is how long `stop` itself waited. A hidden page paints no frames, so it would settle as quiet; the result therefore reports `hidden.was_hidden` and `hidden.hidden_ms`.
- **The gap across a hidden period is not a frame.** `summarize` drops every gap between two frames that overlaps a hidden span. Without that, an 800 ms hidden period comes out as one 850 ms frame (measured 2026-10-06). The fixture's `hide_webview_for` command hides the webview the way a host hides it on minimize (`IsVisible` false), which is how `a_hidden_webview_is_reported_and_its_gap_is_not_a_frame` produces a real hidden period.
- **A reload voids the run (exit 8, `page_reloaded`).** `stop` compares `performance.timeOrigin` with the one recorded at `start`, and checks that the probes are still installed; any new document fails both. An evaluation that fails is retried once 300 ms later, because a reload can destroy the context mid-call and would otherwise surface as a plain error.
- **The probes are removed by `stop`, by a new `start`, by a failed `start`, and by the session ending.** On an attached session, `close` removes them before it answers, and every shutdown path removes them before the session file goes (2 s budget), because the app outlives the session. A launched app is killed through its job, which takes the probes with it.
- **The page clock is aligned by about twenty round trips.** pokit evaluates `performance.timeOrigin + performance.now()`, keeps the sample with the shortest round trip, takes the offset at its midpoint, and reports half that round trip as the uncertainty. It runs when the session starts and at each `measure start`. Every input command reports `sent_at` (one page-clock time per CDP input event it sent) with the `clock` it used, including the target it was aligned on. One alignment serves every target; pages of one WebView2 browser share its clock.

## Measured

- **A backlog is handled in a few long frames, not one per key.** With the fixture stalling 60 ms per key and `hold` sending 20 keys 33 ms apart, three runs gave 3, 2 and 3 frames over 50 ms, the longest 667–850 ms, p95 about 17 ms, and a handled span of 1217–1219 ms (2026-10-06, WebView2 on Windows 11). Chromium handles queued keydowns back to back without painting between them. The count of long frames therefore does not grow with the keys; the time inside them does. The result carries both `over_threshold` (count) and `over_threshold_ms` (time). **Maintainer's call (2026-10-06, #4):** the acceptance item read "frames over 50 ms in proportion to the keys"; shown these runs, the maintainer chose to judge it by `over_threshold_ms` near keys × stall. The alternatives shown were changing the fixture to paint between keys, and keeping the count with a weaker bound.
- **The page clock and pokit's agree to within a millisecond on one machine.** Offsets of −0.08 to +0.05 ms with uncertainties of 0.2–0.7 ms (2026-10-06). Both clocks come from the same system clock, so an integration test cannot see a wrong offset; `clock::tests` covers the arithmetic.
- **A CDP key's `timeStamp` is when the browser created the event.** The first key's `first_received_at` (time origin + `timeStamp`) came after its `sent_at`, by less than a millisecond with no stall.
- **A Tauri page stays visible and painting when its window is covered or minimized.** With the fixture fully covered by a topmost window, and again minimized (`IsIconic`), the page stayed `visible`, painted at 60 fps (p50 16.7 ms) and handled all 10 CDP keys (2026-10-06, Tauri 2.12.1 with wry 0.57.0, WebView2 runtime 154.0.4258.53). WebView2 hides a page only when its host sets the controller's `IsVisible` to false, and asks hosts to do that on minimize (`WebView2.idl`, `ICoreWebView2Controller`, SDK 1.0.4258.31). wry's `WM_SIZE` handler skips `SIZE_MINIMIZED` and never does (`wry` 0.57.0, `src/webview2/mod.rs` 1297). So for a Tauri app, `measure` under a covered or minimized window measures a page that is still rendering. An app that does hide its webview gets `hidden.was_hidden`. `a_covered_or_minimized_window_keeps_rendering_and_taking_keys` pins this, so a WebView2 or wry that starts hiding such pages fails it rather than leaving this note wrong.
- **On macOS the page follows the window's occlusion state, unlike WebView2.** In four arrangements the page's `visibilityState` matched `NSWindow.occlusionState` exactly (WKWebView, macOS 26.6.2, Tauri 2.12.1). Partly covered: visible, 60 fps. Covered by one window filling the screen, minimized, or on another Space: `hidden`, no `requestAnimationFrame` callbacks at all, and a 1 s timer firing about once in 3 s. Covered pixel for pixel is not the test: once the fixture was fully covered by two windows together and stayed visible at 60 fps. Keys still reach a hidden page (see [[sending-input-on-macos]]), so on macOS `measure` under such a window measures a page that is not painting. The plugin can read `occlusionState` directly (measured with a throwaway probe in #10, 2026-10-06).
- **The sending timer can wake early.** Nineteen 33 ms intervals once took 620.5 ms instead of 627 ms. The test allows 10 % either way.
