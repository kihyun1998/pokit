# Measuring the page

## What it is
How pokit measures what the page did with input on Windows: `hold` sends a run of key-downs at a fixed pace without waiting for the page, `measure start` installs probes in the page and `measure stop` reads and summarises them, the page clock is aligned with pokit's so every input command can say when it sent each event on the page's clock, and `hold --compare` runs the same keys on CDP and through the OS, each inside its own measurement, and reports the difference in latency. On macOS only the clock alignment at session start and `sent_at` are built (through the plugin); `measure` and `hold` are not, and what `measure` would see there is recorded below.

## Governing decisions
- [ADR-0002](../adr/0002-hand-written-cdp-client.md) names firing `hold`'s key-downs without awaiting replies as one reason pokit writes its own CDP client. `State::cdp_hold` does that (see Design model).
- [ADR-0001](../adr/0001-commands-talk-to-a-session.md): a measurement lives in the session between `measure start` and `measure stop` (`State::measuring`), and the key-downs `hold` sends in between are added to it. Commands that connected on their own could not keep it.

## Design model
The rules come from maintainer calls on issues (#4, #18, #99) and otherwise only from the source. Size: nothing bounds how long a measurement runs or how much the probes keep. `frames`, `keys` and `changes` are page arrays that only grow until `stop`, and `stop` reads them back in one `Runtime.evaluate` (`measure::read_script`, `EVALUATE_TIMEOUT` 15 s in session/commands.rs) as one CDP reply, which the CDP client's message limit caps ([Speaking CDP](speaking-cdp.md)). `hold --count` is a `u32` with no upper bound, and `State::cdp_hold` keeps one `Instant` and one `Reply` per key (see Known holes).

**`hold`**
- **`hold` sends without waiting for replies.** Chromium answers `Input.dispatchKeyEvent` only after the renderer has handled the key (see [Sending input over CDP](sending-input-over-cdp.md)). Awaiting each reply would space the keys by the page's own speed and hide the backlog `hold` exists to produce. `State::cdp_hold` sends each key with `Cdp::send`, which returns a `Reply` that is awaited after the last key, all against one deadline, `HOLD_ACK_WAIT` (15 s, crates/pokit/src/request.rs), which the CLI adds to its own wait (`Request::extra_wait`). `acknowledged` counts the replies. A `Reply` dropped unanswered removes itself from the pending map (`impl Drop for Reply`, cdp.rs). Every key-down after the first carries `autoRepeat: true` (`KeyPress::down_event`, chord.rs), which the page sees as `KeyboardEvent.repeat`. Pinned by `a_stalling_page_is_measured_as_stalling_while_hold_keeps_its_own_pace` (tests/measure.rs), which requires 19 intervals within 10 % of 19 × 33 ms on a page stalling 60 ms per key.
- **A `hold` that fails while sending still lets go of the keys.** `State::cdp_hold` sends the key-up and the modifiers' key-ups without waiting before it returns the error.
- `hold --count 0` is refused (`State::hold_cmd`). On `--route os` the keys go through the OS ([Sending OS input](sending-os-input.md)); `hold` on the plugin route is refused.
- **Modifier key-downs are not counted as keys.** The probe skips key-downs whose `key` is Control, Shift, Alt or Meta (`modifierKeys` in `measure::INSTALL`), so `hold Ctrl+Equal --count 20` counts 20 handled keys, though CDP sends the modifiers as keys of their own (`KeyPress::modifier_events`; [Sending input over CDP](sending-input-over-cdp.md)). `hold`'s `acknowledged` counts every key event the page acknowledged, the modifiers' included (`State::cdp_hold` awaits their replies too). Pinned by `a_held_chord_counts_its_key_not_its_modifiers` (tests/measure.rs).

**The probes**
- **The probes are page JavaScript, not CDP domains.** Frames (`requestAnimationFrame`), keydowns (a capture listener and a bubble listener on `window`), the watched element (`MutationObserver`) and visibility (`visibilitychange`) are installed by one `Runtime.evaluate` as `window.__pokitMeasure` (`measure::install_script`), tagged with an id for that measurement (`home::token`). Reading and removing go by the id (`measure::with_probes`), so a session that ends late can never remove a newer session's probes. The probes count only trusted events (`e.isTrusted`). The page can read and change the global; that is accepted, because pokit measures the maintainer's own app. A second engine that can only evaluate JavaScript, such as the macOS plugin, can install the same probes (#15, #16).
- **The probes record raw times; Rust summarises them.** The page returns frame timestamps, `[received, dispatched, ended, repeat]` per key, `[time, value]` per change, and hidden spans. `measure::summarize` turns them into the result, so the arithmetic is unit-tested without a page (the tests beside it in measure.rs).
- **Every threshold used is in the result** (`Thresholds::to_json`; `every_threshold_used_is_in_the_result`). Defaults: `long_frame_ms` 25, `over_ms` 50, `quiet_ms` 1000, `ceiling_ms` 10 000 (`Thresholds::default`, and the same defaults on the command line in main.rs).
- **A field nobody asked for, or with nothing to report, says so instead of holding a zero:** "not requested", "no frames painted", "no keys handled" (`measure::summarize`; `missing_frames_and_keys_carry_a_reason_not_a_zero`, `unwatched_fields_say_not_requested`).
- **A key is handled from the capture listener to the bubble listener.** The handled span runs from the first key's capture to the last key's bubble. A page handler that stops propagation hides the bubble; the span then ends at that key's capture, and that key no longer pushes back the settle point (`keyEnd` in `measure::INSTALL`; `keys_span_from_the_first_dispatch_to_the_last_end_or_start`).
- **The page counts as settled when it has gone `quiet_ms` without a long frame or a key ending.** `State::measure_stop_cmd` polls that every 100 ms (`measure::state_script`), up to `ceiling_ms`, and reports `settled: false` past it. `settle_ms` is the time from the last key the page received (or `start`, with no keys) to the last long frame or key end; `settle_wait_ms` is how long `stop` itself waited. A hidden page paints no frames, so it would settle as quiet; the result therefore reports `hidden.was_hidden` and `hidden.hidden_ms`.
- **A backlog is judged by time in long frames, not their count.** The result carries both `over_threshold` (count) and `over_threshold_ms` (time), because Chromium handles a backlog in a few long frames (Reference behaviour). **Maintainer's call (2026-10-06, #4):** the acceptance item read "frames over 50 ms in proportion to the keys"; shown the runs, the maintainer chose to judge it by `over_threshold_ms` near keys × stall. The alternatives shown were changing the fixture to paint between keys, and keeping the count with a weaker bound. Pinned by `a_stalling_page_is_measured_as_stalling_while_hold_keeps_its_own_pace`, which requires `over_threshold_ms` within 0.9–1.5 × 20 × 60 ms.
- **A calm page may show one short long frame.** `a_page_that_does_not_stall_causes_no_frames_over_50_ms` (tests/measure.rs, #18) allows at most 1 frame over 50 ms, under 200 ms in all (`frames_over_threshold_are_the_machines`). Requiring none failed about once in 15 full runs, and once with the screen locked, at `count 95, max_ms 90.1, over_threshold 1` (2026-10-06): one frame from the machine, not the page. The stalled fixture spends at least 1080 ms in such frames (20 keys × 60 ms × 0.9), so the two stay more than 5× apart. **Maintainer's call (2026-10-12, #18):** this relaxes #4's "with no stall, it reports none" to none that the page caused; `measure` itself is unchanged. The other options shown were keeping none and accepting the flake, and comparing a calm and a stalled run in one test. `one_short_long_frame_is_the_machines_and_more_is_the_pages` feeds the rule made-up measurements: 0 and one of 90.1 ms pass, two frames or 200 ms fail. Reddened 2026-10-12: requiring none failed it on the 90.1 ms frame; dropping the count, or the 200 ms bound, each failed it; and the calm test run against the stalled fixture (`__stallMs` 60) failed.

**Hidden periods**
- **The gap across a hidden period is not a frame.** `measure::summarize` drops every gap between two frames that overlaps a hidden span. Without that, an 800 ms hidden period comes out as one 850 ms frame (measured 2026-10-06). The fixture's `hide_webview_for` command (fixtures/app/src/main.rs) hides the webview the way a host hides it on minimize (`IsVisible` false), which is how `a_hidden_webview_is_reported_and_its_gap_is_not_a_frame` (tests/window.rs) produces a real hidden period. That test expects the hidden period reported, `hidden_ms` 600–1500 and no frame over 400 ms (half the 800 ms hidden).
- **A hidden period the page reports only once it is over is taken to be the gap it belongs to** (`measure::hidden_span`, #99). Under load WebView2 can deliver `hidden` and `visible` together after painting has resumed (Reference behaviour), so the reported span sits at the end of the gap or in the frame right after it. When a span starts inside a gap longer than `long_frame_ms`, or in the frame right after one (the next frame within `long_frame_ms`), and the page reported it over after that gap ended, the gap is the hidden period: it is not a frame, and it is what `hidden_ms` counts. A span the page reports over before painting resumes, as a page really hidden reports it, is kept as reported, so a long frame just before a real hide stays a long frame. **Maintainer's call (2026-10-23, #99):** this over leaving `hidden_ms` as the page reports it (and checking only the frame-gap exclusion in the test, which failed 2 of 4 under load because the late span fell after the gap) or first finding what delays the event, which stays open. `a_hidden_webview_is_reported_and_its_gap_is_not_a_frame` passes under CPU load only with `hidden_span`: 6 of 6 runs under load reported about 800 ms hidden and no long frame; without it, 4 of 4 reported 2.2–2.4 ms. The unit tests beside `summarize` cover a span late in the frame after a gap (`a_hidden_period_reported_in_the_frame_after_a_long_gap_began_with_the_gap`), one at the gap's end reported over after it (`a_hidden_period_reported_at_the_end_of_a_long_gap_and_over_after_it_is_the_gap`), one later than the frame after the gap (`a_hidden_period_later_than_the_frame_after_a_long_gap_stays_where_it_was`), one after a short gap (`a_hidden_period_after_a_short_gap_stays_where_it_was`), and a page hidden right after a long frame (`a_page_hidden_right_after_a_long_frame_keeps_both`). Reddened 2026-10-23: dropping the rule, ignoring when the span was reported over, and either half of where it may start each turned a unit test red.

**Latency**
- **`latency` is how long each key took from leaving pokit to the page starting to handle it.** The key-downs `hold` sends while a measurement runs are kept on the page clock (`State::note_key_downs`, only for keys sent to the measured target), and `measure stop` pairs them in order with the key-downs the probe saw (`measure::latency`), reporting p50, p95, max and the clock's uncertainty. Only `hold` feeds it.
  - The pairing is by order, so it holds only when the page handled exactly as many key-downs as pokit sent (`handled_keys`, `sent_keys`). Otherwise the numbers are a sentence saying why: a key from the user, from `key` or `type`, or one an IME swallowed shifts every pair after it, and nothing in the probe tells which key is which (`latency_is_not_paired_when_the_page_saw_other_keys_than_pokit_sent`).
  - A chord of modifiers only (`hold Control`) sends key-downs the probe does not count, so it never pairs.

**`hold --compare`**
- **`hold --compare` takes its own measurements.** `State::hold_compare_cmd` runs `measure start` with the default thresholds, the `hold`, and `measure stop --quiet 300` with `COMPARE_SETTLE` (10 s, request.rs) as the ceiling, first on CDP and then through the OS, and reports each route's `latency`, `keys` and `frames` and `os_minus_cdp` for p50 and p95. The CLI waits twice one run's time plus `COMPARE_SETTLE` on top of its own (`Request::extra_wait`). The OS side of the run is [Sending OS input](sending-os-input.md).
- **`hold --compare` refuses while a measurement runs** (exit 6, `guard_refused`): starting its own would remove the running one's probes. It is refused on a platform without OS input (`unsupported`), and without the app in front (`State::refuse_unless_front`).

**Reloads, removal, races**
- **A reload voids the run (exit 8, `page_reloaded`).** `stop` compares `performance.timeOrigin` with the one recorded at `start`, and checks that the probes are still installed (`page_state`, and a null from `measure::read_script`); any new document fails both. An evaluation that fails is retried once 300 ms later (`page_state`), because a reload can destroy the context mid-call and would otherwise surface as a plain error. Pinned by `a_reload_between_start_and_stop_voids_the_run` (tests/measure.rs). The same rule for a trace or profile is in [Tracing the page](tracing-and-profiling.md).
- **The probes are removed by `stop`, by a new `start`, by a failed `start`, and by the session ending** (`State::remove_probes`, `State::remove_measurement`). On an attached session, `close` removes them before it answers (`Request::Close` in session/commands.rs), and `State::shutdown` removes them before the session file goes, within `REMOVE_WAIT` (2 s), because the app outlives the session. A launched app is killed through its job, which takes the probes with it ([Starting the session process](starting-the-session-process.md)). Pinned by `closing_an_attached_session_without_stop_leaves_no_probe` and, for a failed `start`, `stop_without_start_and_a_watch_on_nothing_are_refused` (tests/measure.rs).
- **Two `measure start`s arriving together run one after the other** (`State::measure_starting`, held for the whole `start`), so the page's probes and the measurement the session records always come from the same `start`; the second replaces the first, as any new `start` does. Without it, one start's probes could end up on the page while the session recorded the other's, and `stop` would report a reload. That interleaving was read from the code (#22) and not seen in 20 tries without the lock (2026-10-08). `two_starts_at_once_give_one_recording_and_pokits_own_refusal` (tests/profile.rs) runs ten such pairs and requires both to succeed and the following `stop` to succeed.

**The page clock**
- **The page clock is aligned by twenty round trips** (`clock::SAMPLES` = 20). `State::align_clock` evaluates `performance.timeOrigin + performance.now()`; `clock::align` keeps the sample with the shortest round trip, takes the offset at its midpoint, and reports half that round trip as the uncertainty (`clock::tests`). It runs when the session starts, on either engine (`State::align_main_clock` through `State::page`; a failure is logged, not fatal), and at each `measure start`. Through the plugin each sample is a fresh loopback connection (`Plugin::request` connects per call, plugin.rs), so its uncertainty includes the connect; no macOS figure has been taken (#15). Every input command reports `sent_at` (one page-clock time per input event it sent) with the `clock` it used, including the target it was aligned on (`State::stamp`, `State::clock_json`); pinned by `input_carries_its_send_time_on_the_page_clock` (tests/measure.rs). One alignment serves every target; pages of one WebView2 browser share its clock.
- `clock::local_ms` puts pokit's `Instant`s on the epoch from one wall-clock reading taken at first use, so pokit's side is monotonic.

## Reference behaviour
- **A backlog is handled in a few long frames, not one per key.** With the fixture stalling 60 ms per key and `hold` sending 20 keys 33 ms apart, three runs gave 3, 2 and 3 frames over 50 ms, the longest 667–850 ms, p95 about 17 ms, and a handled span of 1217–1219 ms (2026-10-06, WebView2 on Windows 11, #4). Chromium handles queued keydowns back to back without painting between them. The count of long frames therefore does not grow with the keys; the time inside them does.
- **The page clock and pokit's agree to within a millisecond on one machine.** Offsets of −0.08 to +0.05 ms with uncertainties of 0.2–0.7 ms (2026-10-06). Both clocks come from the same system clock, so an integration test cannot see a wrong offset; `clock::tests` covers the arithmetic.
- **A CDP key's `timeStamp` is when the browser created the event.** The first key's `first_received_at` (time origin + `timeStamp`) came after its `sent_at`, by less than a millisecond with no stall (2026-10-06).
- **Under CPU load the page can receive `visibilitychange` about 800 ms late, so `hidden_ms` came out short (2026-10-22, #99, all 16 cores busy).** The fixture applied `SetIsVisible(false)` and `(true)` 805–830 ms apart every time, while the page's `hidden` and `visible` sometimes arrived 1–2 ms apart: 1 of 4 hides on one launch (the first), both of 2 with the measure running, 4 of 4 runs of `a_hidden_webview_is_reported_and_its_gap_is_not_a_frame`, and in 2 full test runs (164.6 and 582.6 ms). A `requestAnimationFrame` loop made no difference. Recorded on the page itself under the same load, 6 of 6 launches: the frames stopped for 817–833 ms, and the late `hidden` arrived 3–11 ms after the first frame of the resumed painting and before the next, or (1 of 6) 1 ms before that first frame; `visible` followed within 2 ms. When the span lay after the gap, the gap was read as one 817 ms frame (2 of 4 runs).
- **A Tauri page stays visible and painting when its window is covered or minimized.** With the fixture fully covered by a topmost window, and again minimized (`IsIconic`), the page stayed `visible`, painted at 60 fps (p50 16.7 ms) and handled all 10 CDP keys (2026-10-06, Tauri 2.12.1 with wry 0.57.0, WebView2 runtime 154.0.4258.53). WebView2 hides a page only when its host sets the controller's `IsVisible` to false, and asks hosts to do that on minimize (`WebView2.idl`, `ICoreWebView2Controller`, SDK 1.0.4258.31). wry's `WM_SIZE` handler skips `SIZE_MINIMIZED` and never does (`wry` 0.57.0, `src/webview2/mod.rs` 1297). So for a Tauri app, `measure` under a covered or minimized window measures a page that is still rendering. An app that does hide its webview gets `hidden.was_hidden`. `a_covered_or_minimized_window_keeps_rendering_and_taking_keys` (tests/window.rs) pins this, so a WebView2 or wry that starts hiding such pages fails it rather than leaving this note wrong.
- **On macOS the page follows the window's occlusion state, unlike WebView2.** In four arrangements the page's `visibilityState` matched `NSWindow.occlusionState` exactly (WKWebView, macOS 26.6.2, Tauri 2.12.1). Partly covered: visible, 60 fps. Covered by one window filling the screen, minimized, or on another Space: `hidden`, no `requestAnimationFrame` callbacks at all, and a 1 s timer firing about once in 3 s. Covered pixel for pixel is not the test: once the fixture was fully covered by two windows together and stayed visible at 60 fps. Keys still reach a hidden page (see [Sending input on macOS](sending-input-on-macos.md)), so on macOS `measure` under such a window would measure a page that is not painting. The plugin can read `occlusionState` directly (measured with a throwaway probe in #10, 2026-10-06).
- **The sending timer can wake early.** Nineteen 33 ms intervals once took 620.5 ms instead of 627 ms (Windows). The test allows 10 % either way.

## Cross-cutting invariants
- [Capabilities match behaviour](capabilities-match-behaviour.md): `capabilities` declares `hold`'s routes (`support::routes`, `"hold"`: CDP without taking focus, OS needing the app in front), and `State::hold_cmd` is what does it.

## Blast radius
- [Sending input over CDP](sending-input-over-cdp.md) — `hold` builds its key events from the same chord (`KeyPress::down_event`, `KeyPress::modifier_events`), and the probe's count assumes CDP sends each modifier as a key-down of its own with `key` Control/Shift/Alt/Meta; a change in how a chord is sent shifts `handled` and breaks the latency pairing. Every input command's `sent_at` comes from `State::stamp` here.
- [Sending OS input](sending-os-input.md) — `hold --compare` and `latency` assume the OS route delivers exactly `--count` key-downs to the page, one per send; an OS that auto-repeats, drops or doubles a key leaves the route unpaired.
- [Starting the session process](starting-the-session-process.md) — an attached app keeps the probes after the session unless every exit path calls `State::remove_probes` before the session file goes; a new shutdown path that skips it leaves `window.__pokitMeasure` in the user's app.
- [The app's pages](the-apps-pages.md) — the measurement, the clock alignment and the key-downs noted for latency are tied to the current target, and that target is a CDP one: `State::hold_cmd` reads `State::current` after sending on every route to note its key-downs, and `State::current` fails where the session holds no CDP target, as a plugin session (macOS) holds none. A route that reaches the page without CDP needs the page engine's seam there ([Reaching the page through the plugin](reaching-the-page-through-the-plugin.md)). A change in which target is current, or in when a page counts as ready (`State::ensure_ready`), changes what `measure` measures. A reload is detected by `performance.timeOrigin` alone.
- [Tracing the page](tracing-and-profiling.md) — both void a run on a changed `performance.timeOrigin`; a page that keeps its time origin across a document change would void neither.
- [Reaching the page through the plugin](reaching-the-page-through-the-plugin.md) — the clock is aligned through `Page::Plugin` on macOS, and the probes are written to be installable by plain evaluation (#15); the plugin's per-call connection widens the clock's uncertainty.
- [Testing against the fixture](testing-against-the-fixture.md) — the test bounds assume the fixture stalls exactly `__stallMs` per key in `#stall`, counts keys in `#key-count`'s `data-count`, and hides its webview with `hide_webview_for` the way a host does on minimize.

## Known holes / open
- **macOS: none of `measure`, the probes or the clock figures is built or taken through the plugin.** Tracked: #15. `hold` through the plugin: Tracked: #38.
- **What delays `visibilitychange` under load is not known** (#99); `hidden_span` works around where the late span lands, not why it is late.
- **The probes keep every frame, key and change until `stop`, and nothing bounds a measurement's length.** `stop` reads them in one evaluation with a 15 s timeout and one CDP reply. An hour at 60 fps is about 216k frame times; without `--watch-attr`, every mutation record reads the watched element's whole `textContent`. The cost on a long or busy measurement is unmeasured. Tracked: #87.
- **`hold --count` has no upper bound**; `hold`'s own per-key memory and a CLI wait of count × interval + 15 s grow with it, unmeasured at large counts.
- **The latency pairing cannot tell which key is which**, so any key from elsewhere voids it; no per-key tag exists in the probe.
- **No integration test can see a wrong clock offset** on one machine, because both clocks come from the same system clock (Reference behaviour).
