# Sending OS input

## What it is

How `window activate` brings the launched app's window to the front, and how `key`, `type`, `click`, `hold`, `wheel` and `drag` reach the page on `--route os` through `SendInput` on Windows: the guard that lets OS input through only when it would reach the page pokit is on, the keys sent by physical scan code, the click placed in physical pixels, the keys and button released whatever happens, and the check that the keys and an HTML5 drag reached the page. macOS has no OS route here; that is [Sending input on macOS](sending-input-on-macos.md).

## Governing decisions

**None.** [ADR-0001](../adr/0001-commands-talk-to-a-session.md) is adjacent: the one-at-a-time lock and the keys kept down live on the session it decides, so a session that ends releases them, but it decides where commands run, not how input is sent. [ADR-0002](../adr/0002-hand-written-cdp-client.md) is adjacent too: this route still reads the page over CDP (`devicePixelRatio`, `document.hasFocus()`, the keydown and drag counts), but sends no input through it.

## Design model

The rules come from maintainer's calls on #5, #52 and #93, from #1's stories (17, 38, 42), and otherwise from the source. Outside input: the text of `type`, the chord of `key` and `hold`, a page point, `--notches`, `--count`, `--steps` and `--via`. `--steps` is 1–1000 (clap range in `crates/pokit/src/main.rs — Command::Drag`) and a drag is capped at 10 s of moves (`DRAG_LONGEST`); nothing bounds the length of `type`'s text, `wheel --notches` or `hold --count` except the command's time limit (see Known holes).

### The guard

- **OS input goes ahead only when it would reach the page pokit is on, and is refused otherwise (exit 6, `guard_refused`, nothing sent, nothing scrolled or focused).** #1 story 38. Three checks:
  - before anything happens on the page (`State::refuse_unless_front`, called first by `click_cmd`, `drag_cmd`, `wheel_cmd`, `hold_cmd`, `hold_compare_cmd`, `os_key_cmd`, `os_type_cmd`): the foreground window belongs to the app (`os_input::is_frontmost`); the window that holds the current page, found from the page as `window move` finds it ([Placing the app's windows](placing-windows.md)) with the page given 1 s (`PAGE_ANSWER`) through `State::current_page_window`, is the foreground window itself, not another of the app's windows nor a dialog it owns (`os_input::front_page`); and the page has the input focus (`document.hasFocus()`). A page whose window cannot be found is refused too, naming why (#95).
  - `os_input` checks again right before `SendInput` that the foreground window is that window: `key`, `text` and `strokes` call `front_page`, so each key-down of a hold is checked on its own.
  - a click, a wheel and a drag's first point are placed in that window (`at_page_point`), which must hold a render widget, and the window found at the point (`GetAncestor(WindowFromPoint(..), GA_ROOT)`) must be that window, so a window covering the page cannot take the input.
  - Until #95 the first two asked whether any of the app's windows was in front, and trusted `document.hasFocus()` for which page: with another window in front and the main page also reporting the focus, an OS key went into the other window and was caught only by the delivery check (exit 9), and an OS click landed there and came back `ok` (3 of 3 each, 2026-10-22). The guard is stricter than `window activate`'s test, which counts a window the page's window owns: a dialog in front would take the input.
  - Finding the page's window costs about 1–3 ms of an OS command (2026-10-22, 6 runs: the page's place 0.7–2.4 ms over CDP, the window 1.0–3.0 ms). Ten `key --route os` commands each, alternating with the build before #95, took 192–599 ms against 197–483 ms: the difference is within the noise.
  - `hasFocus` is kept only as a second check because it does not tell which of the app's pages takes the input (see Reference behaviour).
  - Pinned by `os_input_to_an_app_not_in_front_is_refused_and_sends_nothing` (tests/os_input.rs): with the app behind, every OS command and `hold --compare` is refused with exit 6 naming `window activate`, and no key, input, mouse event or scroll reaches the page. The guard passes while either foreground check holds, so a mutation has to remove both to turn it red (done 2026-10-07); moving the click's check after scrolling turned its scroll assertion red.
  - Pinned by the second-window and dialog cases of `os_input_reaches_the_page_as_a_hand_would_send_it` (tests/os_input.rs), run after the clicks: the second window brought forward with `window activate`, then an OS key to the main page refused (exit 6) with nothing reaching it; with the app's own dialog open (`native choose "Help > Ask"`), an OS click refused (exit 6). Removing the page-focus check turned the second-window case red (2026-10-07).
  - Pinned by `os_input_goes_ahead_only_with_the_window_of_the_current_page_in_front` (tests/os_input.rs): it brings the second window forward with another fixture in front, checks that the main page still reports the focus (so the case occurred), and expects an OS key and click to the main page refused (exit 6) with nothing reaching it, a key to the second page delivered, and a key to a stalled page refused. Reddened 2026-10-22: letting any of the app's windows through in `front_page` turned it red; waiting 15 s for the page instead of `PAGE_ANSWER` turned the stalled case red. Counting a window the page's window owns and dropping `hasFocus` together turned the dialog case red; dropping `hasFocus` alone left it green, so the window rule covers the dialog by itself.

### `window activate`

- **`window activate` is how the app gets in front, and it takes the user's focus.** `os_input::activate` tries `SetForegroundWindow`, waits up to 500 ms for the window to hold the foreground (`wait_front`), then the same call while attached to the foreground window's input queue (`AttachThreadInput`, with `BringWindowToTop`), and `State::window_activate_cmd` refuses with exit 6 when Windows keeps the app back, naming `foreground_pid`. The result names which way worked (`how`: `AlreadyFront`, `Plain`, `AttachInput`) and `previous_pid`. A minimized window is restored first (`SW_RESTORE`). **Maintainer's call (2026-10-06, #5):** an explicit command in pokit, not a test-only workaround and not a person bringing the app forward. **Maintainer's call (2026-10-07):** plain, then `AttachThreadInput`, never the synthetic Alt key tao uses. The Alt key would put a keystroke into the user's app, which can open its menu bar.
  - **It brings forward the window that holds the current page** (#93), found through `State::current_page_window` with the page given 1 s to say where it is (`PAGE_ANSWER`). The window is in front when it, or a window it owns, is the foreground window (`holds_front`), so the app's own dialog over it counts and the guard then refuses. The result says `window: "page"`. Until #93 it took the app's largest unowned window and counted any of the app's windows in front as done, so a page in another window could not be brought forward at all, and the next OS command was refused (exit 6, 3 of 3, 2026-10-22).
  - Measured 2026-10-22 (#93, 3 runs, another fixture in front): with the app's own dialog open over the page's window, `window activate` came back `ok` with `window: "page"`, the dialog was the foreground window, the page reported `document.hasFocus()` `false`, and `key KeyA --route os` was refused (exit 6). The same as before #93.
  - **When the page's window cannot be found, the main window comes instead, and the result says so** (`window: "main"`, `page_not_placed` with the reason; the main window is the largest visible unowned one by its normal size, `os_input::app_window`): a page that does not answer within `PAGE_ANSWER`, two windows of one size on top of each other, a minimized window (the main one is restored, not the page's). **Maintainer's call (2026-10-22, #93):** this over refusing, because a stuck page is when bringing what the user sees forward matters most (cf. #53).
  - It forgets the window that was in front at the last click (`foreground_at_click`), so a deliberate activation is not undone by a later give-back ([Reaching an app's native UI](reaching-native-ui.md)).
  - An attached session refuses (exit 7, `State::native_pid`): it does not know the app's process.
  - Pinned by `window_activate_brings_forward_the_window_of_the_current_page` (tests/os_input.rs): it brings the second window's page forward with the main window in front and with another fixture in front, sends it an OS key, and stalls the page for the main-window fallback. The second-window case of `os_input_reaches_the_page_as_a_hand_would_send_it` uses `window activate` too, so it always runs; before #93 it was skipped when the second window did not happen to stay in front. Both read the foreground window's title from the system rather than `document.hasFocus()`, because with the second window opened while the app was behind and taking the foreground, the main page and the second both reported `true` (3 of 3, 2026-10-22), so a `hasFocus` assertion stayed green with `activate` counting any of the app's windows in front. Reddened 2026-10-22: taking the main window whatever the page, counting any of the app's windows in front, and waiting 15 s for the page instead of `PAGE_ANSWER` each turned it red.

### Keys and text

- **A chord is pressed as a hand presses it, by physical key.** Modifiers go down, then the key goes down and up, then the modifiers come up in reverse (`chord_strokes`), all in one `SendInput` call so that no other input interleaves. A page counting keydowns sees Control as a key of its own here; how CDP sends modifiers is [Sending input over CDP](sending-input-over-cdp.md)'s. Pinned by `a_chord_is_pressed_modifiers_first_and_released_in_reverse` (os_input.rs unit test).
  - Each key is sent as its scan code on a US keyboard (`us_scan`, `KEYEVENTF_SCANCODE`, `KEYEVENTF_EXTENDEDKEY` for the arrow, navigation and Meta keys), the same physical key whatever the user's layout: the page's `KeyboardEvent.code` comes from the scan code, and with no scan code `Ctrl+KeyK` arrived as `code ""`. Pinned by `every_key_the_chord_table_knows_has_a_physical_key`.
  - What the key types then follows the user's layout and input method, as a real keyboard's would: on AZERTY `KeyA` types `q`, and with a Korean IME in Hangul mode a letter key arrives as `Process`. The result therefore reports the key's `code`, not a `key` value (`State::os_key_cmd`).
  - The first version sent virtual keys, which `MapVirtualKeyW` mapped through the session thread's layout, and so pressed a different physical key on a non-US layout (independent review, 2026-10-07).
  - If Windows takes only part of a chord, every modifier already pressed is released again, so none is left down for the user (`os_input::key`).
- **`type` sends each character as Unicode (`KEYEVENTF_UNICODE`), one input per UTF-16 unit, and a newline as the Enter key** (`os_input::text`; `\r\n` and `\r` become `\n` in `State::os_type_cmd`). There is no IME composition on this route; `capabilities` says so (`ime_composition: false`), and the CDP route composes ([Typing Korean through IME](typing-korean-through-ime.md)).
- **`type` and `key` check the trusted keydowns the page receives against the key-downs sent, matched by `code`, and fail with exit 9 (`not_delivered`) when some never arrive** (#73, #78; the listener `NOTE_KEYDOWNS`, the matching `check_delivery` and their rules are [Sending input over CDP](sending-input-over-cdp.md)'s). `type` expects one keydown with `code ""` per UTF-16 unit (`os_input::text_down_codes`), a newline being one `Enter`; `key`, one per modifier and one for the key, by their physical codes (`KeyPress::down_codes`). A key typed on a keyboard always has a physical `code`, so it never matches a character `type` sends. OS keys reach the page after `SendInput` returns, so the keydowns are read once every sent one has arrived or after 500 ms (`KEYS_SETTLE_MS`), in one call; read at once it came up short and the command failed though every key arrived (3 runs of 3, 2026-10-08). From just before `SendInput` to the last keydown: mean 2.8 ms, at most 11.9 ms (33 commands, 2026-10-08, #73).
  - Pinned by `os_type_and_key_count_the_keydowns_the_page_received` (tests/os_input.rs): types `Ab😀`, a newline and `한` (6 keydowns) and `Ctrl+KeyK` (2), then swallows `b` and then `Control` and `k` with a page listener and expects exit 9 with the missing count. Reddened 2026-10-08: no count on this route, counting characters instead of UTF-16 units, and reading without waiting (`KEYS_SETTLE_MS` 0, red 3 runs of 3) each turned it red. Since #78 it also types while someone else types (`Pokit::while_someone_types`, tests/common/mod.rs): with `b` swallowed it expects exit 9 with one missing and some unexpected, and with nothing swallowed, for `type` and `key`, exit 0, `unverified`, and no `Backquote` or `` ` `` in the output. Reddened 2026-10-12: counting instead of matching codes, and waiting until the count reaches the number sent (red 3 runs of 3), each turned it red. Unit test: `typed_text_has_a_codeless_keydown_per_utf16_unit_and_enter_for_a_newline`.

### Click

- **A click lands at the element's centre in physical pixels.** The page's top-left corner is the client origin of the WebView2 render widget (`Chrome_RenderWidgetHostHWND`, found by `os_input::render_widget`) inside the page's window. The element's CSS position is multiplied by the page's `devicePixelRatio`, read per command (`State::os_click`), and added to that corner (`to_screen`, pinned by `a_page_point_scales_by_the_pixel_ratio_from_the_viewport_corner`). This is worked out with the thread switched to per-monitor DPI awareness (`SetThreadDpiAwarenessContext` in `at_page_point`), because the session is otherwise unaware and Windows would scale the coordinates it returns. The mouse moves there and clicks, in one `SendInput` call, so the user's cursor moves too. The result gives the `screen` point and the ratio.
  - At 150% scaling (DPI 144, device pixel ratio 1.5) an OS click on `#target` produced `click`, a double click `dblclick`, and a right click `contextmenu` (2026-10-07).

### Hold

- **`hold --route os` presses the modifiers, sends the key-downs on schedule without key-ups, then releases the key and the modifiers** (`State::os_hold`). Windows marks every key-down after the first as a repeat by itself (the key is already down), so the page sees `repeat: true` from the second on. The key and modifiers are released whatever happens, without the foreground check (`os_input::release`): a key left down would stay down for the user, in whichever app is in front by then.
  - The keys down are also kept on the session (`keys_down`) and released when it ends (`State::shutdown`), so `close`, the idle timeout or the app exiting in the middle of a hold leaves none down.
  - OS input commands run one at a time (the `os_input` lock taken in `State::handle` when `Request::sends_os_input`, which includes `hold --compare`): a `type` arriving while a hold has Control down would otherwise type shortcuts. Other CDP commands are not held back; how a CDP `type` or `key` waits for another is [Sending input over CDP](sending-input-over-cdp.md)'s.
  - If the app leaves the front mid-hold, the error says how many key-downs went through and that every key pokit pressed was released.
  - Neither the release at the end nor the one-at-a-time lock has a test; both were read, not reddened.
- **`hold --compare` runs the same keys on CDP and then through the OS, each inside its own measurement, and refuses before either route runs unless the guard passes** (`State::hold_compare_cmd`). Its `os_minus_cdp` is the native layer's share and also holds pokit's hand-off to a blocking thread for each OS key (`spawn_blocking` in `session/os_input.rs — os`); the measuring side is [Measuring the page](measuring-the-page.md)'s. Measured 2026-10-07: in three runs of `hold KeyA --count 20 --compare`, the send-to-handling p50 was 0.6–0.8 ms on CDP and 1.9–2.0 ms through the OS; OS minus CDP was 1.2–1.3 ms at p50 and 1.5–2.5 ms at p95, against a clock uncertainty of 0.10–0.18 ms.

### Wheel

- **`wheel` turns the wheel over an element, a point, or the middle of the page, without scrolling anything into view** (`State::wheel_cmd`, shared by both routes). It aims at the middle of the part of an element that is in view, and refuses an element wholly out of view and a point outside the viewport (exit 5), because the wheel turns where the cursor is. Through the OS it is one `MOUSEEVENTF_WHEEL` of 120 per notch (`WHEEL_DELTA`), sent in a `SendInput` call of its own after the cursor's move (`os_input::wheel`), and how far that scrolls is Windows' and Chromium's business (the user's lines-per-notch setting, display scaling). The CDP notch's size is [Sending input over CDP](sending-input-over-cdp.md)'s; it was set to what one OS notch scrolled (see Reference behaviour).
  - The move and the wheel go in two calls because one call made WebView2 dispatch a notch twice (#64, see Reference behaviour). Pinned by `hold_wheel_and_the_comparison_run_on_both_routes` (tests/os_input.rs): it puts the real cursor off the window before 4 OS notches (`window::put_cursor`, tests/common/window.rs), and each must be one wheel event that scrolls as far as the CDP notch. Four, because one call doubled about 7 notches in 10. The test checks that both routes scroll alike, not a number of pixels. Reddened 2026-10-08: sending the move and the wheel in one call turned it red in 2 runs of 2.

### Drag

- **`drag` holds the left button along a path of page points, and through the OS the path may leave the window.** #1 story 17. The path is the element's centre, any `--via` points, then the drop (an element's centre or `--to-x`/`--to-y`), with `--steps` evenly spaced moves on each straight part, about a frame (16 ms, `DRAG_STEP`) apart (`drag_path`, pinned by `a_drag_path_steps_evenly_along_each_part_and_ends_on_each_point`). These rules are `State::drag_cmd`'s, shared by both routes; the CDP route's own sending is [Sending input over CDP](sending-input-over-cdp.md)'s.
  - Through the OS only the first point is checked to be the page (`at_page_point`); the rest go wherever they lead on the screen, which is the point of the route. Each later point is placed from the first by the same ratio (`start + (x − first.x) × ratio` in `os_input::drag`). The button is released at the end whatever goes wrong, by a guard dropped at the end of the drag (`Held`), so a panic releases it too, and it is kept on the session (`keys_down`, as `LEFT_BUTTON`) so that a session ending mid-drag releases it. `os_input::drag` waits one step after the last move before it lets the button go.
  - A left button left down stays down for the user: reddening the drag by dropping its button release left the system's left button down after the test (`GetAsyncKeyState`) until it was released by hand.
  - `capabilities` says which route leaves the page (`leaves_the_page`).
  - The element dragged is scrolled into view only if it is not in view already (`block: 'nearest'`, `SCROLL_INTO_VIEW_IF_NEEDED`), so points taken from the page before stay where they were. A `--to` element is not scrolled: out of view it is refused (exit 5), because through the OS its centre would be a point outside the window, where the button would be let go over whatever is there.
  - A `--to` element in another page than the one dragged from is refused (exit 2): crossing into another window is a drop at a point with `--route os`.
  - A drag of over 10 s of moves (`DRAG_LONGEST`) is refused (exit 2), so it ends inside a command's time limit and does not keep moving the cursor after the caller gave up.
  - One scale is used for the whole path, the page's `devicePixelRatio`; a path onto a monitor with another scale lands off by the ratio between them. Not measured.
  - Pinned by `a_drag_out_of_the_window_through_the_os_opens_a_window_where_it_was_dropped` (tests/os_input.rs), with `a_drag_on_cdp_moves_the_pointer_within_the_page_and_refuses_to_leave_it` (tests/fixture.rs) for the shared rules. Reddened 2026-10-07: ignoring `--steps`, not releasing the button through the OS, not refusing an OS drag before scrolling, not refusing a `--to` element out of view, and not capping the drag's length each turned one red. Without the command line's `--to` requirement the session's own refusal still gives exit 2. No test: releasing the button when the session ends, a `--to` in another page. Before each OS drag the fixture's window is moved to (40, 40), so that the drop 150 CSS pixels past its right edge is on the screen.
- **HTML5 drag and drop (`draggable`, `dragstart`, `dragover`, `drop`) reaches the page on CDP whatever the app's settings, and through the OS only in a window with Tauri's drag-and-drop handling off** (#52; the measurements and the reason are in Reference behaviour). **Maintainer's call (2026-10-22, #52):** `capabilities` says which kinds of drag each route reaches (`html5_drag`), and an OS drag counts the page's drag events and fails with exit 9 (`not_delivered`) when an in-page drop got a `dragstart` that was not cancelled and a `dragend` with no `drag` between them, naming both causes (the window's drop target, a path too short) and `--route cdp`; a page that changed mid-drag is `unverified`, and a drop outside the page is reported, not checked. Chosen over `capabilities` alone and over reporting the counts with exit 0, against the measurement table and an adversarial read of the options.
  - Built as `NOTE_DRAGS`, `read_drags` and `drag_delivery` (session/os_input.rs). The count is taken on the page's `window` in the capture phase, trusted events only, in a slot of its own (`__pokitDrags`), and a `dragstart` counts as cancelled when its `defaultPrevented` is set once dispatch is over. Every OS drag reports `drag_events` (`dragstart`, `drag`, `dragend`), `null` when no HTML5 drag started (a pointer drag, or one the page cancelled).
  - It is judged by `drag`, which fires on the dragged element and so on the page pokit counts on, not by `dragover` or `drop`, which go to the target: an iframe, another of the app's windows, or a zone that refuses the drop would read as a failure.
  - The read waits for `dragend`, up to 1 s (`DRAG_SETTLE_MS`); measured, it had always arrived already: 10 of 10 (5 with the handling on, 5 off; the read waited 0–0.5 ms, 2026-10-22).
  - The CDP route does not count: Chromium's DevTools drag controller drives the drag there whatever the window's drop target ([Sending input over CDP](sending-input-over-cdp.md)).
  - A drag with no `drag` events between `dragstart` and `dragend` does not by itself tell the handling from a path too short (measured, Reference behaviour), which is why the failure names both.
  - The HTML5 drag page (`drag.html`) opens in a window of its own (`open_drag_page`, tests/common/mod.rs), `drag-on` with Tauri's handling as it is by default or `drag-off` with it off, so the main window and every other test keep the default. Pinned by `an_os_html5_drag_that_never_reached_the_page_is_not_delivered` (tests/os_input.rs): with the handling off the drop arrives and is counted, a cancelled `dragstart` is no drag, with it on the drag is not delivered (exit 9, with the counts and both causes named), and a drag out of the window with it on is reported, exit 0. `a_drag_out_of_the_window_through_the_os_opens_a_window_where_it_was_dropped` checks that a pointer drag reports no HTML5 events. Reddened 2026-10-22: building `drag-on` with the handling off, and `drag-off` with it on, each turned it red at its own assertion; for the delivery check, never failing, failing a drop outside the page too, ignoring a cancelled `dragstart`, and reporting counts with no HTML5 drag each turned its own assertion red. Not reddened: reading without waiting for `dragend`, because it had always arrived. The test places the two drag pages apart: they are the same size, and at the same place `window activate` could not tell them apart and brought the main window instead (exit 6 on the drag, 2 of 2, 2026-10-22).

### Declared

- **`capabilities` says, per input command, which routes exist, which is the default, and whether each takes focus** (#1 story 42; the declarations are [Platform support](platform-support.md)'s): the os route `takes_focus: true` and `needs` the app in front; for `window`, per action, `activate` takes focus, `move` and `resize` do not ([Placing the app's windows](placing-windows.md)). Pinned by `capabilities_say_which_routes_take_focus` (tests/os_input.rs).
- The tests that bring a fixture to the front run only where `quiet_machine` lets them ([Testing against the fixture](testing-against-the-fixture.md)); `os_input_reaches_the_page_as_a_hand_would_send_it` holds its cases in one test, because two fixtures taking the foreground at once would fail each other.

## Reference behaviour

- **Activation (2026-10-07, Windows 11, terminal Orca in front):** all three ways tried (plain, `AttachThreadInput`, synthetic Alt) brought the fixture to the front 11 times out of 11, both with the user idle and while the user was moving the mouse. The foreground window belonged to an Orca process that is not an ancestor of pokit. *Unverified:* Orca may call `AllowSetForegroundWindow(ASFW_ANY)`, which would let any process take the foreground. **The live foreground lock time-out that day is not known** (#61): on 2026-10-08 and 2026-10-23 it was 2147483647 ms (`SPI_GETFOREGROUNDLOCKTIMEOUT`) against the registry's 200000, so "idle for longer than the time-out" most likely never held.
- **Activation with the plain call refused (2026-10-23, #61):** the fixture launched behind another fixture brought to the front, then `window activate`, 10 runs a condition; the fixture's process held the foreground afterwards in every run (read from the system).

  | Condition | Live lock time-out | Plain | `AttachInput` | In front |
  |---|---|---|---|---|
  | a key tapped by another process just before | 200000 ms | 5 | 5 | 10 of 10 |
  | no input for 6 s | 5000 ms (expired) | 9 | 1 | 10 of 10 |
  | a key tapped by another process just before | 2147483647 ms (the live value) | 5 | 5 | 10 of 10 |

  So the plain `SetForegroundWindow` is refused about half the time while the lock holds, and `AttachThreadInput` brought the window forward each of the 11 times it was needed. The time-out was set with `SPI_SETFOREGROUNDLOCKTIMEOUT` for the runs and put back to 2147483647 afterwards (read back).
- **`document.hasFocus()` does not tell which of the app's pages takes the input (2026-10-07, 2026-10-22, #95).** With the fixture's second window brought in front while the app was in front, the main page reported `false` and the second `true`; with the app's own dialog in front, `false`; with the app behind, a page reported `true` after a CDP focus. But with another app in front and the second window then brought forward (by the app opening it, or by `window activate` on it), the main page and the second both reported `true` (3 of 3 each), so the guard asks which window is in front instead.
- **What OS `type` and `key` raise as `keydown` (2026-10-08, #73, 5 runs each, fixture in front):** `type abc` 3 (`a`, `b`, `c`); `type A` 1 (`A`, no Shift: it is Unicode input); `type 한` 1 (`한`); `type 😀` 2, one per UTF-16 unit, each with `key` empty; `type` of a, newline, b 3 (`a`, `Enter`, `b`); `key KeyA` 1; `key Ctrl+KeyK` 2 (`Control`, `k`). Each was trusted, and the same number in every run. Two of the `Ctrl+KeyK` runs were refused with exit 6, the fixture no longer in front; six more in a row kept it in front, so another window is the likely cause, not found.
- **Their `code` (probe 2026-10-12, #78):** every character `type` sends as Unicode arrives with `code ""` (`keyCode` 231), its `key` the character, or empty for each half of an emoji; a newline arrives as `Enter`/`Enter`. `key Ctrl+KeyK` arrived as `Control`/`ControlLeft`, `k`/`KeyK`, and `Shift+Digit7` as `Shift`/`ShiftLeft`, `&`/`Digit7`.
- **Two clicks closer together than the double-click time (500 ms on the measuring machine) are one sequence**, as a hand's are: a single click followed at once by `--double` made a triple, and the page's last event was `click` (the test waits `window::double_click_time()` plus 200 ms between them).
- **A wheel sent in the same `SendInput` call as the move that brings the cursor into the window is often dispatched twice by WebView2 (2026-10-08, #64).** The page received a cancelable `wheel` before the `mouseover` and `mousemove` of the cursor coming in, then the same notch again, not cancelable, right after them (once both carried the same `timeStamp`). With the cursor put off the window before each notch: one call, 14 of 20 notches and 7 of 10 arrived twice; move and wheel in two calls, 0 of 30, whether 0, 50 or 300 ms apart, and the page saw `mouseover` before the `wheel` every time. With the cursor already over the page, one call, 0 of 20. Seen in #47 as one notch scrolling 150 against the CDP notch's 100. Why WebView2 sends it twice was not found; the order of the move and the wheel reaching the page is what decides it. `click` and `drag` send the move in the same call as the button, and that is not affected (2026-10-08, #69): with the cursor put off the window first, 20 of 20 OS clicks reached the page as `mouseover`, `pointerdown`, `mousedown`, `mouseup`, `click`, each once, and 10 of 10 drag starts had their `mouseover` before one `pointerdown`; with the cursor already over the page, 10 clicks and 5 drag starts, the same.
- **One wheel notch scrolled 100 CSS pixels on either route, but a burst does not add up the same (2026-10-07, the measuring machine at 150% and Windows' default three lines per notch, scroller 150 px tall).** Three OS notches sent together reached the page as one `wheel` event of `deltaY` 300, and the scroller moved 150, its own height; five moved 150 too. Three CDP notches (one event of 300) moved 300. Chromium seems to limit what one coalesced OS wheel event scrolls to the scroller's height.
- **A page that captures the pointer still gets the drop outside its window through the OS (2026-10-07, WebView2 154).** The fixture's `#drag-me` calls `setPointerCapture` on `pointerdown`; with the cursor moved 150 CSS pixels past the window's right edge and released there, the page got `pointerup` with `clientX` past `innerWidth` and `screenX` 1008, 19 `pointermove`s before it, and opened its window at the drop. A drag out of the window ends in `dragend` at the release's screen position with either Tauri setting, which is all a page needs to open a window where a block was dropped.
- **Through the OS the drag is a real system drag (`DoDragDrop`), and the window's drop target decides what the page sees.** With Tauri's handling on (`dragDropEnabled`, the default), wry turns WebView2's external drop off (`SetAllowExternalDrop(false)`), revokes WebView2's drop target on the window and its child windows and registers its own (`RevokeDragDrop`, `RegisterDragDrop`), and that one returns at once for anything that is not a file (no `CF_HDROP`) (wry 0.57, `webview2/drag_drop.rs`). The page then gets `dragstart` and `dragend` with `dropEffect` `none`, and nothing in between.
- **What an HTML5 drag raises on each route (2026-10-22, #52, WebView2 155.0.4283.62, Tauri 2 with wry 0.57, DPI 144, 5 runs a cell, each the same in every run).** The fixture's drag page, `#h5-drag` to `#h5-drop` in the page, and to 150 CSS pixels past the window's right edge out of it:

  | Tauri handling | Route | Drop in the page | Drag out of the window |
  |---|---|---|---|
  | on (default) | CDP | `dragstart`, 8 `drag`, 3 `dragenter`, 8 `dragover`, 2 `dragleave`, `drop`, `dragend` (`move`) | refused before sending (exit 5) |
  | on (default) | OS | `dragstart`, `dragend` (`none`); no `drag`, `dragover` or `drop` | `dragstart`, `dragend` at the drop's screen position; no `drag` |
  | off | CDP | as with it on | refused (exit 5) |
  | off | OS | `dragstart`, 13–16 `drag` and `dragover`, 2–3 `dragenter`, `drop`, `dragend` | 9–11 `drag`, 8–10 `dragover`, 2 `dragleave`, `dragend` at the drop's screen position (`none`) |

  A short OS path does not drop either, with the handling off: at `--steps 2` (3 runs) the page got `dragstart`, 2 `drag`, a `dragenter` and a `dragleave`, then `dragend` with `none`; at `--steps 1` (1 run of 3 recorded, the other two recorded nothing) `dragstart` and `dragend` only, the same as the handling on gives at 10. Every event was trusted, each drag preceded by `pointerdown`, `mousedown` and a `pointercancel` when the drag started.

## Cross-cutting invariants

- [Page pixels on the screen](page-pixels-on-the-screen.md) — `os_input::to_screen` and `at_page_point` place a page point on the screen; `os_input::drag` places each later point of a path from the first by the same ratio.
- [Capabilities match behaviour](capabilities-match-behaviour.md) — the os route declares `takes_focus: true`, `needs` the app in front, `ime_composition: false`, `leaves_the_page: true` and `html5_drag`; `window activate` declares `takes_focus: true`.

## Blast radius

- [Placing the app's windows](placing-windows.md) — the guard and `window activate` take the page's window from `window::page_window`; a change to how a window is matched to its page changes which window the guard demands in front and which one `activate` raises.
- [Capturing a window with its native UI](capturing-a-window.md) — `capture --window` shares `State::current_page_window`, `PAGE_ANSWER` and the main-window fallback (`os_input::main_window`) with `window activate`; a change to either the timeout or the fallback changes what both report as `window`.
- [Reaching an app's native UI](reaching-native-ui.md) — `window activate` clears `foreground_at_click`, which the native give-back reads; and the guard's rule that the app's own dialog in front takes the input is what keeps OS input from landing in a dialog `native` opened.
- [Sending input over CDP](sending-input-over-cdp.md) — `type` and `key` on this route use its keydown listener and `check_delivery`; a change to how keydowns are noted or matched by `code` changes what this route reports as delivered. The drag path, `DRAG_STEP` and the drag rules in `drag_cmd` are shared by both routes.
- [Measuring the page](measuring-the-page.md) — `hold --compare` reports `os_minus_cdp`, which assumes the OS hold sends its key-downs on the same schedule as the CDP one, and includes this route's blocking hand-off.
- [Platform support](platform-support.md) — the route declarations in `support::routes` say what this route does (`takes_focus`, `needs`, `leaves_the_page`, `html5_drag`); a change to the guard, focus or drag behaviour here makes them false.
- [Starting the session process](starting-the-session-process.md) — `State::shutdown` releases `keys_down`; a session path that ends without it leaves a key or the left button down for the user.

## Known holes / open

- No OS route on macOS here; `--route os` on macOS is [Sending input on macOS](sending-input-on-macos.md)'s. Tracked: #113.
- Nothing bounds `type`'s text, `wheel --notches` or `hold --count`: each builds its `SendInput` input (or key-down schedule) in full, limited only by the command's time limit.
- Not tested: the release of held keys at the end of a hold, the one-at-a-time lock (`os_input`), releasing the button when the session ends mid-drag, a `--to` in another page, and a window owned by the page's window counting as in front for `window activate`.
- A drag path onto a monitor with another scale uses one ratio for the whole path and would land off by the ratio between the scales. Not measured.
- What raises the live foreground lock time-out above the registry's value was not found (#61); finding it needs a fresh sign-in, which is the user's to do.
- Why WebView2 dispatches a wheel twice when it arrives in the same call as the cursor's entry was not found, nor why only the wheel is dispatched ahead of the move (#64, #69).
- A fast spin of a real wheel was not measured; it may coalesce the way three sent notches did.
- What took the fixture out of the front in two `Ctrl+KeyK` runs (2026-10-08, #73) was not found.
