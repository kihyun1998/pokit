# Sending OS input

How `window activate` brings the launched app to the front, and how `key`, `type`, `click`, `hold`, `wheel` and `drag` reach it on `--route os` through `SendInput` on Windows. Code: `os_input::activate`, `os_input::drag`, `os_input::drag_path`, `os_input::key`, `os_input::text`, `os_input::click`, `os_input::chord_strokes`, `os_input::us_scan`, `os_input::to_screen` (os_input.rs), `State::os_*_cmd`, `State::refuse_unless_front` (session/os_input.rs), `State::window_activate_cmd` (session/native.rs), `support::routes`.

## Design model

- **OS input goes ahead only when it would reach the page pokit is on, and is refused otherwise (exit 6, nothing sent, nothing scrolled or focused).** #1 story 38. Three checks:
  - before anything happens on the page, the app must own the foreground window and the current page must have the input focus (`document.hasFocus()`), which it does not when another of the app's windows or one of its own dialogs is in front;
  - `os_input` checks the foreground window again right before `SendInput`;
  - a click is placed in the app's foreground window, which must hold a page, and the window found at the point (`WindowFromPoint`) must be that window, so a window covering the page cannot take the click.
- **`window activate` is how the app gets in front, and it takes the user's focus.** It tries `SetForegroundWindow`, then the same call while attached to the foreground window's input queue (`AttachThreadInput`), and refuses with exit 6 when Windows keeps the app back. The result names which way worked. **Maintainer's call (2026-10-06, #5):** an explicit command in pokit, not a test-only workaround and not a person bringing the app forward. **Maintainer's call (2026-10-07):** plain, then `AttachThreadInput`, never the synthetic Alt key tao uses. The Alt key would put a keystroke into the user's app, which can open its menu bar.
- **A chord is pressed as a hand presses it, by physical key.** Modifiers go down, then the key goes down and up, then the modifiers come up in reverse (`chord_strokes`), all in one `SendInput` call so that no other input interleaves. A page counting keydowns sees Control as a key of its own here, unlike on the CDP route ([[sending-input-over-cdp]]).
  - Each key is sent as its scan code on a US keyboard (`us_scan`, `KEYEVENTF_SCANCODE`), the same physical key whatever the user's layout: the page's `KeyboardEvent.code` comes from the scan code, and with no scan code `Ctrl+KeyK` arrived as `code ""`.
  - What the key types then follows the user's layout and input method, as a real keyboard's would: on AZERTY `KeyA` types `q`, and with a Korean IME in Hangul mode a letter key arrives as `Process`. The result therefore reports the key's `code`, not a `key` value.
  - The first version sent virtual keys, which `MapVirtualKeyW` mapped through the session thread's layout, and so pressed a different physical key on a non-US layout (independent review, 2026-10-07).
  - If Windows takes only part of a chord, every modifier already pressed is released again, so none is left down for the user.
- **`type` sends each character as Unicode (`KEYEVENTF_UNICODE`), and a newline as the Enter key.** There is no IME composition on this route; `capabilities` says so (`ime_composition: false`), and the CDP route composes ([[sending-input-over-cdp]]).
- **A click lands at the element's centre in physical pixels.** The page's top-left corner is the client origin of the WebView2 render widget (`Chrome_RenderWidgetHostHWND`) inside the app's foreground window. The element's CSS position is multiplied by the page's `devicePixelRatio` and added to that corner (`to_screen`). This is worked out with the thread switched to per-monitor DPI awareness, because the session is otherwise unaware and Windows would scale the coordinates it returns. The mouse moves there and clicks, so the user's cursor moves too.
- **`hold --route os` presses the modifiers, sends the key-downs on schedule without key-ups, then releases the key and the modifiers.** Windows marks every key-down after the first as a repeat by itself (the key is already down), so the page sees `repeat: true` from the second on. The key and modifiers are released whatever happens, without the foreground check: a key left down would stay down for the user, in whichever app is in front by then.
  - The keys down are also kept on the session (`keys_down`) and released when it ends, so `close`, the idle timeout or the app exiting in the middle of a hold leaves none down.
  - OS input commands run one at a time (`State::os_input`, `Request::sends_os_input`): a `type` arriving while a hold has Control down would otherwise type shortcuts. CDP commands are not held back.
  - If the app leaves the front mid-hold, the error says how many key-downs went through.
  - Neither the release at the end nor the one-at-a-time lock has a test; both were read, not reddened.
- **`wheel` turns the wheel over an element, a point, or the middle of the page, without scrolling anything into view.** It aims at the middle of the part of an element that is in view, refuses an element wholly out of view and a point outside the viewport (exit 5), because the wheel turns where the cursor is. On CDP one notch is a `mouseWheel` of 100 CSS pixels (`PIXELS_PER_NOTCH`), what one OS notch scrolled on this machine; on the OS it is one `MOUSEEVENTF_WHEEL` of 120 per notch, sent in a `SendInput` call of their own after the cursor's move, and how far that scrolls is Windows' and Chromium's business (the user's lines-per-notch setting, display scaling). The test checks that both routes scroll alike, not a number of pixels.
- **`hold --compare` runs the same keys on CDP and then through the OS, each inside its own measurement,** and reports each route's latency (see [[measuring-the-page]]) and `os_minus_cdp`, the native layer's share, which also holds pokit's hand-off to a blocking thread for each OS key. It needs the app in front and refuses before either route runs.
- **`capabilities` says, per input command, which routes exist, which is the default, and whether each takes focus** (#1 story 42). For `window` it says so per action: `activate` takes focus, `move` and `resize` do not ([[placing-windows]]).
- **`drag` holds the left button along a path of page points, and through the OS the path may leave the window.** The path is the element's centre, any `--via` points, then the drop (an element's centre or `--to-x`/`--to-y`), with `--steps` evenly spaced moves on each straight part, about a frame (16 ms) apart (`drag_path`, `DRAG_STEP`). #1 story 17.
  - Through the OS only the first point is checked to be the page; the rest go wherever they lead on the screen, which is the point of the route. The button is released at the end whatever goes wrong, and kept on the session (`keys_down`, as `LEFT_BUTTON`) so that a session ending mid-drag releases it.
  - On CDP the page only sees points inside it, so a path that leaves the viewport is refused before anything is sent (exit 5), naming `--route os`. CDP sends `mousePressed`, `mouseMoved` with the button held, then `mouseReleased`, and releases the button even when a move fails.
  - `capabilities` says which route leaves the page (`leaves_the_page`).
  - The element dragged is scrolled into view only if it is not in view already (`block: 'nearest'`), so points taken from the page before stay where they were. A `--to` element is not scrolled: out of view it is refused (exit 5), because through the OS its centre would be a point outside the window, where the button would be let go over whatever is there.
  - A `--to` element in another page than the one dragged from is refused (exit 2): crossing into another window is a drop at a point with `--route os`.
  - A drag of over 10 s of moves (`DRAG_LONGEST`) is refused (exit 2), so it ends inside a command's time limit and does not keep moving the cursor after the caller gave up.
  - One scale is used for the whole path, the page's `devicePixelRatio`; a path onto a monitor with another scale lands off by the ratio between them. Not measured.
  - Through the OS the button is released by a guard dropped at the end of the drag, so a panic releases it too.
- **HTML5 drag and drop (`draggable`, `dragstart`, `drop`) is not covered.** CDP mouse events do not start it without `Input.setInterceptDrags` or `Input.dispatchDragEvent`, and Tauri turns its own file drop handling on by default, which on Windows may keep HTML5 drag and drop from working inside WebView2. Neither was measured; the fixture's draggable uses pointer events.

## Measured

- **Activation (2026-10-07, Windows 11, terminal Orca in front):** all three ways tried (plain, `AttachThreadInput`, synthetic Alt) brought the fixture to the front 11 times out of 11. That held both with the user idle for longer than the foreground lock time-out and while the user was moving the mouse. The foreground window belonged to an Orca process that is not an ancestor of pokit. *Unverified:* Orca may call `AllowSetForegroundWindow(ASFW_ANY)`, which would let any process take the foreground. So the conditions in which the plain call fails were not produced here.
- **At 150% scaling (DPI 144, device pixel ratio 1.5):** an OS click on `#target` produced `click`, a double click `dblclick`, and a right click `contextmenu`.
- **A wheel sent in the same `SendInput` call as the move that brings the cursor into the window is often dispatched twice (2026-10-08, #64).** The page received a cancelable `wheel` before the `mouseover` and `mousemove` of the cursor coming in, then the same notch again, not cancelable, right after them (once both carried the same `timeStamp`). With the cursor put off the window before each notch: one call, 14 of 20 notches and 7 of 10 arrived twice; move and wheel in two calls, 0 of 30, whether 0, 50 or 300 ms apart, and the page saw `mouseover` before the `wheel` every time. With the cursor already over the page, one call, 0 of 20. Seen in #47 as one notch scrolling 150 against the CDP notch's 100. Why WebView2 sends it twice was not found; the order of the move and the wheel reaching the page is what decides it. `click` and `drag` still send the move in the same call as the button; that was not measured.
- **One wheel notch scrolled 100 CSS pixels on either route, but a burst does not add up the same (2026-10-07, this machine at 150% and Windows' default three lines per notch, scroller 150 px tall).** Three OS notches sent together reached the page as one `wheel` event of `deltaY` 300, and the scroller moved 150, its own height; five moved 150 too. Three CDP notches (one event of 300) moved 300. Chromium seems to limit what one coalesced OS wheel event scrolls to the scroller's height. A fast spin of a real wheel was not measured; it may coalesce the same way.
- **The native layer's share of a key's latency is about 1.2–1.3 ms (2026-10-07).** In three runs of `hold KeyA --count 20 --compare`, the send-to-handling p50 was 0.6–0.8 ms on CDP and 1.9–2.0 ms through the OS; OS minus CDP was 1.2–1.3 ms at p50 and 1.5–2.5 ms at p95, against a clock uncertainty of 0.10–0.18 ms.
- **Two clicks closer together than the double-click time (500 ms here) are one sequence**, as a hand's are: a single click followed at once by `--double` made a triple, and the page's last event was `click`.
- **`document.hasFocus()` tells which of the app's pages takes the input when the app is in front (2026-10-07).** With the fixture's second window in front, the main page reported `false` and the second `true`; with the app's own dialog in front, `false`. With the app behind, a page reported `true` after a CDP focus, so the foreground check is still needed.
- **A page that captures the pointer still gets the drop outside its window through the OS (2026-10-07, WebView2 154).** The fixture's `#drag-me` calls `setPointerCapture` on `pointerdown`; with the cursor moved 150 CSS pixels past the window's right edge and released there, the page got `pointerup` with `clientX` past `innerWidth` and `screenX` 1008, 19 `pointermove`s before it, and opened its window at the drop.
- **A left button left down stays down for the user.** Reddening the drag by dropping its button release left the system's left button down after the test (`GetAsyncKeyState`) until it was released by hand.

## Testing

- `os_input_reaches_the_page_as_a_hand_would_send_it` brings its fixture to the front. Its cases run in one test, because two fixtures taking the foreground at once would fail each other.
- The guard test passes while either foreground check holds, so a mutation has to remove both to turn it red (done 2026-10-07). Removing the page-focus check turns the second-window case red; moving the click's check after scrolling turns the scroll assertion red.
- The second-window and dialog cases run in the same test as the rest, after the clicks.
- `a_drag_out_of_the_window_through_the_os_opens_a_window_where_it_was_dropped` (tests/os_input.rs) and `a_drag_on_cdp_moves_the_pointer_within_the_page_and_refuses_to_leave_it` (tests/fixture.rs). Reddened 2026-10-07: not refusing a CDP path that leaves the page, ignoring `--steps`, not releasing the button through the OS, not refusing an OS drag before scrolling, not refusing a `--to` element out of view, and not capping the drag's length each turned one red. Without the command line's `--to` requirement the session's own refusal still gives exit 2. No test: releasing the button when the session ends, a `--to` in another page. Before each OS drag the fixture's window is moved to (40, 40), so that the drop 150 CSS pixels past its right edge is on the screen.
- `hold_wheel_and_the_comparison_run_on_both_routes` puts the real cursor off the window before 4 OS notches (`window::put_cursor`), and each must be one wheel event that scrolls as far as the CDP notch. Four, because one call doubled about 7 notches in 10. Reddened 2026-10-08: sending the move and the wheel in one call turned it red in 2 runs of 2.
