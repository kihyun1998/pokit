# Sending input over CDP

How `click`, `type` and `key` reach the page on Windows, and what masking covers. Code: `session::commands::send_key`, `session::commands::send_ime_key`, `session::commands::check_delivery`, `COUNT_KEYDOWNS`, `hangul`, `State::click_cmd` (session/commands.rs), `State::focus_for_input`, `State::guard_target`, `chord`, `redact`.

- **`Input.dispatchKeyEvent` replies only after the renderer acknowledges the event.** It also focuses the target widget first. If the event never reaches an input observer, the reply comes at once and still says success. Source: `content/browser/devtools/protocol/input_handler.cc` (Chromium main, 2026-09-25), lines 776–797 and 835–848. A reply is therefore not proof of delivery, which is why `type` and `key` count the keydowns the page receives (below); see also the readiness trap in [[launching-a-test-instance]].
- **`type` and `key` count the trusted keydowns the page receives, and fail with exit 9 (`not_delivered`) when fewer arrive than were sent** (#7). A capture listener on `window` counts them from just before the first key until just after the last, and is removed then (`COUNT_KEYDOWNS`, `check_delivery`). The result carries `keydowns_sent`, `keydowns_received` and `delivery`; the error, how many went `missing`.
  - Counted: every key-down sent, modifiers and Hangul `Process` keys included. Text sent with `Input.insertText` raises no keydown and is not checked.
  - The count cannot tell, and says `delivery: "unverified: …"` without failing, when the focus is in a frame (its own window takes the keys) or the page's document changed during the command (the counter went with it).
  - A page listener added earlier that calls `stopImmediatePropagation` on keydown in the capture phase on `window` hides the keys from the count, and the command then fails although they arrived. The error says so. **Maintainer's call (2026-10-08, #7):** a listener per command, as here. They were shown, besides it, a listener every page gets at document start (`Page.addScriptToEvaluateOnNewDocument`), which a page cannot hide keys from but which stays in every page of the session and needs this one for pages already loaded, and counting without failing. They chose this one, and CDP only: `--route os` is not counted.
  - Round trips: with `--into` the listener goes in with the focus call, so the count costs one more call; without `--into`, two.
  - No way was found to make a key really not reach the page: with the webview hidden (`IsVisible` false through the fixture's `hide_webview_for`), a CDP key still reached it and `visibilityState` was `hidden` (2026-10-08). The test swallows keys with a page listener instead.
- **Typed text goes key by key where the US layout has the character** (`keyDown` with `text`, then `keyUp`), through a 2-Set IME composition where it is Hangul, and through `Input.insertText` otherwise (other scripts, emoji). A newline, `\r` or `\r\n`, is one Enter press.
- **Hangul is composed key by key, as a 2-Set (Dubeolsik) IME composes it.** Each syllable is split into the jamo keys a person presses (`hangul::keys_for`), and `hangul::Composer` runs them through the 2-Set rules. Compound vowels and finals build up over two keys. A final consonant moves to the next syllable when a vowel follows: typing 가나 shows 간 before it becomes 가 + 나. A compound final splits. A lone jamo in the text (ㅋㅋ) is composed on its own: whatever is being composed is committed before it and after it, so it never joins its neighbours, though a real IME would join 가ㄴ into 간; a compound consonant jamo (ㄳ) has no key of its own and is inserted as text. When a CDP call fails mid-composition, the composition is cancelled before the error returns. For each key pokit sends:
  - a `Process` key-down (virtual key 229, with the physical key's `code`);
  - `Input.insertText` for any syllable the key commits;
  - `Input.imeSetComposition` for the composition left;
  - a key-up carrying the jamo.

  *Derivation, not measured against a real IME:* the key-up's `key` and virtual key. An OS-input comparison in #5 can check them.
- **IME composition needs no focus.** `Input.imeSetComposition` and `Input.insertText` go straight to the renderer's IME handling (`ImeSetComposition` / `ImeCommitText` on the widget input handler, `content/browser/devtools/protocol/input_handler.cc` 1281–1358, Chromium main, read 2026-10-06), not through the OS. Measured 2026-10-06 on the fixture, typing 한글 gave:
  - `compositionstart`, `compositionupdate` ㅎ 하 한, `compositionend` 한, then the same for ㄱ 그 글;
  - a `Process` key-down per key;
  - the value 한글, with the foreground window unchanged.

  Typing 가나 gave `compositionupdate` ㄱ 가 간, `compositionend` 가, then 나.

  Blink sends one more `compositionupdate` with the committed text just before each `compositionend`.
- **Chords use physical key names.** `key` and the virtual key code come from a US layout table. Modifier bits are Alt 1, Ctrl 2, Meta 4, Shift 8. `Ctrl+Equal` gives `key "=", code "Equal", vk 187, modifiers 2`, the same values penterm's held-size-key script sends. Modifiers are pressed as keys of their own, as a keyboard sends them: Control, Alt, Shift, Meta down in that order, each carrying the modifiers held so far, then the key down and up, then the modifiers up in reverse, each without its own (`KeyPress::modifier_events`). Measured 2026-10-07: one `Ctrl+K` on a real keyboard gave `keydown Control`, `keydown k`, `keyup k`, `keyup Control`, the same as `--route os` and, since this change, CDP. **Maintainer's call (2026-10-07, #5):** modifiers as keys on CDP too, with `measure` leaving modifier key-downs out of the keys it counts. The alternatives shown were keeping modifiers as flags on the main key, the way penterm's held-size-key script sends them, and counting modifier key-downs as handled keys.
  - A Hangul key that needs Shift (ㅃ, ㅆ) still carries Shift as a flag, not as a key of its own (`send_ime_key`): what a real IME sends around it has not been measured.
  - If a CDP call fails in the middle of a `hold`, the key and the modifiers are released before the error returns.
- **The focus guard is checked before pokit changes anything on the page.** Without `--into`, the focused element must lie inside `--require-focus`. With `--into`, the target must lie inside it; only then is it focused, and the focus is checked again once it lands. *Derivation (#3), not a maintainer's call:* the guard exists so that input cannot land in the wrong place, and with `--into` the place is the target.
- **CDP keys reach the page whether or not the app is in front.** In the fixture, `Ctrl+KeyK` was recorded by the page both while the app was behind another window and after it was clicked. All 10 keys of a `hold` also reached the page with its window fully covered, and with it minimized (2026-10-06); Tauri keeps the webview visible when minimized ([[measuring-the-page]]).
- **CDP keys do not raise WebView2's `AcceleratorKeyPressed`; OS keys do.** The fixture logged no event for CDP keys in four tries in #3, with and without `nativeVirtualKeyCode`; Chromium skips the browser's unhandled-key path for an event without it (`input_handler.cc` 1272–1275). The control has now run (2026-10-07): `key Ctrl+KeyK --route os` raised it for Control and K, down and up (`vk=17`, `vk=75`), and a CDP `Ctrl+KeyK` right after raised nothing. So an app's handling of `AcceleratorKeyPressed` is reached only on `--route os` ([[sending-os-input]]).
- **`snapshot` turns the accessibility domain on and off around the tree.** `getFullAXTree` alone leaves Blink keeping a full accessibility tree up to date for the rest of the session (`inspector_accessibility_agent.cc` 242, 687–693). Its `disable` only takes effect after an `enable`.
- **Masking covers text, not pixels or variants.** A secret is replaced wherever its exact text appears in output, logs and the run record. A failed `type --secret` leaves no screenshot. A truncated or encoded form of a secret is not caught, and neither is the secret in a later screenshot of a visible text field.
