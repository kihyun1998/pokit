# Sending input over CDP

## What it is

How `click`, `type`, `key`, `drag` and `wheel` reach the page on Windows through CDP's `Input` domain, the default route: the focus guard checked before anything changes, the check that each key-down sent reached the page as a trusted `keydown`, chords written with physical key names, and the WebView2 menu a right-click opens. Korean text is composed as an IME would, in [Typing Korean through the IME](typing-korean-through-ime.md); what is masked when the text is secret is [Masking secrets](masking-secrets.md). The chord table (`chord.rs`) is also what the OS route ([Sending OS input](sending-os-input.md)) and the plugin route ([Sending input on macOS](sending-input-on-macos.md)) press keys from; its rules are here.

## Governing decisions

- [ADR-0002](../adr/0002-hand-written-cdp-client.md): every input event is a CDP call pokit chose to send; nothing else reaches the app.
- [ADR-0001](../adr/0001-commands-talk-to-a-session.md) governs the session the input commands are requests to, including the per-session turn `type` and `key` take.

## Design model

The rules come from maintainer's calls on issues (#5, #7, #78, #81, #120), one derivation (#3), and reading the source.

- **A CDP reply is not proof of delivery.** `Input.dispatchKeyEvent` replies after the renderer acknowledges the event, but at once and still with success if the event never reaches an input observer (see Reference behaviour). So `type` and `key` count the keydowns the page receives (below), and input waits for the page to be ready first ([The app's pages](the-apps-pages.md), and the launch-time trap in [Launching a test instance](launching-a-test-instance.md)).
- **`type` and `key` check that a trusted keydown reached the page for each key-down sent, and fail with exit 9 (`not_delivered`) when some never did** (#7). A capture listener on `window` notes the `code` of each from just before the first key until just after the last, and is removed then (`NOTE_KEYDOWNS`, `check_delivery`, `delivery_js`). The result carries `keydowns_sent`, `keydowns_received` (sent key-downs that arrived), `keydowns_unexpected` and `delivery`; the error, how many went `missing` (`delivery_verdict`). The same check serves the OS route (with `KEYS_SETTLE_MS`) and the plugin route (with `PLUGIN_KEYS_SETTLE_MS`); on CDP it waits for nothing beyond the keys already acknowledged (settle 0).
  - Checked: every key-down sent, modifiers and Hangul `Process` keys included. Text sent with `Input.insertText` raises no keydown and is not checked (`Typed::downs` holds no entry for it).
  - **Keydowns are matched to what was sent by `code`, each standing for one key-down, in any order (`tally`)** (#78). Until then they were only counted, so a key someone else typed during the command made up for a missing one and the command said `confirmed` (seen 2026-10-08: the page swallowed `b`, and an OS `type abc` returned exit 0). Keydowns pokit did not send make the result `delivery: "unverified: …"` without failing, with how many in `keydowns_unexpected`, and are added to the error when keys are also missing. Their codes are not reported: they are someone's keystrokes. The read waits until every sent key-down is matched, not until the count reaches the number sent, which a foreign key would end early (`delivery_js`). **Maintainer's call (2026-10-12, #78):** match what arrived, of the three ways the issue laid out; the others were recording the limit and changing nothing, and counting only keydowns whose `timeStamp` falls in the send window, which still counts a key typed inside it. Pinned by `tally_counts_each_sent_key_down_once_whatever_the_order` and `tally_leaves_keydowns_nobody_sent_over_and_lets_none_stand_in_for_a_missing_one` (commands.rs unit tests).
  - Matched on `code`, not `key`, because `code` is the one both routes keep stable ([Sending OS input](sending-os-input.md)): the page gets exactly the `key` and `code` CDP sends (probe 2026-10-12: `type "Ab😀\n한"` gave `Shift`/`ShiftLeft`, `A`/`KeyA`, `b`/`KeyB`, `Enter`/`Enter`, then `Process` with `KeyG`, `KeyK`, `KeyS`), while on `--route os` `key` follows the layout and input method.
  - A key someone else types with the same `code` as one that went missing still stands in for it: nothing on the event tells the two apart.
  - Pinned by `keys_someone_else_types_neither_stand_in_for_a_missing_one_nor_confirm_delivery` (tests/fixture.rs), which types `abc` with `b` swallowed and then with nothing swallowed, while another `hold Backquote` puts a trusted keydown on the page every 5 ms. Reddened 2026-10-12: counting instead of matching codes (`tally`), and saying `confirmed` despite unexpected keydowns, each turned it red. Also `type_and_key_report_the_keydowns_the_page_received` and `keydowns_the_page_never_saw_fail_with_how_many_went_missing` (tests/fixture.rs).
  - The count cannot tell, and says `delivery: "unverified: …"` without failing, when the focus is in a frame (its own window takes the keys), when the page's document changed during the command (the counter went with it), or when the page could not be read afterwards (`delivery_verdict`).
  - A page listener added earlier that calls `stopImmediatePropagation` on keydown in the capture phase on `window` hides the keys from the count, and the command then fails although they arrived. The error says so. **Maintainer's call (2026-10-08, #7):** a listener per command, as here. They were shown, besides it, a listener every page gets at document start (`Page.addScriptToEvaluateOnNewDocument`), which a page cannot hide keys from but which stays in every page of the session and needs this one for pages already loaded, and counting without failing. They chose this one, and CDP only at the time; `--route os` is counted since #73 ([Sending OS input](sending-os-input.md)).
  - **`type` and `key` run one at a time in a session, on either route** (`State::keydowns`, `Request::checks_keydowns`, #81). The page has one slot for the listener (`window.__pokitKeydowns`), and installing it removes the one there, so two at once took each other's: one failed with exit 9 though its keys arrived, the other said `unverified: the page changed while the keys were sent` (2 rounds of 10 on 2026-10-12, two 10-character `type`s). An OS `type` or `key` takes this turn before the OS input one (`State::os_input`), and nothing takes them the other way round (`State::handle`). Other commands, `hold` included, are not held back, so a `hold` still types beside a `type` (the #78 tests rely on it). **Maintainer's call (2026-10-12, #81):** one at a time. They were shown, besides it, a listener per command, which leaves two overlapping commands always `unverified` with their keys interleaved in the field, and recording the limit without a fix. Pinned by `type_and_key_commands_sent_together_each_confirm_their_own_keys` (tests/fixture.rs), which starts two 40-character `type`s and a `Ctrl+Shift+KeyK` together, behind a barrier, for 10 rounds, and expects every one `confirmed` with all its keys. Reddened 2026-10-12: without the turn, and with the turn for `type` only, each red 3 runs of 3.
  - Round trips: with `--into` the listener goes in with the focus call, so the count costs one more call; without `--into`, two (`State::focus_then`, `check_delivery`).
  - The tests swallow keys with a page listener, because no way was found to make a key really not reach the page (see Reference behaviour, 2026-10-08).
- **Typed text goes key by key where the US layout has the character** (`chord::key_for_char`; `keyDown` with `text`, then `keyUp`), through a 2-Set IME composition where it is Hangul ([Typing Korean through the IME](typing-korean-through-ime.md)), and through `Input.insertText` otherwise (other scripts, emoji) (`type_text`). A newline, `\r` or `\r\n`, is one Enter press (`State::type_cmd`). The result counts `key_events`, `inserted_chars` and `composed_chars`.
- **Chords use physical key names.** `key` and the virtual key code come from a US layout table (`PRINTABLE`, `NAMED`, `parse_chord`). Modifier bits are Alt 1, Ctrl 2, Meta 4, Shift 8 (`ALT`, `CTRL`, `META`, `SHIFT`). `Ctrl+Equal` gives `key "=", code "Equal", vk 187, modifiers 2`, the same values penterm's held-size-key script sends (pinned by `ctrl_equal_matches_the_values_penterm_sends`, chord.rs). A character given instead of a key name, or an unknown name, is refused by name (`a_character_instead_of_a_key_name_is_refused_with_the_name_to_use`, `an_unknown_key_is_refused_by_name`).
  - Modifiers are pressed as keys of their own, as a keyboard sends them: Control, Alt, Shift, Meta down in that order, each carrying the modifiers held so far, then the key down and up, then the modifiers up in reverse, each without its own (`KeyPress::modifier_events`, `send_key`; pinned by `modifiers_are_pressed_as_keys_in_order_and_released_in_reverse`, chord.rs, and `a_chord_on_cdp_presses_its_modifiers_as_keys_like_a_keyboard`, tests/fixture.rs). Measured 2026-10-07: one `Ctrl+K` on a real keyboard gave `keydown Control`, `keydown k`, `keyup k`, `keyup Control`, the same as `--route os` and, since this change, CDP. **Maintainer's call (2026-10-07, #5):** modifiers as keys on CDP too, with `measure` leaving modifier key-downs out of the keys it counts. The alternatives shown were keeping modifiers as flags on the main key, the way penterm's held-size-key script sends them, and counting modifier key-downs as handled keys.
  - A press that types a character is a `keyDown` with `text`; one with Ctrl, Alt or Meta, or a key that types nothing, is a `rawKeyDown` without it (`KeyPress::down_event`).
- **The focus guard is checked before pokit changes anything on the page.** Without `--into`, the focused element must lie inside `--require-focus` (`State::guard_focus`). With `--into`, the target must lie inside it (`State::guard_target`); only then is it focused, and the focus is checked again once it lands (`State::focus_then`). A refusal is `guard_refused` and says nothing was sent (`focus_verdict`, `target_verdict`). *Derivation (#3), not a maintainer's call:* the guard exists so that input cannot land in the wrong place, and with `--into` the place is the target. Pinned by `input_is_refused_when_focus_is_outside_the_required_target` and `refused_input_leaves_focus_where_it_was` (tests/fixture.rs). `click` on an element checks the current focus, not the element (`State::click_cmd`).
- **A click moves the mouse to the point, then presses and releases** (`State::click_cmd`): once, twice with `clickCount` 1 and 2 for `--double`, the right button for `--right`, and no press for `--hover`. An element is scrolled to the centre of the view first and clicked at its centre; an element with no size is `not_found`. Coordinates are the page's CSS pixels as `getBoundingClientRect` gives them, sent as they are: CDP input converts nothing to the screen. Pinned by `chords_and_mouse_variants_reach_the_page_as_the_page_reports_them` (tests/fixture.rs).
- **A right-click on a page that does not prevent `contextmenu` opens WebView2's own menu, and pokit closes it at once (`menu_closed`).** After a CDP right-click, pokit looks for a topmost tool window of the process listening on the debugging port that was not open before the press (`proc::listening_pid`, `native::browser_menus`), for up to 250 ms (`BROWSER_MENU_WAIT`), posts Escape to it (`native::close_browser_menu`, which waits up to 1 s for it to go), and reports whether one closed (`close_new_browser_menu`). The class is matched only by its `Chrome_WidgetWin_` prefix and the extended style decides, because the class differs between runtimes and a tooltip of the same process is topmost but not a tool window (see Reference behaviour). A menu the app opens after preventing the page's is a `#32768` window of the app's own process ([Reaching native UI](reaching-native-ui.md)) and is never touched; the page's capture listener is not consulted, so the blind spots of the macOS route (#118) do not arise. The port's listener is the browser process for a launched and an attached session alike (#120). Before the click, pokit also notes the other app's window in front (`State::foreground_at_click`), for the native menu code to give the foreground back to. **Maintainer's call (2026-10-26, #120):** close it, as on macOS (#34). Shown with it: leaving it open as a mouse would (it then stays topmost over the user's work, `native` cannot see it), stopping it from opening (no way leaves the page's view unchanged without an app change), and refusing `--right`. Pinned by `a_right_click_closes_the_menu_webview2_opens_and_leaves_the_page_taking_clicks` (tests/fixture.rs): three rounds closed and the next left click landing, then `menu_closed: false` on an element whose page prevents the menu.
- **A drag on CDP stays inside the page.** It presses the left button at the centre of `from` (scrolled into view only if needed), moves along the path through `--via` points in `--steps` moves per leg (`os_input::drag_path`), one move per `DRAG_STEP` (16 ms), and releases where the last move landed, also when a move fails (`State::drag_cmd`). A path that leaves the viewport is refused before anything is sent; so is a drop element on another page, or one not in view. A drag that would take over `DRAG_LONGEST` (10 s) is a usage error. Pinned by `a_drag_on_cdp_moves_the_pointer_within_the_page_and_refuses_to_leave_it` and `a_drag_on_cdp_drops_an_html5_draggable_with_tauris_drag_handling_on` (tests/fixture.rs).
- **The wheel turns `PIXELS_PER_NOTCH` (100) CSS pixels per notch** (`State::wheel_cmd`), over the visible middle of an element, a point, or the middle of the page, without scrolling anything into view first; an element not in view, or a point outside the viewport, is `not_found`. The value is what one OS notch scrolled on the measuring machine at 150% display scaling and Windows' default three lines per notch (2026-10-07; [Sending OS input](sending-os-input.md)); the comment on `PIXELS_PER_NOTCH` says "at 100%", which the measurement does not show.
- **Each result carries when its events were sent on the page clock** (`State::stamp`, [Measuring the page](measuring-the-page.md)).
- **What `capabilities` declares for the CDP route is what it does** (`support::routes`): `takes_focus: false` for every input command (CDP input moves no window to the front; see Reference behaviour), the `right_click_menu` sentence for `click`, `ime_composition: true` for `type`, and `leaves_the_page: false`, `html5_drag: "always"` for `drag`. See [Capabilities match behaviour](capabilities-match-behaviour.md).
- **Size and count.** The text of `type` is the caller's, from an argument, stdin or an environment variable; nothing bounds its length except the command's `--timeout`, and each character costs at least two CDP calls. A drag is bounded to 10 s of moves.

## Reference behaviour

- **`Input.dispatchKeyEvent` replies only after the renderer acknowledges the event.** It also focuses the target widget first. If the event never reaches an input observer, the reply comes at once and still says success. Source: `content/browser/devtools/protocol/input_handler.cc` (Chromium main, 2026-09-25), lines 776–797 and 835–848.
- **On CDP Chromium drives an HTML5 drag itself.** When the button went down through `Input.dispatchMouseEvent` and `Input.setInterceptDrags` is off, the drag the page starts is handed to the DevTools input handler's own drag controller (`InputHandler::StartDragging`, `InputHandler::DragController` in `content/browser/devtools/protocol/input_handler.cc`), which raises `dragenter`, `dragover` and `drop` in the page from the CDP mouse moves and release, without the system's `DoDragDrop`. So the window's drop target is never asked, and `setInterceptDrags` is not needed. The drop lands where the last `dragover` was, not at the release's coordinates (`EndDragging` uses the drag state's position), and the moves' `buttons` are not read: releasing at the start point and moving with `buttons` 0 left `a_drag_on_cdp_drops_an_html5_draggable_with_tauris_drag_handling_on` green (2026-10-22, #52). With `setInterceptDrags` on, Chromium instead stops the drag and sends `Input.dragIntercepted` with the drag data (string items only), and the caller drives the page with `Input.dispatchDragEvent`; pokit does not use it. Measured 2026-10-22 (#52): on CDP the `drag` events carry `screenX` equal to `clientX`; with `setInterceptDrags` on, one probe got `dragIntercepted` with the `text/plain` item after the moves, the page having seen only `dragstart`, then `dragEnter`, `dragOver` and `drop` through `dispatchDragEvent` reached the drop zone. What each route raises, cell by cell, is in [Sending OS input](sending-os-input.md).
- **A key that does not reach the page could not be produced:** with the webview hidden (`IsVisible` false through the fixture's `hide_webview_for`), a CDP key still reached it and `visibilityState` was `hidden` (2026-10-08).
- **CDP keys reach the page whether or not the app is in front.** In the fixture, `Ctrl+KeyK` was recorded by the page both while the app was behind another window and after it was clicked. All 10 keys of a `hold` also reached the page with its window fully covered, and with it minimized (2026-10-06); Tauri keeps the webview visible when minimized ([Measuring the page](measuring-the-page.md)).
- **CDP keys do not raise WebView2's `AcceleratorKeyPressed`; OS keys do.** The fixture logged no event for CDP keys in four tries in #3, with and without `nativeVirtualKeyCode`; Chromium skips the browser's unhandled-key path for an event without it (`input_handler.cc` 1272–1275). The control ran 2026-10-07: `key Ctrl+KeyK --route os` raised it for Control and K, down and up (`vk=17`, `vk=75`), and a CDP `Ctrl+KeyK` right after raised nothing. So an app's handling of `AcceleratorKeyPressed` is reached only on `--route os` ([Sending OS input](sending-os-input.md)).
- **WebView2's right-click menu** (#120, 2026-10-26). Windows 11 26200, runtime 156, the fixture shown but not in front: the page saw `mousedown`, `mouseup`, `auxclick` and `contextmenu` (button 2), and Back, Refresh, Save as, Print, More tools and Inspect opened at the point as a visible `Chrome_WidgetWin_1` window of the browser process, extended style `0x8200088` (topmost, tool window, no-activate). On runtime 131 (`windows-2022` runner, 2026-10-26) the same menu was a `Chrome_WidgetWin_2` with the same style, visible 30–37 ms after the release returned. The foreground did not move. It stayed through a CDP left click and a CDP Escape (the page got both), a reload, and a second right-click (still one menu), until `close`; an Escape posted to the window closed it, as did `WM_CLOSE`. Over 10 rounds it was visible 0–4 ms after the release returned, closed 120–180 ms after the posted Escape, opened again each time, and the next left click landed. A tooltip of the same process and class is topmost but not a tool window (`0x8200028`).
- **A real keyboard's chord** (2026-10-07, #5): one `Ctrl+K` gave `keydown Control`, `keydown k`, `keyup k`, `keyup Control`.
- Prior art compared: penterm's held-size-key script, which sends `Ctrl+Equal` as `key "=", code "Equal", vk 187, modifiers 2` with modifiers as flags (#5).

## Cross-cutting invariants

- [Capabilities match behaviour](capabilities-match-behaviour.md) — site: `support::routes`, the `cdp` entries for `click`, `key`, `type`, `hold`, `wheel` and `drag`, against `State::click_cmd`, `State::type_cmd`, `State::key_cmd`, `State::drag_cmd`, `State::wheel_cmd`.

## Blast radius

- [Sending OS input](sending-os-input.md) — it presses keys from the same chord table and is counted by the same `NOTE_KEYDOWNS`/`check_delivery` under the same `State::keydowns` turn; a change to the codes a press sends, or to how keydowns are matched, changes what the OS route reports as delivered.
- [Sending input on macOS](sending-input-on-macos.md) — the plugin route uses the same chord table (`KeyPress::mac_events`), focus guard verdicts and delivery verdict; a changed rule here changes the macOS result too.
- [Typing Korean through the IME](typing-korean-through-ime.md) — `type_text` decides which characters are composed, and the delivery check counts each `Process` key-down by its physical `code`; changing either breaks the composed path's count.
- [Measuring the page](measuring-the-page.md) — `hold` presses chords with the same modifier events, and `measure` leaves modifier key-downs out of the keys it counts on the assumption that modifiers are keys of their own.
- [Reaching native UI](reaching-native-ui.md) — it gives the foreground back to the window `State::foreground_at_click` noted, and relies on pokit never closing a `#32768` menu of the app's own process here.
- [Finding elements on the page](finding-elements-on-the-page.md) — every element target is resolved there, inside the command's object group.
- [The app's pages](the-apps-pages.md) — input assumes `ensure_ready` passed for the page it goes to; a page not ready drops keys while CDP says success.
- [Masking secrets](masking-secrets.md) — `type --secret` sends its text through `type_text` like any other; the delivery check reports codes, not text, so nothing of the secret is in the result.
- [Platform support](platform-support.md) — `capabilities` reads `support::routes`, which states this route's behaviour.

## Known holes / open

- A right-click through `--route os` is not covered by the menu closing, and neither is a WebView2 menu over a window that covers the app (the topmost style says it draws above).
- No test makes a key truly fail to reach the page; the tests swallow keys with a page listener instead.
- Two overlapping `type`/`key` commands are serialised, but a `hold` beside them is not, and its keys show up as `keydowns_unexpected`.
- Nothing bounds the length of typed text except `--timeout`.
